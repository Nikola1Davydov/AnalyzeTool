# Где должен крутиться цикл агента и кто за него платит

[#80](https://github.com/Nikola1Davydov/AnalyzeTool/issues/80) перечисляет три варианта
хостинга AI-агента, управляющего моделью.
[#118](https://github.com/Nikola1Davydov/AnalyzeTool/issues/118) затем показывает, что
они не взаимозаменяемы, потому что их чисто разделяет одно свойство.

## Три варианта

| | A. Внешний клиент через MCP | B. Встроенный агент | C. Sidecar |
| --- | --- | --- | --- |
| Статус | **работает сегодня** | план ([#80](https://github.com/Nikola1Davydov/AnalyzeTool/issues/80)) | опция ([#118](https://github.com/Nikola1Davydov/AnalyzeTool/issues/118)) |
| Цикл крутится в | Claude Code / Desktop | фоновом `Task` внутри Revit | отдельном процессе |
| Модель | клиентская | из настроек | сильная, внешняя |
| Инициатива | **только pull, навсегда** | любая | любая |
| Цена | попробовать бесплатно | надо написать свой tool-calling-цикл | биллинг по токенам |

## Свойство, которое всё решает: у кого инициатива

MCP-сервер **не может начать разговор** — соединение открывает клиент. `2026-07-28`
ужесточает это (SEP-2260: запросы от сервера только пока сервер обрабатывает
клиентский). Уведомления сервер→клиент вроде `resources/updated` толкают *состояние*,
а не задачу; клиент от них не начинает новый ход.

Значит вариант A остаётся pull-only навсегда. Разница между A и C не в модели и не в
цене — **в том, кто может начать.**

[#118](https://github.com/Nikola1Davydov/AnalyzeTool/issues/118) дальше показывает
топологию, где каждая стрелка направлена в разрешённую сторону и будить чужой клиент
не требуется нигде:

1. сработал триггер в Revit — локально;
2. детерминированный фильтр решил, что есть о чём думать — локально, без модели;
3. плагин позвал внешний мозг — **инициатор плагин**;
4. мозг дотянулся за подробностями через наш MCP — **инициатор мозг, как клиент**;
5. ответ лёг карточкой в ленту — плагин толкнул в свой WebView, по каналу, который уже
   есть (host-initiated broadcast без request id, `clientapp/src/RevitBridge.ts:80`);
   см. [`../concepts/inbox-and-cards.md`](../concepts/inbox-and-cards.md);
6. человек открыл ленту, когда захотел — **инициатор человек**
   ([#116](https://github.com/Nikola1Davydov/AnalyzeTool/issues/116)).

Следствие, которое стоит записать: **MCP перестаёт быть альтернативой внутреннему
агенту и становится его частью.** Вся работа по
[#97](https://github.com/Nikola1Davydov/AnalyzeTool/issues/97),
[#113](https://github.com/Nikola1Davydov/AnalyzeTool/issues/113) и по описаниям команд
окупается здесь второй раз — это рука, которой удалённый мозг тянется внутрь.

## Цикл можно не писать: Microsoft Agent Framework

Появилось в комментарии к [#80](https://github.com/Nikola1Davydov/AnalyzeTool/issues/80)
от 25.07.2026 и заметно меняет оценку варианта B. MAF дошёл до GA 03.04.2026, то есть
риск превью-API снят, и он закрывает значительную часть «построить самим»:

- **агентский цикл** — `ChatClientAgent` вместо рукописного «LLM → tool calls →
  результаты → LLM». Построен на `Microsoft.Extensions.AI` / `IChatClient`, на который
  миграция и так запланирована ([#56](https://github.com/Nikola1Davydov/AnalyzeTool/issues/56)
  фаза 0), то есть ложится на существующий путь;
- **инструменты** — `AIFunctionFactory` плюс тонкий адаптер: по каждой
  `CommandRegistration` создаётся `AIFunction` (имя, описание, JSON-схема уже есть), а
  делегат кладёт `CommandRequest` в `CommandQueue`;
- **human-in-the-loop и чекпойнтинг** — workflows MAF умеют останавливаться на решении
  человека и сохранять состояние, то есть ровно требование ленты и pause/resume;
- бонусами — встроенный MCP в обе стороны и OpenTelemetry.

Оценка фазы 1 сокращается с недель до дней, и заодно исполняется фаза 0 из
[#56](https://github.com/Nikola1Davydov/AnalyzeTool/issues/56).

**Границы названы обязательными, и это главное:**

- **точка принуждения остаётся в `CommandQueue`** — гейт, белый список инструментов
  агента, исключение `ExecuteRevitCode`. Не в middleware фреймворка. **У MAF не должно
  быть пути к Revit в обход очереди.** См.
  [`../entities/command-queue.md`](../entities/command-queue.md);
- чекпойнтинг MAF — сохранение состояния, **не** durable execution: упавший процесс сам
  не возобновится. Для локального агента внутри Revit достаточно, но границу знать;
- слабые локальные модели MAF не чинит — проверка «модель пригодна для агентского
  режима» остаётся;
- спайк загрузки в изолированный ALC нужен рано: TFM подходит (net8 для R25/26, net10
  для R27), риск — транзитивные зависимости.

Для конвейеров ([#70](https://github.com/Nikola1Davydov/AnalyzeTool/issues/70)) решение
принято отдельно и осторожнее: **MAF не в V1**. Это внешняя зависимость внутри
`AnalyseTool.Core`, который грузится в ALC внутри процесса Revit и мультитаргетится. И
поскольку `.atpipe` в любом случае остаётся контрактом, принять MAF позже не дороже, чем
сейчас; честный момент — [#92](https://github.com/Nikola1Davydov/AnalyzeTool/issues/92),
где чекпойнтинг и human-in-the-loop перестают быть ожидаемыми и становятся обязательными.

## Зеркальная половина: мы как MCP-клиент

[#115](https://github.com/Nikola1Davydov/AnalyzeTool/issues/115) указывает на
неиспользованную половину. Встроенный агент — это LLM-цикл с function calling, значит он
может *потреблять* чужие MCP-серверы. Задача «написать интеграцию с каждой системой»
превращается в «уметь быть клиентом» — тот же принцип «один контракт, много
реализаций», на котором стоит весь остальной проект, только применённый к исходящим
интеграциям.

Здесь же открывается настоящий путь эскалации, и issue говорит об этом до того, как
что-либо построено: содержимое внешних систем втекает в контекст агента, который может
позвать `SetDataToParameters` на живой модели. Письмо или комментарий в трекере — текст,
который писал не пользователь, и он может содержать указания. Митигации: destructive-
вызовы в любом цикле, видевшем внешнее содержимое, — только через карточку, без
исключений; `ExecuteRevitCode` остаётся исключённым; внешнее содержимое помечается как
данные и показывается в карточке как происхождение; явный белый список серверов.

Но не в процессе Revit — по той же причине, по которой в
[#80](https://github.com/Nikola1Davydov/AnalyzeTool/issues/80) выбран LiteDB, а не
SQLite: граф зависимостей, сокеты и чужие процессы не место в CLR, общем с Revit.
Естественный дом — долгоживущий воркер, который и так смотрит папку проекта.

## Почему модель для узла не берут через MCP

Из [`../sources/pipeline-design-doc.md`](../sources/pipeline-design-doc.md), и это самый
конкретный технический аргумент во всей теме направления.

Переиспользовать существующее MCP-соединение с чат-клиентом вместо своего провайдера
выглядит соблазнительно и **не работает — по причине направления, а не трудозатрат.**
**MCP инвертирован относительно того, что нужно узлу**: через MCP вызывающий — это
AI-клиент, а AnalyseTool поставщик инструментов; AI-узлу нужно *быть* вызывающим.

В протоколе такая возможность есть (sampling: сервер просит у клиента продолжение), но
**наш транспорт её не выражает**: `RevitBridgeClient` — это TCP с соединением на каждый
запрос, один запрос и один ответ на соединение, без постоянного сокета и без корреляции по
id. Значит бридж не может ничего инициировать в сторону клиента. Поддержка sampling
означала бы двунаправленную переделку провода.

**Проверено по коду 2026-08-31:** в `RevitBridgeClient.cs` соединение создаётся внутри
запроса (`using var client = new TcpClient();`) — соединение на запрос подтверждается.
Заодно это ровно та причина, по которой в
[`../concepts/long-running-calls.md`](../concepts/long-running-calls.md) прогресс требует
нового кадра на проводе.

И даже если переделку сделать, зависимость была бы неправильной: конвейер работал бы,
только пока открыт и подключён чат-клиент пользователя, что уничтожает смысл повторяемого
прогона с ленты, а 25–50 пакетных вызовов по модели в 500 элементов ушли бы в квоту и
запросы согласия того приложения вместо предсказуемого биллинга по собственному ключу.

Настоящая роль агента здесь — другой конец: **авторство** конвейеров («пять шагов в чате →
сохранить как конвейер») и **запуск** `RunPipeline`. Агент → конвейер → детерминированные
узлы с островками ИИ — вот композиция, которая работает; агент-как-модель-внутри-узла —
та, которая нет.

## Блокер коммерческий, а не технический

[#118](https://github.com/Nikola1Davydov/AnalyzeTool/issues/118) помечает это как то,
что надо решить **до** кода, потому что от этого зависит вся экономика:

- **подписку Claude Code так вызвать нельзя** — она авторизует человека в клиенте,
  программный доступ это отдельный продукт с оплатой за токены;
- **ключ пользователя (BYO-key)** — чисто, законно и работает, инфраструктура уже есть
  (`AiProviderRegistry` с шифрованием DPAPI). Прагматичный ответ по умолчанию;
- **наш ключ с перепродажей** — проще пользователю и хуже всего для вопроса локальности
  ниже;
- **Claude Code пользователя как sidecar** — дешевле всего для него, но допустимо ли
  третьему продукту программно его водить, **в условиях не проверено**. Пока не
  подтверждено — на этом строить нельзя.

И потолок расходов — не настройка, а обязательный элемент: интерактивная трата
коррелирует с вниманием человека, проактивная — нет. Жёсткий дневной потолок, видимый;
молчание по его достижении — нормальное поведение, а не отказ.

## Локальные модели — условие допуска, а не бесплатный тариф

[#117](https://github.com/Nikola1Davydov/AnalyzeTool/issues/117) переосмысляет фазу 2
из [#56](https://github.com/Nikola1Davydov/AnalyzeTool/issues/56) («embedded inference,
free tier»). Для проектного бюро данные модели и переписка с заказчиком часто **не
могут покидать периметр** — это условие договора или регламента, а не предпочтение и не
вопрос цены. Для такого клиента локальная модель не дешёвый вариант, а единственный
допустимый, и облачная не продаётся ни за какие деньги, потому что решает не тот, кто
пользуется.

Если это так: фаза 2 из [#56](https://github.com/Nikola1Davydov/AnalyzeTool/issues/56)
— условие входа в целый сегмент, а не приятное дополнение; готовность платить может
быть **за саму локальность**; белому списку из
[#115](https://github.com/Nikola1Davydov/AnalyzeTool/issues/115) нужно состояние
«никаких внешних серверов»; а настройка модели агента должна выражать «ничего не
покидает машину» как режим, который нельзя нарушить добавлением провайдера.

Неприятное следствие, названное в issue: локальные модели слабее, а слабая модель в
tool-calling-цикле ломается, а не работает хуже. Значит сегмент, которому локальность
нужнее всех, получает агента, который работает хуже всех, и ломается тихо. Предлагаемый
ответ — сузить обещание для таких клиентов: детерминированные проверки плюс локальная
модель на объяснение и формулировку, где LLM не принимает решений. Это снова
[`../concepts/deterministic-core.md`](../concepts/deterministic-core.md).

> [!warning] не проверено
> [#117](https://github.com/Nikola1Davydov/AnalyzeTool/issues/117) сам помечает свою
> посылку как рыночную гипотезу, а не факт, и предлагает три вопроса реальным бюро —
> включая то, засчитывается ли «европейский хостинг» как достаточная мера или требуется
> именно локальность. Стоит выяснить до вложений в фазу 2.

## Три яруса задержки

Полезное примирение из
[#118](https://github.com/Nikola1Davydov/AnalyzeTool/issues/118): мгновенные подсказки в
интерфейсе (призрачный текст,
[#45](https://github.com/Nikola1Davydov/AnalyzeTool/issues/45)) обязаны быть локальными
— облачный круг на такой задержке недопустим. Фоновой проактивности облако подходит
идеально. Интерактивный чат облако терпит. Значит локальный вывод не умирает, даже если
побеждает облачный мозг: он обслуживает другой ярус.
