# Встроенный агент: решение и план

Итог разговора 2026-09-02 (владелец + ассистент) о том, как углубить внутренний ИИ —
чтобы модель сама звала команды, с ней можно было говорить, а слабая локальная модель
могла передать тяжёлую работу сильной. Записано как план в
[#133](https://github.com/Nikola1Davydov/AnalyzeTool/issues/133); здесь — почему так.
Продолжает [`agent-hosting.md`](agent-hosting.md), где перечислены варианты; тут выбран один.

## Что есть сегодня

Внутренний ИИ — шесть команд с фиксированными промптами
(`src/AnalyseTool.Tools/Ai/Features/`) поверх `IChatClient` из Microsoft.Extensions.AI.
Ответ не стримится по-настоящему (`OpenAiCompatibleChatClient.cs` отдаёт один кусок),
инструментов модель не видит, диалога нет. Фундамент при этом правильный: `IChatClient` —
ровно тот интерфейс, на котором строится цикл с вызовом инструментов, а провайдеры с
шифрованными ключами уже есть (`AiProviderRegistry.cs`).

## Три решения

**1. Сильный мозг — облачная модель по ключу пользователя.** Не sidecar и не программное
управление Claude Code: реестр провайдеров уже умеет это подключить, и ничего нового
строить не надо. Когда локальной модели не хватает, разговор переключается на облачный
провайдер, и он делает тяжёлую часть. Вариант C из `agent-hosting.md` закрыт осознанно.

**2. «Позвать сильного агента через MCP» — не механизм.** Направление MCP не позволяет
плагину начать разговор с внешним клиентом: соединение открывает клиент, спецификация
2026-07-28 разрешает серверу спрашивать клиента только внутри клиентского запроса, а наш
провод — соединение на запрос без sampling. Поэтому эскалация — это **смена провайдера
внутри собственного цикла**, а не обращение наружу. MCP остаётся рукой внешнего агента,
не нашим способом до него дотянуться.

**3. Локальная модель не становится лишней.** У неё две работы, которые облако не
возьмёт: мгновенные подсказки в интерфейсе и бюро с запретом на выгрузку данных
([#117](https://github.com/Nikola1Davydov/AnalyzeTool/issues/117)). Для второго нужен
режим «ничего не покидает машину», который нельзя нарушить добавлением провайдера.

## Где что живёт — по контракту зависимостей

Цикл нуждается в трёх вещах, живущих в разных проектах: каталог команд и очередь (Core),
провайдеры (Tools/Ai), окно (App). Tools не может ссылаться на Core, поэтому:

- **Core** — механизм, безголовый и проверяемый на ярусе 1 с поддельным `IChatClient`:
  адаптер «одна `AIFunction` на `CommandRegistration`» (имя, описание и JSON-схема уже есть
  для MCP), делегат кладёт `CommandRequest` с источником `agent` и гейтом в `CommandQueue`;
  сам цикл — `FunctionInvokingChatClient` из Microsoft.Extensions.AI, не рукописный;
  бюджет шагов и токенов; белый список.
- **App** — только проводка: берёт `IChatClient` из `AiClientFactory`, регистрирует команду
  чата (`HiddenFromMcp`), стримит на страницу по каналу прогресса, который уже есть.
- **Tools/Ai** — провайдеры как были; `OpenAiCompatibleChatClient` учится `tools` в запросе,
  разбору `tool_calls` и настоящему SSE. Для Ollama это умеет OllamaSharp.

Точка принуждения остаётся в очереди, не в middleware — правило из
[`../entities/command-queue.md`](../entities/command-queue.md) не меняется.

## Пересмотр тем же вечером: слабая модель в цикле и место в очереди дел

Владелец усомнился: если внутренний агент зовёт команды, а модель слабая — насколько это опасно,
полезно и необходимо. Ответ, с которым сошлись:

- **Опасно** не само по себе, а в сочетании «слабая модель + запись». Слабая модель в цикле не
  деградирует плавно, а ломается: зацикливается, путает аргументы, выдумывает ids. Пока ей доступно
  только чтение, худшее — потерянное время; запись без подтверждения — тихая порча модели. Гейт в
  очереди — условие существования, и он для облачной модели тоже.
- **Полезен** цикл почти целиком за счёт сильной модели. Локальным 7–14B служит другой паттерн,
  который уже есть: плагин собирает данные детерминированно, модель формулирует
  ([`../concepts/deterministic-core.md`](../concepts/deterministic-core.md), команды `Ollama*`).
- **Необходимости** нет: сильный агент с циклом уже существует — внешний MCP-клиент, доведённый
  2026-09-02 до надёжности (#99, #108, #109, #110, #134). Встроенный чат добавляет не способность, а
  продуктовую вещь: чат в Revit тому, у кого внешнего клиента нет.

Итог ([#133](https://github.com/Nikola1Davydov/AnalyzeTool/issues/133) переписан): цикл с инструментами только для моделей, объявляющих их поддержку (по
факту облачных; Ollama говорит об этом в `/api/show`); локальная модель получает чат без инструментов и
рецепты с детерминированной подготовкой контекста; всё это **после фундамента** — теневого индекса,
инвентаря и разметки BIM-руководства, потому что модуль проверки от агента не зависит.

## Порядок шагов — после фундамента

1. **Чат в Revit по облачному ключу, пока без инструментов:** страница в док-панели, история на
   сессию документа, стриминг, существующий выбор провайдера и модели. Локальные модели здесь тоже
   работают, только разговором.
2. **Инструменты для способных моделей, гейт в очереди.** Курируемый набор из 6–8 инструментов для
   локальных моделей (полный каталог из 20+ съедает контекст), `GetModelOverview` первым
   шагом, `ExecuteRevitCode` исключён, деструктивные команды — через pre-execution gate в
   карточку подтверждения, жёсткий лимит шагов на ход. Ollama через `/api/show` говорит,
   умеет ли модель `tools`; модель без них получает режим «только разговор» с честной
   подписью, а не тихие поломки — слабая модель в цикле ломается, а не работает хуже.
2. **Чат** в док-панели: история на сессию документа, стриминг через host-initiated канал
   в `src/clientapp/src/RevitBridge.ts`, карточки подтверждения в ленте сообщений,
   существующий выбор модели и провайдера. Модель без поддержки инструментов в цикл не попадает.
3. **Эскалация = смена провайдера.** «Продолжить с <облачный провайдер>» перезапускает тот
   же разговор или сжатую задачу на сильной модели; видимый дневной потолок расходов;
   режим «только локально».
4. Проактивность и лента из
   [#80](https://github.com/Nikola1Davydov/AnalyzeTool/issues/80) /
   [#118](https://github.com/Nikola1Davydov/AnalyzeTool/issues/118) — после этого, не вместо.

Мы как MCP-клиент ([#115](https://github.com/Nikola1Davydov/AnalyzeTool/issues/115)) —
позже и не в процессе Revit, как и записано в `agent-hosting.md`.
