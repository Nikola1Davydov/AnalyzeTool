# Центр контекста: одно знание проекта для агентов во всех инструментах

Слой знаний проекта и бюро (стандарт, требования, маппинги, решения, находки), который любой
агент в любом инструменте — плагин в Revit, worker над IFC, Claude Desktop у координатора —
читает и дописывает через один MCP-сервер. Концепт со слов владельца, 2026-09-13; не построен.

Главное решение концепта: **это не новый формат, а раскладка папки из существующих
стандартов плюс сервер доступа.** Формат без инструментов, которые его читают, не стоит
ничего, а Solibri и Revit чужой формат читать не будут. Центр становится реальным не потому,
что программы читают файл, а потому, что агенты внутри программ ходят на один сервер.

## Чего не хватает отрасли

| Слой | Стандарт | Есть |
| --- | --- | --- |
| модель («что») | IFC, AEC Data Model, Speckle | да |
| требования | IDS | да |
| замечания | BCF | да |
| словарь | bSDD | да |
| **контекст проекта для агента («почему и как у нас принято»)** | — | **нет** |

Speckle и AEC Data Model централизуют данные модели. Центр контекста — другой слой: как
бюро называет, что обязательно на какой стадии, как типы уезжают в IFC, что решили на
совещании и почему. Сегодня это Word, переписка и головы.

## Три части

```
клиенты        плагин Revit      worker над IFC      Claude Desktop / Teams     CI в CDE
                     │                 │                    │                     │
                     └────────┬────────┴─────────┬──────────┴──────────┬──────────┘
                              ▼                  ▼                     ▼
сервер                        AnalyseTool.Context (MCP, stdio + TCP)
                              читает папку, отвечает с цитатами, принимает черновики
                                                │
хранилище      генеральная папка бюро  ──►  папка проекта  ◄──  inbox\ (шина)
               (только источники)           (стандарт, маппинги, решения, находки)
```

1. **Хранилище** — [`../entities/project-folder.md`](../entities/project-folder.md) из #124,
   расширенная. Внутри не своя схема, а композиция стандартов: IDS для требований, BCF для
   замечаний, JSON для маппингов, Markdown для прозы и решений.
2. **Сервер доступа** — один MCP-сервер над папкой. Тот же контракт, что уже есть у
   плагина (`McpWire.cs`), но подложка — папка, а не живой Revit. Это ровно headless-доступ
   из #125, доведённый до общего входа для всех клиентов.
3. **Дисциплина ведения** — агенты читают свободно, пишут только черновики в `inbox\`,
   человек утверждает в плагине. Инвариант из
   [`../concepts/deterministic-core.md`](../concepts/deterministic-core.md): агент, пишущий
   правила напрямую, — это ИИ, пишущий политику.

## Раскладка папки

Расширение раскладки из #124. Что уже было — помечено.

```

                          генеральную папку, версия формата
  sources\                (#124) неизменяемые входы: PDF, DOCX, письма, транскрипты
  standard\

    rules.ids             исполнимые требования — экспорт свода в IDS
    template.params       (#121) шаблон параметров, GUID как идентичность
    mappings\
      ifc-export.json     тип → IfcExportAs, PredefinedType, Pset
      classification.json тип → DIN 276 / eBKP-H / Uniclass
      value-aliases.json  «EI 30», «ei30» → «EI30»: подтверждённые слияния
  decisions\
    2026-09-13-brandschutz-parameter.md   одно решение — один файл, с датой и кем принято
  findings\
    <model-guid>\2026-09-13.jsonl         результат прогона, только на дозапись
    export\*.bcf                          то же для смежников
  inbox\                  (#126) шина: карточки, черновики правил и маппингов
  log\anna.jsonl          (#124) журнал, шардован по людям
  .cache\                 (#124) снимки источников и модели по хешу
```

Правило распределения: **что выражается стандартом, живёт в стандарте; что не выражается,
живёт прозой во втором регистре.** Своё здесь только три вещи: раскладка папки, манифест и
схемы трёх JSON-маппингов. Всё это wire-контракт в дисциплине #131: версия формата в каждом
файле, читатель терпим на версию назад.

Порядок чтения — из [`../entities/general-folder.md`](../entities/general-folder.md):
проектный стандарт выше общего, расхождение — находка линта, а не тихий выбор.

## Поверхность сервера

Чтение — для любого клиента, без ограничений:

| Инструмент | Отвечает на |
| --- | --- |
| `GetProjectContext` | что за проект, стадия, модели, какой стандарт действует |
| `GetRequirements(category, stage)` | какие параметры обязательны для стен на LP3 — из `rules.ids` и шаблона |
| `GetMapping(kind, type)` | как тип уезжает в IFC / какой класс DIN 276 |
| `SearchStandard(query)` | цитаты из `regelwerk.md` со ссылкой на источник и страницу |
| `GetDecisions(topic)` | что решили про огнестойкость и когда |
| `GetFindings(model, since)` | что нашёл последний прогон, что ушло в BCF |
| `GetInventory(model)` | плотные строки инвентаря из снапшота — та же форма, что для агента в Revit ([`../concepts/agent-legibility.md`](../concepts/agent-legibility.md)) |

Запись — только черновики, только в `inbox\`:

| Инструмент | Кладёт |
| --- | --- |
| `ProposeRule` | черновик правила с цитатой (#123) |
| `ProposeMapping` | черновик строки маппинга: тип, предложение, обоснование |
| `RecordDecision` | черновик решения из транскрипта или переписки |

Утверждение — в плагине, с предпросмотром эффекта («правило пометит 48 из 312»). Никакого
авто-применения из мессенджера, как в #126.

## Клиенты и что каждый берёт

| Клиент | Читает | Пишет | Особенность |
| --- | --- | --- | --- |
| плагин Revit | всё | утверждает черновики, снапшоты, находки | единственный, у кого есть обратная петля «находка → исправление» |
| worker над IFC (xBIM) | `rules.ids`, маппинги | находки, BCF | проверка без Revit, в CI по CDE |
| Claude Desktop / Teams | всё | черновики | координатор без Revit задаёт вопросы и получает ответы с цитатами |
| Solibri, BIMcollab | `rules.ids`, `*.bcf` | — | не наши агенты; читают только стандартные файлы, и это принятая рамка |

Последняя строка важна: встроенные ассистенты вендоров в центр не пойдут. Мост к ним — IDS и
BCF, ничего больше.

## Три сценария

**Руководство → свод → две проверки.** Бюро кладёт руководство в `sources\`. Импорт даёт
черновики правил с цитатами, человек утверждает, свод экспортируется в `rules.ids`.
Плагин проверяет живой индекс на каждой синхронизации; worker проверяет IFC перед сдачей
тем же файлом; Solibri у заказчика читает тот же `.ids`. Одно авторство, три места проверки.

**Вопрос без Revit.** Координатор в Claude Desktop: «какие двери на третьем этаже без
огнестойкости и что об этом требует стандарт». `GetInventory` даёт список из снапшота,
`SearchStandard` — цитату, `GetDecisions` — что уже решили. Ни одного открытого Revit.

**Находка в IFC возвращается в модель.** Worker нашёл расхождение, положил BCF и карточку в
`inbox\`. Плагин при открытии модели показывает карточку с предложенным исправлением;
человек применяет. Это #126, только источник карточки — не Teams, а worker.

## Где здесь ИИ

Ровно там, где в [`checking-module.md`](checking-module.md): составляет и объясняет, не
решает. Руководство → черновики правил и IDS (один раз на документ). Транскрипт → черновик
решения. Тип → предложение маппинга, человек утверждает, дальше маппинг применяется кодом.
Пятьсот находок → двадцать осмысленных BCF с текстом для смежника. Вердикт о соответствии и
геометрия — никогда.

## Фазы

| Фаза | Что появляется | Проверяет |
| --- | --- | --- |
| 0 | раскладка папки, манифест, `regelwerk.md`, `decisions\` — руками, без кода | нужна ли структура вообще: одно бюро, один проект |
| 1 | `AnalyseTool.Context`: MCP только на чтение над папкой; клиенты — плагин и Claude Desktop | задаёт ли координатор без Revit вопросы центру и полезны ли ответы |
| 2 | экспорт свода в `rules.ids`, worker над IFC на xBIM | одно авторство, две проверки |
| 3 | черновики через `inbox\`, утверждение в плагине | безопасная запись из внешних клиентов |
| 4 | второе бюро, генеральная папка | переносимость: свод, написанный через `BuiltInCategory` (#113), а не через локальные имена |

Фаза 0 — не код, и это принципиально: если папка с прозой и решениями никому не нужна,
сервер над ней тем более.

## Чего центр не делает намеренно

- **Не хранит геометрию и не заменяет CDE.** Граница «хранится против вычисляется» из
  [`checking-module.md`](checking-module.md) действует и здесь; данные модели — в снапшотах
  и в живом индексе, не в центре.
- **Не требует нашего сервера.** Файловый шар, OneDrive или ACC Docs — бэкенд за
  интерфейсом, как в #131. Для периметрового клиента (#117) ничего не покидает сеть.
- **Не вводит бинарный или свой формат.** Markdown, JSON, IDS, BCF. Единственная своя часть —
  раскладка и три схемы маппингов.
- **Не пускает агентов к прямой записи.** Только черновики, только через `inbox\`.

## Сильные стороны и риски

За: ложится на всё спроектированное (#124, #125, #126, #131, #132), нейтрален к вендорам,
один свод обслуживает все подложки, ров накапливается с каждым месяцем ведения.

Против, и это надо помнить:

- **Курица и яйцо.** Пока клиент один, центр выглядит как папка с файлами. Фаза 1 с двумя
  клиентами существует именно для того, чтобы это проверить рано.
- **Управление содержимым — оргпроблема.** Кто пишет, кто утверждает, как разрешаются
  конфликты проекта и бюро. Код даёт lock-файл и линт, остальное — регламент бюро.
- **Соблазн масштаба.** «Центр для всех программ» легко превращается в операционную
  систему BIM. Граница: только знания и требования.

## Не проверено

> [!warning] не проверено
> Выразительность IDS. Фасеты IDS 1.0 — entity, attribute, property, classification,
> material, partOf. Правила про «используется ли тип», «нет in-place семейств», «ничего на
> Workset1» и связи вида «дверь в стене» в IDS не выражаются. Значит `rules.ids` — экспорт
> **подмножества** свода, а не сам свод; сколько это подмножество от реального руководства
> бюро, покажет только разметка одного руководства — тот же следующий шаг, что назван в
> конце [`checking-module.md`](checking-module.md).

> [!warning] не проверено
> Схемы маппингов. Три JSON-файла спроектированы с потолка; их надо строить от двадцати
> реальных типов одного проекта, а не заранее целиком — то же правило, что для языка правил.

> [!warning] не проверено
> Один сервер на несколько проектов. Клиент вроде Claude Desktop у координатора работает с
> бюро целиком, а не с одним проектом. Адресация «канал = проект» из #125 покрывает Teams;
> для desktop-клиента нужен явный выбор проекта в `GetProjectContext` или обход списком, как
> у worker'а в [`agent-hosting.md`](agent-hosting.md).
