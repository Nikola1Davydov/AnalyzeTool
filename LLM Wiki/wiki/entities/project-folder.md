# Папка проекта

Общее хранилище источников, свода правил, шаблона параметров и журнала — обычная папка на
файловом шаре или в OneDrive. Спроектирована в
[#124](https://github.com/Nikola1Davydov/AnalyzeTool/issues/124), не построена.

На неё опираются пять планов, поэтому у неё своя страница: без папки не работают ни
headless-доступ, ни обратная петля из чата, ни шаблон параметров, ни индексация документов.

## Раскладка

```
по умолчанию:  %LOCALAPPDATA%\AnalyseTool\projects\<model-guid>\   ← работает сразу, соло
в настройках:  «Папка проекта» → \server\Projekte\WohnparkSüd\AnalyseTool\

внутри:
  sources\          ← сюда кидают всё: PDF, письма, транскрипты, .txt параметров
  regelwerk.md      ← свод: правила и наставления, с цитатами
  template.params   ← шаблон параметров (#121)
  log\              ← журнал
  .cache\           ← служебное: снимки по хешу, индекс извлечения
```

**Не в RVT.** Extensible Storage раздувает файл и уезжает ко всем — тот же запрет, что для
теневого индекса в [#80](https://github.com/Nikola1Davydov/AnalyzeTool/issues/80), а для PDF
тем более.

## Папка и есть интерфейс

Ключевое решение: не «загрузка в систему», а обычная папка, в которую бюро и так умеет
класть файлы. Explorer как UI с нулевым обучением. Паттерн в продукте уже есть — папки
библиотек в палитре семейств.

Выбрал общую папку — команда соединилась: несколько человек кидают документы, свод общий,
журнал общий. **Коллаборация без единого нашего сервера**; файловый шар и есть бэкенд.

Для периметрового клиента ([#117](https://github.com/Nikola1Davydov/AnalyzeTool/issues/117))
это идеально с двух сторон: ничего не покидает сеть бюро, а нам нечего хостить и нечего
проходить по GDPR-аудиту.

## Идентичность по хешу, а не по пути — насмерть

Папка живая: файлы переименуют, поправят, удалят. А цитата вида «R-012 → стр. 8» обязана
открываться годами. Поэтому при первом прочтении файл получает хеш, снимок уходит в
`.cache\`, и цитаты ссылаются на хеш.

Выигрыш в том, что поломки перестают быть поломками и становятся **находками линта**:

| Что случилось | Что говорит система |
| --- | --- |
| файл изменился | новая версия плюс линт дрейфа: «v8 пришла, 12 правил цитируют v7, страница 8 изменилась — перепроверить?» (диффом извлечения v7 против v8) |
| файл удалили | «источник исчез из папки, снимок сохранён, 12 правил цитируют» |
| тот же файл под другим именем | узнан по хешу, дубликата нет |

**Дрейф источника — тот же класс тихого устаревания**, ради которого существует линт этой
вики, только на уровне документов бюро. И он тоже ловится механически.

## Два настоящих риска

**Одновременная запись.** Несколько человек и агентов в `regelwerk.md` на SMB — потерянные
правки. Решение без переусложнения: правки свода идут через плагин с **lock-файлом** («свод
редактирует Анна» — модель, которую Revit-пользователи знают наизусть), а **журнал шардован
по людям** (`log\anna.jsonl`) и сливается при чтении, поэтому записи не конкурируют вообще.

По сути это worksharing для знаний: центральная папка, локальные кэши, моменты
синхронизации. Аудитория уже знает эту механику.

**Папка станет свалкой.** Кинут всё: фото, ZIP, «Kopie von Kopie (2)». Система триажит, а не
давится: новый файл → очередь «Новые источники (N)» → человек или черновик от агента
распределяет — в правила, только в поиск, или игнорировать. **Необработанный файл не
ошибка**, он просто пока не цитируется.

Наблюдатель за папкой уже заявлен в [#56](https://github.com/Nikola1Davydov/AnalyzeTool/issues/56)
фазе 3: та же папка, тот же watcher, два потребителя — правила и извлечение.

## Папка как шина сообщений

Отдельное свойство, ради которого она и работает во внешнем контуре
([#126](https://github.com/Nikola1Davydov/AnalyzeTool/issues/126)): сервис кладёт карточку в
`inbox\`, плагин читает её при открытии модели. **Прямого соединения Teams ↔ Revit нет.**

Отсюда устойчивость ко времени достаётся даром: комментарий, написанный в воскресенье
вечером, спокойно ждёт до понедельника 8:00, и никого не надо будить. Разбор самой петли —
[`../concepts/inbox-and-cards.md`](../concepts/inbox-and-cards.md).

## GDPR — с первого дня, а не после вопроса юриста

Письма и транскрипты совещаний — персональные данные конкретных людей; транскрипты ещё и
согласие на запись. В [#56](https://github.com/Nikola1Davydov/AnalyzeTool/issues/56) это уже
стоит открытым вопросом.

В дизайне это должно быть с самого начала: «эти типы файлов индексируем только после решения
бюро». Дешевле заложить, чем переделывать после первого вопроса.

## Наблюдение: это тот же паттерн, что у этой вики

Не решение из бэклога, а замеченное сходство, которое может сэкономить проектирование.

`sources\` плюс `regelwerk.md` — структурно ровно `raw/` плюс `wiki/` этого хранилища:
неизменяемый слой источников, поверх него поддерживаемый свод, цитаты вниз, журнал сбоку.
Значит соглашения, выработанные здесь, переносятся туда почти без изменений: неизменяемость
источников, след у каждого утверждения, линт как отдельная операция, журнал только на
дозапись.

И наоборот: линт дрейфа версий из [#124](https://github.com/Nikola1Davydov/AnalyzeTool/issues/124)
— это проверка, которой не хватает здесь. У нас снимки датированы, но никто не сверяет, не
разошёлся ли свежий снимок с тем, на который ссылаются страницы.

## Не проверено

> [!warning] не проверено
> Поведение lock-файла на реальном SMB-шаре и в OneDrive: как быстро освобождается, что
> происходит при упавшем Revit с незакрытым локом. Ровно на этом уже обожглись в
> [#103](https://github.com/Nikola1Davydov/AnalyzeTool/issues/103), где OneDrive держал
> хендл и мешал удалить папку.

> [!warning] не проверено
> Ключ папки — `<model-guid>` — та же идентичность, что у теневого индекса, и упирается в
> тот же неотвеченный вопрос: регенерируется ли `Document.CreationGUID` при Save As
> ([#85](https://github.com/Nikola1Davydov/AnalyzeTool/issues/85)). Минутный эксперимент
> закрывает оба.
