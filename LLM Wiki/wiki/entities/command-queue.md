# CommandQueue

Единственная дверь, через которую любой транспорт попадает в платформу.
`internal sealed class` в `src/AnalyseTool.Core/Common/Dispatch/CommandQueue.cs`, 135
строк вместе с конвертом запроса.

Страница написана по коду 2026-08-31, а не по issue: на `CommandQueue` ссылались пять
страниц этой вики, и ни одна не открывала файл.

## Главное недоразумение: это не очередь

Собственный комментарий класса говорит прямо:

> Not yet a scheduling queue: requests execute immediately and may overlap — actual Revit
> model access still serializes on the RevitTaskHub external event.

То есть **`CommandQueue` ничего не ставит в очередь и ничего не сериализует.** Запросы
исполняются сразу и могут перекрываться. Сериализация происходит уровнем ниже, на
внешнем событии `RevitTaskHub`, и только для доступа к модели.

Воронка существует не ради планирования, а ради **места**: чтобы планирование,
приоритеты, гейты согласования и политику на источник можно было добавить в ОДНОМ месте,
не трогая транспорты. Добавление транспорта не должно требовать здесь ни строчки.

Из этого следуют вещи, которые в бэклоге выглядят разными задачами, а на самом деле все
упираются сюда: ограничение частоты
([#112](https://github.com/Nikola1Davydov/AnalyzeTool/issues/112)), проверка лицензии
([#120](https://github.com/Nikola1Davydov/AnalyzeTool/issues/120)), и то, что прогон
конвейера не атомарен ([#90](https://github.com/Nikola1Davydov/AnalyzeTool/issues/90)).

## Конверт: `CommandRequest`

`record CommandRequest(string Command, JToken Payload, string Source)` плюс три
необязательных свойства:

| Поле                | Что несёт                                                                                           |
| ------------------- | --------------------------------------------------------------------------------------------------- |
| `Command`           | зарегистрированное имя; у расширений это `<id>.<name>`                                              |
| `Payload`           | сырой JSON; `JValue.CreateNull()`, если команда не принимает аргументов                             |
| `Source`            | личность транспорта для логов, телеметрии и политики: `webview2`, `mcp`, `ribbon`, будущий `remote` |
| `CancellationToken` | по умолчанию `None`; доходит до каждой команды                                                      |
| `Progress`          | `IProgress<ProgressInfo>?`, привязывается транспортом к конкретному вызывающему (окну, id запроса)  |
| `Gate`              | `Func<CommandRegistration, Task<bool>>?` — предвыполнительный гейт                                  |

В коде оставлен комментарий о том, куда это будет расти: `Priority`, когда очередь
действительно начнёт планировать, и `CallerIdentity`, когда появятся удалённые
транспорты с аутентификацией. Свойства `init` подобраны так, что добавление не ломает
существующих вызывающих.

## Что делает `ExecuteAsync` — цепочка декораторов

С 2026-09-25 (коммит e5d9fe5) `CommandQueue.ExecuteAsync` — одна строка: запрос уходит в цепочку
`ICommandExecutor`, собранную в конструкторе очереди
(`src/AnalyseTool.Core/Common/Dispatch/CommandPipeline.cs`):

```
Logging → Gating → Tracking → Dispatching
```

Каждая ступень держит ровно одну заботу; ступень, которой нужно поменять запрос (трекер
подставляет свой токен и sink прогресса), передаёт копию через `with` — запись, построенную
транспортом, никто не мутирует.

1. **`LoggingExecutor`** — одна строка лога на **исход**: finished с длительностью, cancelled,
   refused, failed с полным исключением, типом и сообщением корневой причины и сокращённым
   payload. До этой ступени очередь писала только «invoked» на Debug, а команда, упавшая из окна
   WebView, не оставляла в логе ничего: транспорт отдаёт странице `ex.Message` и выбрасывает
   остальное. Теперь те же строки получает каждый транспорт, ничего не логируя сам; бридж MCP
   перестал логировать сбои очереди второй раз.
2. **`GatingExecutor`** — гейт транспорта, если он есть. Резолвится `CommandRegistration`, и
   гейт видит метаданные — имя, `ReadOnly`, `Destructive`. Отказ — `UnauthorizedAccessException`.
   Тонкость из комментария: неизвестное имя гейт не трогает, оно проваливается к диспетчеру,
   который откажет по имени. Всё, что **может** исполниться, сначала резолвит регистрацию —
   значит ни одна команда не доходит до диспетчера, минуя гейт своего транспорта.
3. **`TrackingExecutor`** — реестр исполняющихся команд и событие `RunningChanged`,
   отмена на прогон, которую может нажать **человек** (`TryCancel(runId)` — кнопка окна
   активности, [#134](https://github.com/Nikola1Davydov/AnalyzeTool/issues/134)), и мультикаст
   прогресса слушателям очереди (`ProgressReported`) — синхронно, на потоке отчёта.
4. **`DispatchingExecutor`** — `CommandDispatcher.DispatchAsync`.

Новая сквозная забота (кэш, политика по источнику, планирование) — ещё один декоратор в
конструкторе очереди; транспорты и другие ступени не меняются. Это ровно то, что
[#153](https://github.com/Nikola1Davydov/AnalyzeTool/issues/153) предлагал «когда понадобится»
— issue при этом открыт, см. [`../analyses/architecture-review-2026-09.md`](../analyses/architecture-review-2026-09.md).

## Тихие команды и почему это про читаемость лога

Список `Quiet` в `CommandPipeline` (до 2026-09-25 — `CommandQueue.Untracked`): такие команды не
попадают ни в реестр исполняющихся, ни в лог. В списке ровно одно имя: `GetQueueStatus`. Причина в комментарии двойная — опрос статуса
не должен делать инструмент «занятым» и не должен переоткрывать событие, на которое сам
же отвечает.

Второй абзац комментария стоит прочитать целиком, потому что он связывает мелочь с
крупным дефектом: индикатор спрашивает каждые пару секунд, на каждое открытое окно, всё
время работы Revit; в одной сессии намерили **~840 таких строк вокруг трёх настоящих
событий**. Вывод в коде сформулирован так: это не делает лог многословным, это делает
его нечитаемым, а нечитаемый лог — причина, по которой команда, падавшая весь вечер, так
и не была диагностирована.

Это про [#98](https://github.com/Nikola1Davydov/AnalyzeTool/issues/98) и
[#97](https://github.com/Nikola1Davydov/AnalyzeTool/issues/97), и то же изменение видно в
истории репозитория как коммит «Make the log readable: stop logging the status poll».

## Наблюдаемость

- `Running` — снимок исполняющихся команд, старые первыми: `(Id, Command, Source, StartedUtc)`.
- `RunningChanged` — событие на рабочем потоке; подписчик, бросивший исключение,
  логируется предупреждением и не роняет очередь.
- `RegisteredCommands`, `IsRegistered`, `GetRegistration` — интроспекция для транспортов:
  `tools/list` в MCP, таблица команд в настройках, и лента, решающая, может ли клик по
  кнопке запустить команду или сначала надо спросить аргументы.

## Где сериализуется на самом деле: `RevitTaskHub`

`RevitTaskHub.cs`, 102 строки. Одно долгоживущее `ExternalEvent`, созданное однажды в
валидном API-контексте; вызывающие из любого потока кладут синхронную работу в
`ConcurrentQueue` и ждут результат.

Ключевая деталь — `Execute` **разбирает всю очередь целиком** в одном заходе:

```csharp
while (_queue.TryDequeue(out Action<UIApplication>? item)) { item(app); ... }
```

Отсюда два следствия, которые в бэклоге выглядят несвязанными:

- **Прогон конвейера не атомарен** — между узлами успевают отработать другие транспорты
  ([#90](https://github.com/Nikola1Davydov/AnalyzeTool/issues/90) принимает это для V1 и
  требует, чтобы изменяющие узлы перепроверяли свои предусловия).
- **Одно модальное окно замораживает платформу**, а не одну команду
  ([#88](https://github.com/Nikola1Davydov/AnalyzeTool/issues/88)): диалог, поднятый
  внутри `item(app)`, держит этот цикл, а он — единственный путь к модели для всех.

Продолжения намеренно не выполняются на потоке Revit:
`TaskCreationOptions.RunContinuationsAsynchronously`, с комментарием, что иначе
продолжение могло бы повторно войти в обработчик события или заблокировать его.

## Как платформа понимает, что Revit занят

Два независимых механизма, и они отвечают на разные вопросы.

**`RevitAvailability`** — техника из RevitDBExplorer: хост держит постоянную подписку на
`UIApplication.Idling`, обработчик только штампует время. Пока Revit простаивает, событие
идёт непрерывно, поэтому устаревший штамп означает, что Revit держит модальное окно,
режим редактирования или родная команда. Порог — `BusyThresholdSeconds = 1.5`, то есть
обнаружение примерно за секунду и **при нулевом трафике очереди**.

**`RevitTaskHub.Status`** — `(Pending, WaitingSeconds, Executing)`, и различие между
последними двумя полями важнее, чем кажется:

- ждём, при этом **ничего не исполняется** → Revit не может уйти в idle: человек в
  диалоге, в режиме редактирования или в родной команде;
- ждём, при этом **что-то исполняется** → просто наша текущая работа длинная. Это
  безобидно.

Ровно это различие не удалось провести в
[#104](https://github.com/Nikola1Davydov/AnalyzeTool/issues/104), где команда «зависла»
на четыре минуты: `GetQueueStatus` во время зависания никто не спросил, а он бы ответил.

## Баг, оставленный в коде как предупреждение

`EnqueueAsync` увеличивает `_pending` **до** постановки в очередь, и рядом объяснено
почему: при обратном порядке `Execute` успевал снять и уменьшить счётчик раньше, чем
приращение долетало, `_pending` уходил в −1, условие сброса `== 1` больше не
срабатывало, и `GetQueueStatus` мерил `waitingSeconds` от протухшей метки — **сообщая
«Revit занят» на простое, ровно по тому сигналу, которому агентам велено доверять.**

Стоит помнить при чтении [#104](https://github.com/Nikola1Davydov/AnalyzeTool/issues/104)
и [#102](https://github.com/Nikola1Davydov/AnalyzeTool/issues/102): этот класс уже один
раз врал о занятости.

## Запутанный заместитель: почему `RunPipeline` не выставлен агенту

Из [`../sources/pipeline-design-doc.md`](../sources/pipeline-design-doc.md), и это лучший
разбор того, чего гейт на транспорте не умеет.

`SavePipeline` выставлен в MCP, а `RunPipeline` — **нет**, и асимметрия здесь и есть
дизайн: сохранение ничего не исполняет и оставляет файл, который человек может прочитать.
Агент вправе **предложить** конвейер, запускает его только человек — то же разделение, что
делает узел одобрения внутри прогона.

Причина конкретная, а не осторожность: **бридж решает по КОМАНДЕ**, что агенту можно
вызывать, а узлы диспатчатся под идентичностью самого `RunPipeline`. Значит агент,
способный позвать его со встроенным документом, дотянулся бы до команд, в которых ему
отказано напрямую. Выставить `RunPipeline` — значит пронести политику вызывающего в каждый
узел, и `CommandRequest.Gate` тут крючок. Это работа, а не переключение флага.

Классическая проблема запутанного заместителя, и она объясняет, почему проверка политики
уровня платформы должна жить в `ExecuteAsync`, а не в гейте транспорта.

## Отмена доходит не везде

Уточнение к разделу про конверт. `CancellationToken` действительно доходит до каждой
команды, но **`RevitTaskHub.EnqueueAsync` не принимает токен вообще**: работа, уже отданная
потоку Revit, доработает до конца. Отмена наблюдается только там, где команда сама её
наблюдает — например `PurgeFamilies` расширения Family Manager проверяет между чанками
по 40, — поэтому прогон
останавливается на границе следующего шага, а не мгновенно.

Ревью архитектуры 2026-09-23 уточнило картину и завело issue —
[#142](https://github.com/Nikola1Davydov/AnalyzeTool/issues/142): не дошедшей может оказаться и
работа, которая **ещё не начиналась**. Поставленная, пока Revit не простаивает (диалог, режим
редактирования), она выполнится позже — уже после того, как вызывающий получил «Cancelled», и
включая запись в модель. План — токен в `RunInRevitAsync` (аддитивно в Sdk) и пропуск отменённых
элементов в `Execute`. Разбор — [`../analyses/architecture-review-2026-09.md`](../analyses/architecture-review-2026-09.md).

## Чего здесь ещё нет

Всё это — работа, у которой уже есть правильное место, и ни одна не сделана:

- планирование и приоритеты (`Priority` зарезервирован комментарием);
- ограничение частоты ([#112](https://github.com/Nikola1Davydov/AnalyzeTool/issues/112)) —
  и `CommandPipeline.IsQuiet` уже показывает, как исключить `GetQueueStatus` из троттлинга;
- проверка лицензии ([#120](https://github.com/Nikola1Davydov/AnalyzeTool/issues/120)) —
  сознательно **не** в `Gate`, потому что гейт ставит транспорт;
- эксклюзивное исполнение `Destructive`-команд — reader/writer lock, чтобы запись не шла по данным,
  прочитанным до чужой записи ([#144](https://github.com/Nikola1Davydov/AnalyzeTool/issues/144));
- ранний ответ при `RevitAvailability.IsRevitBusy`, чтобы заблокированный Revit отвечал
  сразу, а не съедал таймаут клиента
  ([#88](https://github.com/Nikola1Davydov/AnalyzeTool/issues/88), остаток).
