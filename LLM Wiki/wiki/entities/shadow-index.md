# Теневой индекс

Лёгкий слепок модели вне Revit — id элемента → категория, тип, уровень, ключевые
параметры, — собираемый фоново и обновляемый инкрементально дельтами журнала
изменений. Запланирован, не построен.

Он всплывает в пяти разных планах как то, что делает их доступными по цене, и это
делает его самым нагруженным непостроенным компонентом бэклога.

## Решение по нему разворачивалось дважды

Важно при чтении: статус индекса менялся, и последнее слово — за августом.

**Июль 2026 — индекс отложен.** В комментарии к
[#80](https://github.com/Nikola1Davydov/AnalyzeTool/issues/80) обнаружен конфликт с
[#52](https://github.com/Nikola1Davydov/AnalyzeTool/issues/52) (Fingerprints), где слой
данных вне Revit уже детально спроектирован на **Parquet + DuckDB**: слепки по
требованию, diff версий, `QueryFingerprint(sql)`, freshness-гейт. Решили — Fingerprints
первичен как аналитический слой, фаза 4 с LiteDB **откладывается**, на первых фазах
агенту хватает журнала в памяти плюс свежего слепка. LiteDB возвращается только при
реальной потребности в живом мутируемом состоянии между слепками.

**Август 2026 — индекс возвращён и сдвинут вперёд.** Из ветки про модуль проверки он
стал основанием **двух пользовательских функций**, а не заделом для агента:

- инвентари данных — это буквально запросы к индексу; сканировать 8 410 элементов на
  каждое открытие вкладки нельзя. **Инвентарь оказывается первым UI индекса**, то есть
  индекс проверяется живым использованием, а не только агентом;
- проверка на каждой синхронизации и `RunCheck` / `GetDataInventory` по MCP отвечают из
  индекса, не трогая поток Revit.

Выбор LiteDB подтверждён с новой стороны: инвентарь дёргает индекс интерактивно из
WebView, и «чисто managed, точечные чтения» нужны именно там.

**Сентябрь 2026 — план постройки, SQLite вместо LiteDB.** 2026-09-04 владелец предложил
конкретную форму: выгрузка модели в SQLite (элементы, типы, параметры, уровни, помещения, bbox),
инкремент по `DocumentChanged`, SQL-запросы агента через MCP, живой API только для геометрии,
выделения и записи. План и сверка с вики —
[`../analyses/model-index-plan.md`](../analyses/model-index-plan.md). Главное расхождение с
таблицей хранилищ ниже: **LiteDB снимается в пользу SQLite** — агенту нужен SQL, файл должен
читаться worker'ом вне Revit, а риск нативной DLL закрывается системной `winsqlite3.dll` либо
загрузкой по полному пути из ALC лаунчера. Слепки для диффа — `VACUUM INTO`, Parquet
припаркован. Таблица ниже оставлена как история решения, не как действующее.

**У индекса два потребителя с разными требованиями.** Инвентарю нужно *широко и мелко*
(все отобранные параметры и их значения), своду правил — *узко и глубоко* (ровно те,
которые называют правила). Схема обязана обслуживать оба.

**Снапшоты получают продуктовое назначение**: строка «Parquet для диффа версий» — это
платные блоки динамики в отчёте
([#122](https://github.com/Nikola1Davydov/AnalyzeTool/issues/122)), «пустых полей за
6 недель: 120 → 44». Память — платная часть по границе
[#120](https://github.com/Nikola1Davydov/AnalyzeTool/issues/120), и физически она живёт
здесь.

> [!warning] не проверено
> Как уживаются LiteDB-индекс и Parquet-слепки из
> [#52](https://github.com/Nikola1Davydov/AnalyzeTool/issues/52) после разворота:
> июльское «снапшоты = fingerprints, отдельная реализация не нужна» не отменяли, но и не
> подтверждали заново.

## Зачем он

- **Чтения перестают трогать поток Revit.** «У каких из этих сорока дверей пустая
  классификация» становится запросом к индексу
  ([#118](https://github.com/Nikola1Davydov/AnalyzeTool/issues/118)).
- **Удаления становятся видимыми.** Удалённый элемент из модели прочитать нельзя — а в
  индексе он есть ([#80](https://github.com/Nikola1Davydov/AnalyzeTool/issues/80)).
- **Ответы при занятом Revit.** `GetDataInventory` и `RunCheck` читают индекс и
  отвечают во время долгой операции
  ([#123](https://github.com/Nikola1Davydov/AnalyzeTool/issues/123)) — то самое
  свойство, которое смягчает
  [`../concepts/long-running-calls.md`](../concepts/long-running-calls.md).
- **Проект отвечает вообще без Revit.** Снапшоты в папке проекта — это то, что
  позволяет сервису ответить на «какое состояние проекта?» из чата
  ([#125](https://github.com/Nikola1Davydov/AnalyzeTool/issues/125)).

## Уже обоснованные решения по хранению

Из [#80](https://github.com/Nikola1Davydov/AnalyzeTool/issues/80):

| Данные                            | Хранилище                                                       | Почему                                                                                                                                                           |
| --------------------------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| журнал изменений                  | память, кольцевой буфер                                         | жизнь — сессия, килобайты, не источник истины                                                                                                                    |
| теневой индекс                    | **LiteDB**, `%LOCALAPPDATA%\AnalyseTool\models\<guid>\index.db` | точечные обновления и чтения; **чисто managed**, значит нет конфликта нативных DLL в процессе Revit (риск SQLite / `e_sqlite3`)                                  |
| память агента, карточки           | JSON                                                            | килобайты, человекочитаемо, повторяет существующий паттерн `ai-providers.json` (`Ai/Infrastructure/AiProviderRegistry.cs:49` — файл в профиле, не в репозитории) |
| снапшоты для диффа версий, архивы | Parquet                                                         | write-once, колоночное сжатие, дифф — колоночный скан                                                                                                            |

Правило: **живое и мутируемое → LiteDB, неизменяемые слепки → Parquet.**

Два жёстких ограничения, оба сформулированы как абсолюты:

- **Индекс — восстановимый кэш, истина всегда модель.** Любая рассинхронизация — упал
  Revit, модель правили без плагина, сменился формат — помечает его устаревшим и
  запускает фоновую переиндексацию тем же кодом, что и первичную.
- **Никогда не хранить в RVT** через Extensible Storage: раздувает файл, уезжает к
  коллегам, требует транзакций.
  [#124](https://github.com/Nikola1Davydov/AnalyzeTool/issues/124) повторяет этот
  запрет для документов проекта.

## Идентичность

Ключ — модель, а не путь к файлу: `WorksharingCentralGUID` либо UniqueId
`ProjectInformation`. Та же задача идентичности — и то же решение — возникает для свода
правил ([#119](https://github.com/Nikola1Davydov/AnalyzeTool/issues/119)) и папки
проекта ([#124](https://github.com/Nikola1Davydov/AnalyzeTool/issues/124)).

[#85](https://github.com/Nikola1Davydov/AnalyzeTool/issues/85) предлагает
`Document.CreationGUID` для истории на стороне MCP и отмечает вопрос, который надо
закрыть первым: **регенерируется ли он при Save As?** Закрыто 2026-09-02 тестом в Revit
(`src/AnalyseTool.RevitTests/DocumentIdentityTests.cs`): **не регенерируется** — свежий документ, два
Save As под новыми именами, оба файла заново открыты, GUID один и тот же. Копия наследует
идентичность, значит ключ — `CreationGUID` плюс `PathName` с проверкой при открытии. Для
worksharing-моделей ключом должен быть GUID центральной модели, иначе у каждого члена
команды окажется изолированная история там, где она должна быть общей.

## Схему индекса определяет свод правил

Уточнение из комментария к [#119](https://github.com/Nikola1Davydov/AnalyzeTool/issues/119)
(28.08.2026). В [#80](https://github.com/Nikola1Davydov/AnalyzeTool/issues/80) индекс
описан обобщённо — «ключевые параметры». Со сводом правил **«ключевые» перестаёт быть
догадкой**: индексировать надо ровно те параметры, которые называют правила. Добавили
правило про новый параметр — индекс дозаписал колонку. Не гадаем заранее и не тащим всё
подряд.

Там же — граница объёма, совпадающая с границей дешевизны: проверки по **хранимым**
данным обслуживаются индексом и не трогают поток Revit вообще, поэтому их можно гонять на
каждой синхронизации. Всё **вычисляемое** (геометрия, коллизии) требует настоящей модели
и настоящего потока — и разваливает этот конвейер. См.
[`../analyses/checking-module.md`](../analyses/checking-module.md).

## Цена и единственный дорогой момент

В установившемся режиме дёшево. Дорогая часть — первичная сборка при открытии
документа: фоновая, чанками, и до готовности агент молчит. Открытие документа не
блокируется никогда ([#118](https://github.com/Nikola1Davydov/AnalyzeTool/issues/118)).

## Почему он в бесплатной части

[#120](https://github.com/Nikola1Davydov/AnalyzeTool/issues/120) кладёт индекс и
инвентари данных в бесплатный продукт сознательно: показать человеку беспорядок в его
собственной модели убедительнее любой презентации. Инфраструктура бесплатна; платно то,
что на ней построено.
