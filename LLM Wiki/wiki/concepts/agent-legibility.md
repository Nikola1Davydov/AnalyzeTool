# Как сделать модель понятной агенту, не тратя контекст

Сколько агент понимает — не функция того, сколько данных ему послали. Бэклог сходится
на более точном правиле: **ответы должны сцепляться по ключам, а статические
идентификаторы надо вкладывать в динамические ответы**, а не отгружать отдельно.

## Три яруса, три механизма

Из [#113](https://github.com/Nikola1Davydov/AnalyzeTool/issues/113) — там это сказано
яснее всего:

| Ярус | Пример | Механизм |
| --- | --- | --- |
| Универсальное / статическое | перечисление `BuiltInCategory`, объектная модель API | **никогда не отгружать контекстом** |
| На установку | локализованное имя ↔ `BuiltInCategory`, язык, версия Revit | кэшируемый ресурс |
| На документ | уровни, счётчики по категориям, активный вид | ответ (`GetModelOverview`) |

Мысль, которая делает задачу решаемой: **ярус 1 полезен только спроецированным через
ярус 3.** Полная таблица категорий бесполезна как контекст; те ~30 категорий, которые
есть *в этой модели*, снабжённые языконезависимыми идентификаторами, — ровно то, что
нужно, и стоит почти ничего.

## Повторяющийся дефект: ответ выбрасывает ключ, который держал в руках

- `categoryCounts` возвращает `{"Wände": 8}`. `BuiltInCategory` вычисляется строкой
  ниже, для `hasTopography`, и выбрасывается — так что агент обязан уже знать из
  обучения, что `Wände` это `OST_Walls`. На немецкой установке обычно угадает, на
  чешской или японской — нет.
- `ElementSummary.Level` — **строка**, тогда как `LevelInfo` несёт id, имя и отметку.
  То есть элемент связывается со своим уровнем только по отображаемому имени. Ровно
  этот дефект уже нашли и починили строкой выше, для `familyId`, и комментарий там
  гласит: *две команды описывали одни и те же семейства и не имели общего ключа*.
- Имена параметров тоже локализованы, `builtInParameter` рядом нет, а значения
  приходят как `"Höhe": "2400"` без единицы. Для чтения это неудобство; для
  `SetDataToParameters` — разница между стеной 2400 мм и 2400 футов.

Ничего из этого не ждёт новых глаголов протокола. Это поля в ответах, которые и так
отправляются.

## Плотность важнее полноты

[#123](https://github.com/Nikola1Davydov/AnalyzeTool/issues/123) даёт экономическую
версию аргумента одной строкой:

```
BRANDSCHUTZ: EI30 214 · EI60 38 · EI90 12 · пусто 44
```

~20 токенов, и о модели это говорит больше, чем триста строк `GetElements`. Плотный
инвентарь не только дешевле — он делает специализированный путь *выгодным*, а это и
есть ответ на проблему вытеснения из
[`../analyses/mcp-surface-state.md`](../analyses/mcp-surface-state.md).

Та же тема в [#83](https://github.com/Nikola1Davydov/AnalyzeTool/issues/83) P4:
`uniqueId` и `versionGuid` — примерно половина полезной нагрузки списочного ответа,
причём `versionGuid` был одинаков у всех 213 семейств, потому что описывает документ,
а не запись. [#85](https://github.com/Nikola1Davydov/AnalyzeTool/issues/85) это
поправляет: он не шум, он ключ инвалидации кэша, лежащий не там. Перенести в конверт.

## Выделение — третий канал, и он бесплатный

Из комментария к [#80](https://github.com/Nikola1Davydov/AnalyzeTool/issues/80)
(25.08.2026). Между «агент приходит сам» и «человек пишет в чат» есть третье: **человек
выделил элементы и спрашивает про них.** Восемь выделенных стен точнее любого описания,
стоят ноль токенов и ноль запросов к модели.

Обратное направление сильнее: **агент может отвечать выделением.** «В каких стенах нет
проёмов» — сейчас это список идентификаторов, который человек не читает. Подсветка в виде
понятна мгновенно, стоит ноль токенов, и человек сразу видит, правильно ли агент понял
вопрос — **обратная связь по пониманию, а не только по результату.**

Команды для обеих сторон уже есть: `SelectionInRevit` и `IsolationInRevit`.

## Локализация — вопрос переносимости, а не удобства

[#119](https://github.com/Nikola1Davydov/AnalyzeTool/issues/119) записывает это как
*блокирующую* зависимость всего модуля проверки: правило, написанное как «категория
Wände», ломается на любой другой языковой установке, поэтому свод бюро обязан
выражаться через `BuiltInCategory` и встроенные параметры.

Это поднимает [#113](https://github.com/Nikola1Davydov/AnalyzeTool/issues/113) из
удобства для агента в фундамент продукта. Два механизма идентичности, одна цель:
встроенное — через `BuiltInParameter`, общие параметры — через GUID
([#121](https://github.com/Nikola1Davydov/AnalyzeTool/issues/121)).

## Не гадать, сработало ли

[#113](https://github.com/Nikola1Davydov/AnalyzeTool/issues/113) заканчивается самой
важной дисциплиной: всё это — гипотеза о поведении агента, и проверяет её метрика
**вызовов на задачу**. Зафиксированная база: *8 вызовов, чтобы разместить 2 экземпляра
семейства; хватило бы 3* ([#84](https://github.com/Nikola1Davydov/AnalyzeTool/issues/84)).
Если число не сдвинулось — значит добавили полей и рассказали себе историю.
