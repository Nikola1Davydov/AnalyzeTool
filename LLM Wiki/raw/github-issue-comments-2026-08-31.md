Да, абсолютно. Более того, именно для Revit-плагина это выглядит как очень сильная фича.

Я бы даже не называл это "командной палетой", а скорее Radial Command Menu или Pie Menu. Такие меню давно используются в профессиональных программах (Blender, Maya, Houdini, ZBrush, SolidWorks и т.д.), потому что они быстрее обычных панелей.

В твоем случае архитектура может быть примерно такой:

C# хранит список всех доступных команд (их уже наверняка можно описать единым интерфейсом).
Vue только отображает круговое меню.
Пользователь открывает настройки и говорит:
сектор 1 → Analyse Parameters
сектор 2 → Export
сектор 3 → Select Elements
...
Конфигурация сохраняется.
При выборе сектора Vue отправляет только ID команды в C#, а тот уже выполняет нужный ICommand.
Это даже лучше, чем фиксированное меню

Если все команды описаны метаданными (Id, Name, Icon, Category), то пользователю вообще не нужно менять код.

Например:

○ Analyse Parameters
○ Export Excel
○ Purge
○ Show Warnings
○ Select by Category
○ Create Sheets
○ ...

Любую можно назначить на любой сектор.

Что можно сделать еще интереснее

Не ограничиваться 10 слотами.

Например:

Центральный круг — избранное.
Внешний круг — дополнительные команды.
Или несколько страниц:
General
Selection
AI
Views
Parameters
Есть еще одна идея

Я бы вообще сделал это не просто меню, а универсальный Launcher для AnalyseTool.

То есть одна и та же команда может запускаться:

из Ribbon;
из поиска (как Command Palette в VS Code);
из AI;
из радиального меню;
по горячей клавише;
через MCP.

Все эти способы вызывают один и тот же Command ID.

Тогда добавление новой команды происходит один раз в C#, а дальше она автоматически становится доступной везде. Это очень масштабируемая архитектура: со временем у тебя может появиться 100–200 команд, и пользователи смогут организовать доступ к ним так, как им удобно, не меняя код плагина.
Именно здесь есть нюанс. Если у тебя основа — WPF-окно с WebView2, то вариантов несколько.

Вариант 1. Отдельное маленькое WPF-окно (я бы выбрал его)

Когда пользователь нажимает, например, Space или Middle Mouse, ты:

Получаешь текущую позицию курсора.
Создаешь маленькое прозрачное WPF-окно без рамки.
Размещаешь его так, чтобы центр совпал с курсором.
Внутри этого окна находится WebView2 с Vue.
Пользователь выбирает команду.
Окно сразу закрывается.

Получается ощущение, что меню появилось прямо вокруг мыши.

Плюсы:

работает независимо от основного окна;
можно открыть в любом месте экрана;
легко сделать полупрозрачность и анимации;
Vue вообще не знает, что это отдельное окно.

Let users install extensions with one paste: a GitHub repo link (or zip/raw file) → AnalyseTool downloads, validates and unpacks it into the right extensions\<RevitYear>\ folder. Delivery only — no marketplace, no hosting, no billing.

Package convention (docs, not code)
An extension package is just a set of files; zip is only transport.
Multi-year layout: zip/repo root contains year folders (2025/, 2026/, 2027/), each with its own plugin.json + files. Single-year layout (plugin.json at root) is also accepted.
The installer picks the folder matching the running Revit year; clear error if missing ("not built for Revit 2026").
Accepted sources (one input field, auto-detected)
github.com/user/repo → latest release zip asset if releases exist, else branch zipball (api.github.com/repos/{o}/{r}/zipball) — author only has to push, no manual packaging. (Note: zipball wraps everything in a repo-sha/ root folder — descend into single root before validating.)
github.com/user/repo/releases/... → that specific release asset.
Direct https://…/*.zip URL.
Raw single .cs URL (gist / raw.githubusercontent.com) → installs as a script extension (one file, no build).
Local path: .zip file or a plain folder.
Install pipeline (backend)
Download to a temp folder (never touch extensions\ before validation).
Validate: plugin.json exists and parses, valid id, year folder present for the running Revit version, SDK major compatible (reuse the existing load-time check).
Two-phase for the confirm dialog: phase 1 = fetch + validate + return manifest info (id, name, version, author, source) + a token; phase 2 (after user confirms) = move files into extensions\<year>\<id>\, write install.json (source URL, installed version, date) next to them, trigger Reload.
IProgressAware on the download/extract so the UI shows progress.
Overwrite semantics: same id already installed → show "update X.Y → Z.W" in the confirm dialog, replace folder atomically (extract to temp sibling, swap).
Security (mandatory)
Confirm dialog before anything is written: "This will run code from <source> inside Revit. Only install from authors you trust." + manifest details.
Record provenance in install.json so it's always visible where an extension came from.
No sandbox (by design); signatures/hashes are a later option.
Frontend (Settings → Extensions)
"Install from URL / file" input + button (+ folder/file picker for local).
Confirm dialog (manifest + security warning + update-vs-fresh info).
Download progress; success toast → table refresh; remind that a brand-new ribbon button needs a Revit restart (existing behavior).
Docs
ONBOARDING.md + LLM.md: new "Sharing your extension" section — repo layout convention, GitHub release how-to, gist for script extensions.
v2 (design for it now, build later)

Browse catalog without a marketplace: a public JSON index (community "awesome-analysetool" repo: name, description, repo URL) rendered in Settings; Install reuses the same mechanism.

## #52 — AnalyseTool: Fingerprints — данные модели вне Revit

https://github.com/Nikola1Davydov/AnalyzeTool/issues/52

### Nikola1Davydov · 2026-07-03T17:54

Да, и тут даже не одно направление, а несколько — причём с разной степенью реалистичности. Разберу честно, от практичного к спекулятивному.

**1. Самое реальное и ближайшее: контекст для AI-агентов (не обучение, а RAG)**

У тебя уже есть MCP + ReAct-агент. Его главная слабость сейчас — каждый вопрос о модели требует живых вызовов Revit API, это медленно и жрёт контекст. Отпечатки это меняют радикально:

- Агент отвечает на «сколько дверей без FireRating на 3 этаже» **одним SQL-запросом к parquet** вместо серии MCP-вызовов в Revit. DuckDB-запрос — миллисекунды, Revit даже не нужен запущенным.
- Text-to-SQL — одна из самых сильных способностей LLM. Твоя схема (elements/params/relations) компактно описывается в системном промпте, и агент генерирует запросы по ней куда надёжнее, чем цепочки Revit API-вызовов.
- Relations-таблица даёт агенту то, чего LLM обычно не хватает — **фактическую структуру** конкретной модели: что от чего зависит, что где находится. Это готовый grounding против галлюцинаций.

По сути отпечаток = «векторная база знаний о модели», только лучше — структурированная и queryable. Это фича, которую можно делать уже в Фазе 2, и она прямо усиливает твой существующий MCP-стек.

**2. Реалистично на горизонте: ML на накопленной истории**

Когда общая папка поживёт год и в ней сотни отпечатков десятков проектов, появляется датасет, которого ни у кого нет:

- **Аномалии и QA/QC**: «в 95% ваших проектов у стен этого типа заполнен параметр X — в новом проекте он пуст» — статистика по истории, даже без нейросетей;
- **Предсказание параметров**: подсказки значений на основе паттернов компании (какой FireRating обычно у стен между такими помещениями);
- **Diff-паттерны**: какие изменения исторически предшествовали проблемам/переделкам — ранние предупреждения для координации.

Важно: это ML *для* компании *на её* данных — идеально ложится в твой платный тир и в BYO-key/GDPR-модель, которую вы уже проговаривали.

**3. Спекулятивно: обучение foundation-моделей на BIM**

Индустрия об этом говорит (Autodesk со своими AI-амбициями сидит ровно на таких данных), но тут честные оговорки: данные моделей принадлежат заказчикам, юридически использовать их для обучения без явного согласия нельзя — для Drees & Sommer это красная линия. Если когда-то — то только agregированно/анонимизированно и с opt-in.

**Что из этого следует для плана — почти ничего менять не надо**

Приятный вывод: твой формат уже AI-ready по построению. Колоночные таблицы + явные связи + версии — это ровно то, что нужно и для RAG, и для ML. Единственное, что я бы добавил в туду сейчас — маленький пункт в Фазу 2: **«MCP-tool `QueryFingerprint(sql)` — доступ агента к отпечаткам через DuckDB»**. Это дёшево (DuckDB есть .NET-клиент, схема уже есть) и превращает твой ReAct-агент из «управляет Revit» в «понимает модель». Остальное (аномалии, предсказания) — записать в «отложено осознанно» как направление платного тира.

## #53 — Parameter Requirements Table (Parameter Manager)

https://github.com/Nikola1Davydov/AnalyzeTool/issues/53

### Nikola1Davydov · 2026-07-06T12:39

Вот как я вижу интеграционную картину для Parameter Manager — от ближних к дальним:
1. IDS / buildingSMART (главный мост)
Экспорт и импорт .ids превращает твою таблицу из внутреннего формата в отраслевой стандарт. Одна и та же таблица требований работает тогда в Solibri, BIMcollab Zoom, usBIM — заказчик проверяет IFC своим чекером, координатор правит модель через твой tool. Ты становишься «авторской средой для IDS внутри Revit», а таких инструментов сейчас почти нет — ниша пустая.
2. IFC-пайплайн
Проверка не только живой Revit-модели, но и экспортированного IFC: та же таблица требований, но валидация по IfcPropertySet. Это закрывает классический разрыв «в Revit параметр есть, в IFC он не выехал из-за маппинга». Технически ложится на твой Fingerprint-пайплайн — IFC можно так же разобрать в Parquet и гонять проверки через DuckDB без Revit вообще.
3. CDE-платформы (BIM 360 / ACC)
Через APS API (OAuth у тебя уже реализован) — забирать модели из ACC и запускать проверку через Design Automation for Revit в облаке: BIM-менеджер получает compliance-отчёт без открытия Revit. Результаты проверки можно пушить как Issues в ACC — нарушение параметра становится задачей конкретному человеку. 
4. BCF для координации
Экспорт нарушений в BCF (BIM Collaboration Format): каждое нарушение — issue с viewpoint, element GUID и описанием правила. Открывается в любом BCF-клиенте (Revizto, BIMcollab, Solibri). Это дешёвая в реализации фича с большим wow-эффектом, потому что встраивает тебя в существующие координационные процессы, а не требует их менять.
5. Совместная работа (платный тир, Supabase)
Здесь самое интересное для монетизации. Таблица требований живёт не в локальном JSON, а в Postgres:

Версионирование требований: таблица v1.0 для LP3, v2.0 для LP5, история изменений «кто добавил параметр и когда» — это то, что в Excel теряется мгновенно.
Роли: BIM-менеджер редактирует требования в веб-интерфейсеб, координаторы в Revit видят read-only актуальную версию. Никаких «а у меня старый Excel».
Live compliance dashboard: каждый координатор гоняет проверку локально, результаты (агрегаты, не модель) уходят в Supabase — менеджер видит по всем моделям проекта «Архитектура 96%, ТГА 78%» в реальном времени. Realtime-подписки Supabase здесь из коробки.
Организационная библиотека: параметрические стандарты компании как переиспользуемые наборы — новый проект стартует с шаблона, а не с чистого листа.

6. MCP / AI-слой
Твоя MCP-интеграция даёт бесплатный бонус: «Claude, проверь модель по требованиям заказчика и исправь пустые Planname» — таблица требований становится контекстом для агента, а bulk-fix у тебя уже работает. Плюс агент может сам предлагать правила: «в 95% элементов этот параметр заполнен по паттерну E##, добавить как regex-правило?»
Стратегически я бы выстроил так: BCF-экспорт и IDS — фаза 2 (открытые форматы, укрепляют open-core репутацию), Supabase-коллаборация — фаза 3 и ядро платного тира, ACC/DA4R — фаза 4, когда появятся enterprise-клиенты. Хочешь, распишу какой-то из блоков детальнее — например, схему данных для совместных таблиц в Supabase или структуру BCF-экспорта?

## CommunityToolkit/AI — готовый слой хранения для Phase 3

https://github.com/CommunityToolkit/AI

Это не AI-фреймворк и не конкурент `Microsoft.Extensions.AI`. Это дом для коннекторов `Microsoft.Extensions.VectorData`: их вынесли из репозитория Semantic Kernel и передали .NET Foundation, чтобы у провайдеров векторных БД был вендор-нейтральный community-maintained дом. MIT, 10 пакетов (AzureAISearch, CosmosMongoDB, CosmosNoSql, InMemory, PgVector, Qdrant, Redis, SqlServer, SqliteVec, Weaviate).

Зрелость: `1.0.1-preview`, опубликован 22.07.2026, ~700 скачиваний всего — репозиторию недели. TFM у SqliteVec: net8.0 / net10.0 / netstandard2.0 / net462, то есть R25/R26 (net8) и R27 (net10) покрыты.

### Что это меняет в Phase 3

Два пункта попадают дословно:

- `Choose stores: sqlite-vec (local/free) + pgvector on Supabase (paid/collab)` → `CommunityToolkit.VectorData.SqliteVec` + `CommunityToolkit.VectorData.PgVector`.
- `VectorStore abstraction over both (upsert, query, filter by metadata)` → **отменяется**. Абстракция — это `Microsoft.Extensions.VectorData.Abstractions` от Microsoft; писать свою поверх двух стораджей не нужно.

`.InMemory` дополнительно закрывает прототип ingestion-пайплайна и тесты без всякой БД.

Риск preview-статуса умеренный именно потому, что контракт микрософтовский, а не тулкитовский: если конкретный коннектор разочарует — меняется коннектор, а не наш код. Версии пинить точные (то же правило, что и для Sdk в `docs/extension-platform-design.md`: плавающие диапазоны запрещены).

Phase 0 при этом уже наполовину сделан: `Microsoft.Extensions.AI` 10.5.2 в CPM, `IChatClient` работает в `AiClientFactory`. VectorData.Abstractions (10.7.0) — то же семейство, стыкуется естественно.

### Ограничение, которое надо зафиксировать до кода: SqliteVec не заходит в процесс Revit

# Дополнение: синергия с агентом (#80), таксономия AI-узлов, уроки ComfyUI

Этот план писался до #80 (встроенный AI-агент). Ниже — как обе фичи усиливают друг друга, плюс проработка AI-узлов как отдельного рода узлов.

## Синергия с #80 (агент) и #79 (коллизии)

- **Агент — для разового, пайплайн — для повторяемого.** Будить LLM-цикл на каждую синхронизацию расточительно; триггер из Change Journal (#80), запускающий детерминированный пайплайн (где AI — лишь один узел), — дёшев и предсказуем.
- **Агент как автор пайплайнов.** Сценарий «агент сделал за пять шагов в чате → кнопка "сохранить как pipeline"»: шаги замораживаются в `.atpipe`-рецепт, который дальше гоняется без LLM. Автоматизация, которую показываешь, а не программируешь.
- **Граф как объяснимость.** Многошаговый план агента рендерится тем же Vue Flow-редактором на одобрение — одна инфраструктура на две фичи (как уже сделано с палитрой #43).
- **Триггеры из Change Journal** — более ценный вид триггера, чем scheduled (сейчас в 2.5): «после синхронизации / после батча изменений» без затрат на LLM.
- **#79 — готовый флагманский пайплайн:** Detect → правила → AI-классификация остатка → propose → Approval → Apply. Конвейер коллизий не нужно проектировать отдельно — это первый серьёзный потребитель платформы.

## Таксономия узлов — пять родов

1. **Командные** — `[RevitCommand]` из Tools **и расширений** (см. «экосистема» ниже), через `CommandQueue` на Revit-поток.
2. **Оркестраторные** — без Revit, фоновый поток: Filter, группировка, ExportExcel/Pdf (уже в плане).
3. **AI-узлы** — три разных зверя с разной надёжностью и ценой:
   - **AI-трансформация**: prompt + items → выход по жёсткой JSON-схеме (схема задаётся в конфиге узла, она же — формат ответа модели + валидация с ретраем). Заметно: AI-узел *легче* типизировать, чем команду — его OutputSchema не требует рефакторинга, это просто настройка.
   - **AI-router**: ветвление потока по смыслу («какие warnings критичные?») — семантические условия вместо сравнения полей.
   - **AI-агент-узел**: ограниченный агентский цикл внутри узла — свой белый список инструментов, бюджет шагов, цель. Слияние #70 и #80: детерминированный скелет, интеллектуальные островки.
4. **Взаимодействие** — approval gate (карточка в inbox #80), запрос значения. Следствие для движка: **pause/resume состояния пайплайна** — заложить в схему `.atpipe` сразу, даже если V1 синхронный.
5. **Триггерные** — ручной, on-sync, on-change-batch (Change Journal), по расписанию.

## Принцип сборки и инвариант безопасности

LLM-узел надёжен только **зажатым между детерминированными**: вход готовит команда/фильтр, выход валидируется схемой. Отсюда машинно-проверяемое правило на этапе сборки графа: **ребро из AI-узла не может вести в Destructive-команду напрямую — между ними обязан стоять approval-узел** (редактор вставляет его автоматически). «AI никогда не пишет в модель без человека» — инвариант топологии графа, а не дисциплины пользователя.

## Практика AI-узлов

- **Модель на узел** — выбор из `AiProviderRegistry` в конфиге узла (классификация — дешёвой локальной, агент-узел — сильной).
- **Батчинг items** — узел сам чанкует (10–20 items на вызов) и склеивает; инфраструктура узла, не забота автора пайплайна.
- **Провенанс** — каждый item после AI-узла несёт «решил AI + уверенность + почему»; approval-узел показывает это человеку, и это же копится в память проекта (#80) как few-shot.

## Уроки ComfyUI (ближайший референс: граф над тяжёлым недетерминированным вычислителем)

- **Перезапуск только изменённых узлов**: кэш результата узла по хэшу (входы + параметры) — правка последнего узла не перезапускает `GetElements` и не жжёт токены заново. Инвалидация кэша — через Change Journal (#80): изменились элементы категории X → протух кэш узлов, читавших X.
- **Workflow зашит в результат**: каждый экспортированный отчёт/Excel несёт породивший его `.atpipe` + версии команд + модель. Аудит и воспроизводимость «из коробки».
- **Экосистема custom nodes** — уже есть по построению: расширения через SDK регистрируют команды → автоматически узлы палитры. Явный козырь платформы.
- **Спагетти-порог** (почему массовый пользователь остался на простых формах): (а) линейный V1 — правильно не только по трудозатратам; (б) готовые пайплайны доступны как обычные панели-формы («предзапечённые пайплайны» — кнопка сверху, граф под капотом для кастомизации).
- **Ключевое отличие от ComfyUI**: их узлы — чистые функции, наши Destructive-узлы мутируют живую модель. Поэтому кэш и авто-перезапуск — **только для ReadOnly-узлов** (флаг уже есть); мутирующие — идемпотентность через режимы (`OnlyIfEmpty`/`SkipIfEqual`) + approval-инвариант. Формула: «ComfyUI до последнего узла, транзакционная система — в конце».

# Plan checked against the code → design doc + phases split out

Full write-up: [`docs/pipeline-design.md`](https://github.com/Nikola1Davydov/AnalyzeTool/blob/claude/pipelines-plan-f8jrgf/docs/pipeline-design.md) (branch `claude/pipelines-plan-f8jrgf`). Step 1 is now #88 → #92; this issue stays the umbrella and keeps Step 2.

## What the sweep confirmed

The platform side of 1.2 is in better shape than the plan assumed. `CommandRequest` already carries `CancellationToken`, `IProgress<ProgressInfo>` and a `Gate`, so `LocalDispatcher` really is a thin wrapper — the busy bar, `GetQueueStatus` and the confirmation gate come along for free. Cancellation already reaches `IRevitTask.ExecuteAsync`, so the Stop button is nearly free. Input schemas are solved: **46 of 72** registered commands declare `InputType`, which is what generates the node parameter form.

Three things the plan did not have, that the code does:

1. **`RevitTaskHub.Execute` drains its whole queue** (`RevitTaskHub.cs:65`). There is no "this pipeline owns the Revit thread" — WebView2 and MCP work runs between nodes N and N+1.
2. **`IFailuresPreprocessor` exists only in the Families slice** (`SwallowWarningsPreprocessor`, 8 call sites). The write-safety blocker in the header is real and narrower than it looks.
3. **`AnalyseTool.Test` is one `UnitTest1.cs` and references `AnalyseTool.App`** → it drags in Revit. "Unit tests against a fake dispatcher (no Revit)" in 1.1 has nowhere to live today.

## Decisions taken

**A node IS a command.** No separate orchestrator node kind in the engine: Filter / ExportExcel / ExportPdf are ordinary `[RevitCommand]`s in Tools with `Headless = true`, and the dispatcher routes them off the Revit thread. One node type, one dispatch decision, features stay in Tools — and the custom-node ecosystem from the ComfyUI comment exists by construction, since any extension command is already a node.

**Outputs are the critical path, and they ship first and alone (#89).** Today **no command declares a result type** — `GetCommands` returns `new { commands }`, `SetDataToParameters` returns `null`, and the MCP bridge advertises `InputSchema` only. Typed edges therefore mean refactoring Tools commands slice by slice. That work pays for itself before any pipeline exists: an agent currently infers response shapes from prose. Related inversion worth noting — an **AI node is easier to type than a command**, since its output schema is node configuration, not a refactor.

**A run interleaves and is not atomic** (V1). Leasing the hub would freeze the UI for the length of a mutating pipeline and edit the most delicate piece of dispatch in the repo, before a single pipeline has ever run. Instead: mutating nodes re-check their own preconditions — the existing `Overwrite`/`OnlyIfEmpty`/`SkipIfEqual` modes are the mechanism — and `.atpipe` states the non-atomicity out loud. Revisit with measurements, not in advance.

**MAF is not in V1** (spike from the comment above stays open). It is an external dependency inside `AnalyseTool.Core`, which loads into an ALC in the Revit process and multi-targets net8/net10. Since `.atpipe` stays our contract either way, adopting MAF later costs nothing that adopting it now would save; the honest moment is #92, where checkpointing and human-in-the-loop stop being anticipated and become required.

Two things reserved in `.atpipe` v1 even though V1 is linear and synchronous, because retrofitting either is a migration: **per-node contract version** and a **resume `state`**. Result caching is limited to `ReadOnly` nodes — ComfyUI's nodes are pure functions, our destructive ones are not.

# Restructured: the contract shrank to one property, and the gate moved to the editor

Follow-up to the comment above, after checking every anticipated contract change against the
code rather than against the plan. Doc rewritten: [`docs/pipeline-design.md`](https://github.com/Nikola1Davydov/AnalyzeTool/blob/claude/pipelines-plan-f8jrgf/docs/pipeline-design.md).

## Two phases left this umbrella

#88 (write-safety) and #89 (declared outputs) are now standalone. Neither is a pipeline phase:
both are defects in what ships today, and both pay off with zero pipelines in existence.
Keeping them under a pipeline epic made the pipeline look like it cost more than it does, and
made two independently shippable fixes look blocked on a feature nobody has asked for yet.

## The SDK delta is one property

I brought a list of capability flags over from 1.2 of this plan. Checked one by one against
the code, all of them fell:

| Proposed | Why not |
| --- | --- |
| `Headless` | Routing is **already implicit**. `CommandDispatcher.DispatchAsync` awaits `ExecuteAsync` on the caller's thread and `RunInRevitAsync` is the only path to the Revit thread — a command that never calls it already runs entirely off it. The flag decides nothing. |
| `SupportsProgress` | `IProgressAware` is implemented or not, visible at registration. Duplicating an interface with a flag. |
| `[NodeParam]` | `InputType` + `[Description]` + generated schema already serves node forms, MCP tools and validation — for 46 of 72 commands. Defaults come from property initializers, choices from the enum. |
| Execution-mode signal | Added so a command could choose swallow-vs-collect. Collecting is better in both modes, so the mode has no consumer. |
| `RequiresUser` | Three interactive commands exist, all in App. A list in the palette builder, not public contract, until a third-party case appears. |

What survives is `OutputType` — which completes a pair `InputType` already half-declares, and
which MCP wants regardless. One additive property, one bump, 1.1.2 → 1.2.0.

Worth recording as a signal rather than an anecdote: a third client that were a crutch would
deform the contract under itself. This one didn't. The funnel absorbed it; the pressure landed
in Core, where it belongs.

## Failure handling has three outcomes, not one

`onFailure` per node in `.atpipe` (`continue` | `stopNode` | `stopPipeline`, defaulting to
`stopPipeline` for `Destructive`), decided by the **engine** from the node's outcome — the
command neither knows nor declares it. And `DeleteAllWarnings()` is right for a button, wrong
for a batch: the shared preprocessor collects and reports, warnings ride in the command's
declared result (#89). Author discipline can't cover third-party commands or Roslyn scripts,
so the guarantee is a host-level backstop during unattended runs (#88).

Approval nodes suspend the run rather than raise a modal. A modal blocks the Revit thread and
therefore the entire platform — the same failure #88 exists to remove, and it would be
self-inflicted this time.

## The gate moved

It was before Step 2 (cloud). That is too late: the node editor — the expensive part, and the
only piece adding a new consumer surface — would already be built.

**The gate is now before #91 (editor).** #88, #89, #90 stand on their own; #90 is a JSON format
plus a linear runner, and it gives MCP what it lacks — a way to freeze a working chain and
replay it without an LLM.

And the editor may never be needed. By this issue's own comment, authoring goes to the agent
("five steps in chat → save as pipeline") and consumption is a button ("pre-baked pipelines as
ordinary panels; button on top, graph underneath"). If both hold, neither side needs a canvas:
a pipeline is a format plus a runner. Build #91 only when agent-authored `.atpipe` files
circulate AND someone asks to edit one by hand.

# Технологическое решение: Microsoft Agent Framework (MAF) для фазы 1

MAF дошёл до GA 03.04.2026 (RC — февраль 2026), риск превью-API снят. Он закрывает значительную часть «построить самим» из этого плана.

## Что берём из MAF

- **Агентский цикл**: `ChatClientAgent` вместо рукописного цикла «LLM → tool calls → результаты → LLM». Построен на `Microsoft.Extensions.AI` / `IChatClient` — мы уже ссылаемся на этот пакет (генерация схем в `CommandDispatcher`), а миграция на `IChatClient` и так запланирована (= #56 Phase 0, см. комментарий о консолидации выше). MAF ложится на существующий путь.
- **Инструменты**: `AIFunctionFactory` + тонкий адаптер — по каждой `CommandRegistration` создаётся `AIFunction` (имя, описание, JSON-схема уже есть), делегат кладёт `CommandRequest` в `CommandQueue`.
- **Human-in-the-loop + checkpointing**: workflows MAF умеют останавливаться на человеческом решении и чекпойнтить состояние — ровно требование inbox/pause-resume из этого плана.
- **Бонусы**: встроенная поддержка MCP (потребление инструментов и экспонирование агента), OpenTelemetry из коробки.

## Границы (обязательные)

- **Точка принуждения остаётся в `CommandQueue`**: Gate, белый список инструментов агента, исключение `ExecuteRevitCode` — на уровне очереди, НЕ в middleware фреймворка. MAF не должен иметь пути к Revit в обход очереди.
- **Чекпойнтинг MAF — сохранение состояния, не durable execution** (уровня Temporal): упавший процесс сам не возобновится. Для локального агента внутри Revit достаточно («переоткрыл модель → продолжил с чекпойнта»), но границу знать.
- **Слабые локальные модели MAF не чинит** — проверка «модель пригодна для агентского режима» из плана остаётся.
- **Спайк загрузки в изолированный ALC** — рано, до основной работы (TFM подходит: net8 для R25/26, net10 для R27; риск — транзитивные зависимости).

## Обновление фазы 1

Было: «Tool calling в чат-клиенте + агентский цикл с ручным триггером».
Стало: **«Спайк MAF: `ChatClientAgent` + адаптер `CommandRegistration` → `AIFunction` → `CommandQueue`, ручной триггер, только ReadOnly»**. Оценка сокращается с недель до дней; заодно исполняется #56 Phase 0.

Оговорка: workflows MAF определяются кодом, `.atpipe` — пользовательские данные → нужен интерпретатор «`.atpipe` JSON → граф MAF». Решение: **`.atpipe` остаётся контрактом, MAF — заменяемая деталь исполнения**; формат файла к фреймворку не привязывать. ## 1. Выделение — канал, которого в плане нет, и он бесплатный

План хорошо покрывает «агент приходит сам» (триггеры) и «человек пишет в чат». Между ними есть
третье: **человек выделил элементы и спрашивает про них**. Восемь выделенных стен точнее любого
описания, стоят ноль токенов и ноль запросов к модели.

Обратное направление сильнее: **агент может отвечать выделением**. «В каких стенах нет проёмов» —
сейчас это список идентификаторов, который человек не читает. Подсветка в виде понятна мгновенно,
стоит ноль токенов, и человек сразу видит, правильно ли агент понял вопрос — обратная связь по
пониманию, а не только по результату.

Для интерактивного разбора карточек из раздела «code review для BIM» это прямо просится: изоляция
элемента во вьюпорте там уже описана, выделение — её дешёвый вариант.

## 2. Зрение

В проекте нигде нет `ExportImage`. Агент работает по JSON в геометрическом домене — план этажа,
отданный зрячей модели, содержит больше пригодного к действию, чем два десятка вызовов
`GetElements`. Для «ревью вида» и для размещения это меняет класс решаемых задач.

агент получает килобайты base64 как текст и не может их увидеть.

Карточки в inbox — правильно для того, что требует решения. Но часть находок должна уезжать в
инструменты, которыми команда уже пользуется:

- **BCF** — стандарт замечаний в BIM; находки агента сразу совместимы с Solibri, BIMcollab,

- Ревизионные облака и примечания в модели — замечание там, где на него посмотрят.
- Спецификация как отчёт (#57).

Заведено отдельно: варианты A и C трактуют MCP как то, чем мы являемся или что нас ведёт. Цикл из

## ⚠️ Предупреждение к фазе 5

> Принятые/отклонённые решения копятся как few-shot примеры — агент выучивает конвенции без
> дообучения

удалить накопленное, и осторожность с тем, чтобы **отклонения** весили столько же, сколько
одобрения (отклонённое решение — более чистый сигнал, чем одобренное: одобряют в том числе не
глядя).

There is a cheaper fix for this than the one this issue implies, and it arrived with `2026-07-28`.

The obvious reading of "the saved command never reaches `tools/list`" is that we need
`notifications/tools/list_changed`, and therefore that the bridge must learn to write to the socket

share across users, **without needing a long-lived SSE stream to learn about changes**."

A short `ttlMs` on our tool listing would mean a client re-lists on its own within the window, and a
command saved mid-session shows up without anything being pushed at it. That is a field on a
response we already send, versus a new channel.

Two things to check before believing it:

- [ ] Whether `ttlMs` applies to **stdio** results or only to Streamable HTTP — the spec text

- [ ] Whether the client honours it (an ignored `ttlMs` leaves us exactly where we are)
- [ ] Whether `ModelContextProtocol` 1.3.0 exposes it at all — the gate in #107

⚠️ Unverified against the final spec; see the caveat in #107.

Worth recording either way: this issue was on its way to justifying a push channel, and it turns out
not to need one. The same goes for the rest of the roadmap — progress, cancellation, long

## #106 — Dry-run + confirmToken for destructive commands: show what will change before it changes

https://github.com/Nikola1Davydov/AnalyzeTool/issues/106

### Nikola1Davydov · 2026-08-14T07:59

`2026-07-28` gives this an official protocol mechanism, and it fits the design here closely enough
to be worth adopting rather than inventing a parallel one.

Elicitation was restructured (SEP-2322, "Multi Round-Trip Requests"). Instead of the server holding
a stream open while it waits for an answer, it returns an `InputRequiredResult`:

```json
{
  "resultType": "inputRequired",
  "inputRequests": {
    "confirm": {
      "type": "elicitation",
      "message": "Delete 3 files?",
      "schema": { "type": "boolean" }
    }
  },
  "requestState": "eyJzdGVwIjoxLCJmaWxlcyI6WyJhIiwiYiIsImMiXX0="
}
```

The client collects the answer and **re-issues the original call** with `inputResponses` plus the
echoed `requestState`.

Mapped onto this issue: `requestState` is the `confirmToken`, and the dry-run result is the
`message`. The difference from what is sketched here is that it is one logical call the client
completes, rather than two calls we have to correlate and expire ourselves — which removes the part
of this design that would have needed the most care (what a token means, how long it lives, what
stops it being replayed against a model that changed underneath it).

Two constraints that come with it, both of which happen to suit us:

## Ограничение объёма: первая версия — только хранимые данные

Решение принято: **геометрию не берём.** Коллизии и всё вычисляемое пространственное остаются в
#79. Это уточняет фазу 1 выше.

Три причины, и третья — главная:

1. **Геометрия — другой движок.** Пространственный индекс, солиды, допуски, другой профиль
   производительности. В первой версии это удвоение проекта.
2. **Коллизии — занятая часть рынка** (Solibri, Navisworks, Revizto). Там соревнуются в полноте, и
   это соревнование не выиграть. Качество данных обслужено хуже, и именно оно блокирует сдачу.
3. **Данные обслуживаются теневым индексом, геометрия — нет.** Проверка по хранимым данным не
   трогает поток Revit вообще: индекс, память, миллисекунды. Значит её можно гонять на **каждой**
   синхронизации, и никто не заметит. Геометрия требует настоящей модели и настоящего потока — и
   тогда весь дешёвый конвейер из #118 разваливается.

То есть ограничение не просто «поменьше объём» — оно **совпадает с границей, за которой архитектура
остаётся дешёвой**.

## Граница проходит по «хранится / вычисляется», а не по «параметры / геометрия»

Важное уточнение, потому что «только параметры» — это у́же, чем можно взять бесплатно.

**В объёме первой версии** (Revit это хранит, вычислять нечего):

- параметры — значения и наличие
- имена всего: элемента, типа, семейства, вида, листа, уровня, ворксета
- категория и `BuiltInCategory`
- связь тип ↔ экземпляр
- назначенный уровень, назначенный ворксет
- внутреннее семейство или загружаемое, системное или нет
- используется ли тип вообще (непрочищенное)
- метаданные видов и листов
- **связи, которые Revit хранит**: хост двери (`FamilyInstance.Host`), привязка стены к уровню,
  замкнутость помещения

Последний пункт — поправка к классификации, обсуждавшейся раньше: отношения и топология **не все**
дорогие. «Двери должны размещаться в стенах» — правило про данные, а не про геометрию, и оно
попадает в первую версию даром.

**Вне объёма** (надо вычислять — в #79): пересечение, расстояние, зазор, вложенность по геометрии,
положение в пространстве.

И отдельно: не потерять **класс гигиены модели** — нет внутренних семейств, нет импортированного
CAD, ничего на «Рабочий набор1», нет непрочищенных типов. Всё хранимое, всё дешёвое, и в реальных
BIM-руководствах это часто самый большой раздел.

## Следствие для теневого индекса (#80)

В #80 индекс описан обобщённо — «ключевые параметры». Со сводом правил **«ключевые» перестаёт быть
догадкой**: индексировать надо ровно те параметры, которые называют правила.

**Свод определяет схему индекса.** Добавили правило про новый параметр — индекс дозаписал колонку.
Не гадаем заранее и не тащим всё подряд.

## Ловушки, которые съедят больше времени, чем движок

Параметры в Revit нерегулярны:

- **тип против экземпляра** — одно имя, разный владелец; правило обязано указывать, о каком речь
- **встроенный / общий / проектный** — разная идентичность, и **только встроенный не зависит от
  языка** (это #113 с другой стороны: без него свод бюро непереносим между установками)
- **тип хранения** — значение бывает строкой, double, int, ElementId; «равно» для каждого своё
- **единицы** — double лежит во внутренних футах, пока не преобразован
- **формульные и только для чтения** — проверить можно, исправить нельзя, и находка обязана это
  говорить, иначе предложенное исправление не сработает
- **«параметра нет» ≠ «параметр пуст»** — разные находки с разными способами починки (добавить
  параметр в проект против заполнить значение). Чекер, который их смешивает, выдаёт нечинимые
  замечания.

## Авторство перевёрнуто: от данных, а не от правила — и это меняет фазу 1

Итог серии макетов (кликабельный, все вкладки живые):
https://claude.ai/code/artifact/02606410-fcf3-4c25-a8e9-388b924fe5e1

Первый заход строил экран «напишите правило» — чистый лист, который надо заполнять из головы, и
вокруг него росли подсказки. Рабочая версия начинается с другого конца: **распределение значений —
это уже почти готовое правило.**

```
BRANDSCHUTZ   EI30 · 214   EI60 · 38   EI90 · 12   [EI 30 · 3]   [ei30 · 1]   пусто · 44
```

Правило читается со строки до его создания: видно три законных значения, две опечатки и 44
пустых. Клик — галочки допустимых, «не пусто», эффект «пометит 48 из 312». Побочно исчезла
нужда в пробном прогоне: правило, собранное из наблюдённых значений, не бывает мёртвым и не
срабатывает на всём — распределение было перед глазами.

Что закрепилось в конструкции:

- **Один экран инвентарей с переключателем** (Parameters / Types / Families / Worksets), а не
  вкладка на каждый вид данных. Шаблон один: сущность → распределение → состояние. Гигиена
  модели перестала быть исключением «за кнопкой прозы» — непрочищенный тип, in-place семейство
  и занятый Arbeitssatz1 это обычные строки своих инвентарей.
- **Правило — отдельная сущность.** Рождается в контексте строки, живёт отдельно: карточка с
  областью, автором, историей срабатываний. Расширение области — операция с предпросмотром
  («включение Fenster добавит 41 находку — у них своя схема FE-xx»); расширить область на глаз —
  самый быстрый способ залить отчёт мусором.
- **Опечатки значений** («EI 30», «ei30») — находка до всяких правил, возможно самая быстрая
  польза продукта; предложение объединить прямо в конструкторе.
- **Уровень удобства взят у Solibri** (сгруппированный список, знакомая модель), **трудоёмкость
  авторства — нет**: структуру собирает система из данных и LLM из текста, человек утверждает.
