## #45 — Auto AI name suggestion (ghost text) in the rename dialog

state: open | labels: enhancement | created: 2026-07-01 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/45

Goal: when the rename dialog or another ai dialog opens, an AI-suggested name appears on its own as
"ghost" text below the input. Accept with Tab, dismiss with Esc. Copilot-style,
but lightweight because Ollama is local/slow.

### Core behavior
- [ ] On dialog open, auto-fire `OllamaSuggestName` with the current name + context
      (category / type) — no button click required.
- [ ] Show a small inline spinner next to the field while the request is in flight.
- [ ] Render the result as ghost text below the input:
      `Suggested: <name>   ⏎ Tab to accept · Esc to dismiss`
- [ ] Tab = insert the suggestion into the input. Esc / any edit = hide the ghost.
- [ ] Add a "Suggest another" button to request one more variant on demand.

### Robustness (the part that makes it not feel laggy)
- [ ] Debounce any re-trigger by ~400–600 ms (VueUse `useDebounceFn`).
- [ ] Cancel the previous request when a new one starts
      (AbortController, or a request-id "last one wins" guard) so a stale
      answer never overwrites a newer one.
- [ ] Cache suggestions by key `currentName + context` — don't hit Ollama twice
      for the same input.
- [ ] If Ollama is not running (`OllamaGetModels.running === false`), skip the
      auto-request silently — no error toast, just no ghost.

### Scope decision
- [ ] Do NOT make it fully reactive per keystroke (feels laggy with local Ollama).
      One auto-suggestion on open + manual "suggest another" is enough.

### Reuse
- [ ] Reuse the existing `OllamaSuggestName` command and `AiModelIndicator`
      (shared global model) — do not add new backend commands.

## #47 — AI Reviewer for Revit

state: closed | labels: - | created: 2026-07-02 | comments: 1
https://github.com/Nikola1Davydov/AnalyzeTool/issues/47

AI Reviewer is a Revit plugin that continuously monitors BIM models and detects inconsistencies, missing data, and design anomalies in real time. It combines deterministic rule-based analysis with a local or cloud LLM (e.g. Ollama) to provide human-readable explanations and actionable recommendations.
The system does not directly analyze raw BIM geometry with AI. Instead, it uses a structured analysis engine in C# to extract relevant findings, which are then interpreted by an AI layer.
Architecture
Revit Document
      ↓
Change Detection (DocumentChanged / Idling events)
      ↓
C# Analysis Engine (AnalyseTool Core)
      ↓
Rule System + Context Builder
      ↓
Structured Findings (JSON)
      ↓
LLM Layer (Ollama / Local Model / Cloud AI)
      ↓
Explanation + Recommendations
      ↓
UI (WPF / WebView Panel)
Core Principles
1. Deterministic First
All validation logic is executed in C#:
parameter validation
schema compliance
value ranges
duplication checks
category-based rules
AI is never responsible for deciding whether something is valid or invalid.
2. Context-Based Analysis
Each element is enriched with contextual data before being sent to the AI layer:
host elements (walls, floors, systems)
connected elements
surrounding spaces (rooms, zones)
project-level statistics
historical modifications
Example:
{
  "element": "Door 1245",
  "issues": [
    {
      "type": "MissingParameter",
      "name": "FireRating",
      "severity": "High"
    }
  ],
  "context": {
    "hostWall": {
      "fireRating": "EI60"
    },
    "adjacentRooms": ["Office", "Corridor"]
  }
}
3. Continuous Monitoring
The plugin operates in near real-time using Revit events:
DocumentChanged triggers incremental analysis
Idling executes background validation
only modified elements are re-evaluated
This avoids full model scans and ensures responsiveness.
AI Layer (Ollama Integration)
The AI model is used exclusively for interpretation, not validation.
Responsibilities:
explain detected issues in natural language
correlate multiple findings
suggest probable root causes
provide BIM-aware recommendations
Example Prompt Input:
Analyze the following BIM issue:

Element: Door 1245  
Issue: Missing FireRating  
Host Wall Fire Rating: EI60  
Adjacent Rooms: Office / Corridor  

Project rule: Doors in rated walls must match wall fire rating.
Example Output:
The door is located in an EI60-rated wall but has no FireRating defined.
According to project standards, the door should inherit or explicitly define EI60 rating.
This may indicate an incomplete family setup or an oversight during duplication.
Advanced Features
1. Anomaly Detection
The system identifies statistical outliers:
inconsistent parameter usage
rare missing values
naming deviations
unexpected type variations
2. Project Memory
The AI can learn from project history:
recurring issues
user behavior patterns
common modeling mistakes
3. Context Correlation
Finds relationships between:
elements of the same type
elements on the same level
system-connected components
Key Value Proposition
real-time BIM quality monitoring
reduction of manual QA effort
early detection of modeling inconsistencies
AI-assisted interpretation of technical issues
fully local deployment option via Ollama for enterprise privacy
Positioning
AI Reviewer is not a replacement for BIM standards or rule checking systems.
It is an augmentation layer that transforms technical validation output into actionable engineering insight.

## #48 — Third-party extension distribution (clean, no-marketplace model)

state: open | labels: - | created: 2026-07-02 | comments: 1
https://github.com/Nikola1Davydov/AnalyzeTool/issues/48

Principle: AnalyseTool is runtime + delivery mechanics ONLY. Vendors sell, license,
host and support their tools themselves. No money, no code review, no binary hosting
on our side — minimal legal surface.

### Manifest capabilities (useful for our own tools too)
- [ ] Multiple buttons per extension: `ui.buttons: []` (name/tooltip/icon/command/dockable per button)
- [ ] Button kinds: push / pulldown / stacked; `order` within panel; separators
- [ ] Locked/disabled button state hook (driven by the VENDOR's own license check)
- [ ] Vendor metadata: `publisher`, `website`, `supportUrl` — shown in Settings

### Packaging & install
- [ ] Package = zip containing the extension folder (plugin.json inside)
- [ ] Settings: "Install extension from file…" → unzip into extensions\<year>\ + Reload
- [ ] Install-time disclaimer: third-party code, full Revit permissions, publisher is
      responsible, we don't review it — user must confirm (log the consent)

### Updates (vendor-hosted, we are just the courier)
- [ ] Optional `updateFeed` URL in manifest (vendor's server, returns {version, downloadUrl})
- [ ] "Update available" badge in Settings; download comes from the vendor's URL
- [ ] Never host third-party binaries ourselves

### Legal minimum
- [ ] EULA section "Third-party extensions": run at user's own risk, publisher liable,
      no endorsement / no review by AnalyseTool
- [ ] Crash/error attribution: ExtensionDiagnostics tags errors with extension id;
      error dialogs say "error in extension X by Y — contact supportUrl"
- [ ] Optional vendor-provided signature/hash: display "signed by publisher" / "unsigned",
      no PKI of our own, no guarantees implied

### Explicitly OUT of scope (keeps us clean)
- No payment processing, no revenue share, no entitlement API for vendors
- No package review/approval process
- No central catalog with hosted packages (at most: a JSON list of LINKS marked
  "third-party, not endorsed")

## #52 — AnalyseTool: Fingerprints — данные модели вне Revit

state: open | labels: - | created: 2026-07-03 | comments: 1
https://github.com/Nikola1Davydov/AnalyzeTool/issues/52

## AnalyseTool: Fingerprints — данные модели вне Revit

### Фаза 1: Экспорт (Command Core)

1. **Task `CreateFingerprint`** — экспорт по требованию (кнопка, не фоновый стриминг): выбор категорий → полное извлечение.
2. **Выбор категорий из документа** — `doc.Settings.Categories` + фильтр по наличию элементов, не хардкод (решает вопрос немецких имён). Мультивыбор категорий в один отпечаток (Türen + Türbeschriftungen).
3. **Экстрактор параметров** — сырые значения (`AsDouble`/`AsInteger`/`AsString`, internal units, без `AsValueString`), сбор в колоночные массивы, порциями через `Idling` + `ProgressBarWindow`. Категорийно-агностичный: модельные элементы, аннотации, типы — одна схема.
4. **Схема данных (гибрид):**
   - `elements.parquet` — UniqueId, ElementId, Category, Family, Type, Level, ContentHash, IfcGuid, LocX/LocY/LocZ, BBoxMin/Max 🔗 *(UniqueId — ключ связи с будущей геометрией; BBox уже даёт zoom-to-element)*
   - `params.parquet` — long-формат: UniqueId, Name, StorageType, ValueStr/ValueNum/ValueElementId
   - `types.parquet` — type-параметры отдельно

5. **`relations.parquet`** — рёбра `from_id | to_id | relation_type | source`: Level, Room (`GetRoomAtPoint`, `FromRoom/ToRoom`), Host, DependentElements, Type, Group, Workset, OwnedByView (аннотации), Tags (`IndependentTag.GetTaggedLocalElementIds`), MEP-системы.
6. **Архитектура `IRelationExtractor`** — компонуемые извлекатели по 20–40 строк, каждый сам проверяет применимость (без switch по категориям). Открыто для SDK-extensions — паттерн `IRevitTask`.
7. **Bundled-контекст** — Rooms + Levels всегда; Views + Sheets в отпечатки аннотационных категорий. Висячие ссылки — норма, отпечатки обогащают друг друга при join.
8. **ContentHash** — детерминированная сериализация (сортировка по имени, invariant culture) → SHA-256.
9. **Запись Parquet.Net** (.NET 8) — temp-файл + `File.Move` (атомарность на шаре).
   - 9.5. *(второй очереди)* Локальный кэш хешей — только оптимизация с fallback, не источник истины.
10. **Структура папки:** `fingerprints\{timestamp}_{user}_{categories}\` + `fingerprint.json` (модель, категории, юзер, дата, количество, комментарий, время синхронизации с central через `WorksharingUtils`, поле `hasGeometry`). Без центрального манифеста — список версий = перечисление папок.

### Фаза 2: Просмотр в AnalyseTool (WebView2) + AI-слой

11. **Вкладка «Fingerprints»** — таблица отпечатков: кто, когда, категории, комментарий, свежесть относительно central.
12. **Интерфейс `FingerprintSource` (TS)** — абстракция источника: `BridgeSource` (JSON-RPC) сейчас, `FsaSource`/HTTP позже.
13. **DuckDB-WASM** — SQL по parquet во фронте; WASM-бандл локально (CDN-блокинг), раздача через `SetVirtualHostNameToFolderMapping`.
14. **Просмотр отпечатка** — таблица, фильтры, группировки (PIVOT), запросы по relations («двери без марок», «элементы по помещениям»). `WITH RECURSIVE` — всегда с cycle-guard (depth-лимит / `UNION` вместо `UNION ALL`): граф зависимостей может содержать циклы.
15. **2D-план** — SVG/scatter по Location-колонкам по уровням. 🔗 *(компонент против интерфейса «UniqueId + раскраска» — позже дополнится 3D-панелью)*
    - 15.5. **`geometry_lite.parquet`** — kind: outline/curve/box + flat float array; дешёвое извлечение (LocationCurve, footprint, BBox), схематичный Three.js-рендер. Lite-геометрия живёт в отпечатке (лёгкая, версионируется с данными).
16. **Diff двух отпечатков** — join по UniqueId, сравнение хешей → added/modified/deleted + причинность через relations («стена изменилась → зависимые двери»).
17. **Revit-интеграция** — подсветка/выбор элементов из таблицы (только WebView2-режим).
18. **MCP-tools:** `ListFingerprints()`, `QueryFingerprint(sql)` (DuckDB .NET, работает без запущенного Revit), `CreateFingerprint(categories[])`.
19. **Паттерн read/write:** анализ — SQL по отпечаткам, действия — живые Revit-инструменты по UniqueId. Не делать «аналитических» живых инструментов. После bulk-write агент обновляет затронутые отпечатки.
20. **Freshness-гейт server-side** — `QueryFingerprint` отказывает при устаревших данных без явного `acceptStaleData=true`, инструктируя агента спросить юзера. Порог — настройка плагина. Поверх — UI-плашка «Данные от {date} — [Обновить] [Использовать как есть]», кнопка дёргает `CreateFingerprint` мимо LLM. Возраст данных — в каждом ответе инструмента.

### Фаза 3: Standalone-вьювер (Free-тир, без Revit)

21. **Desktop-вьювер = WPF-окно + WebView2** с тем же Vue-фронтом (не Electron, не MAUI).
22. **Один билд, режимы в рантайме** — по `window.chrome.webview` / `viewer.config.json`.
23. **File System Access API** — `showDirectoryPicker()` на шару, persist handle в IndexedDB.
24. **Лайт-вьювер** — single-file HTML (`vite-plugin-singlefile` + hyparquet, без workers), открывается по `file://`. Дефолтный относительный путь к `..\fingerprints\`.
25. **Self-provisioning** — плагин кладёт `_viewer\` на шару, `version.txt` (semver-сравнение, обновляет только более новый плагин), swap через temp-папку.

### Фаза 4: Хостинг и монетизация

**Free:** экспорт, просмотр в плагине, desktop-вьювер, лайт-вьювер.

**Paid (team-слой):**
26. **Hosted-версия** — браузер + мобильный доступ (адаптивная вёрстка).
27. **Комментарии, назначения, статусы, realtime-коллаборация** — здесь появляется Supabase/Postgres (mutable-данные, права; честные server costs = честная цена).

**Self-hosted (enterprise-лицензия):**
28. Docker-образ (nginx + статика); вариант с примонтированной шарой, если FSA запрещён политикой.
29. «Deploy to Azure» кнопка (Bicep) — позже.
30. Кнопка «Deploy viewer to network folder» из плагина — позже, по запросам.

### Фаза 5: Геометрия (по триггеру, база уже есть — `FamilyMeshService`)

**Готово** ✅ — тесселяция (solid → face → `Triangulate()`), материалы (цвет + прозрачность), композиция трансформов вложенных инстансов через `GetSymbolGeometry()`, per-element guards.

31. **Рефакторинг `FamilyMeshService` → `ElementMeshService`:**
    - Symbol-кэш: `Collect` один раз на FamilySymbol, инстансы — только `fi.GetTransform()` + UniqueId (500 дверей = 1 меш + 500 матриц);
    - Системные семейства: тот же `Collect` через `element.get_Geometry()`, мировые координаты, без инстансинга;
    - `Fine` → `Coarse` для модельного экспорта (галерея семейств остаётся на Fine);
    - Base point offset против float32-jitter на shared coordinates далеко от origin.
32. **Бинарный формат вместо JSON** — float32 positions/indices (убрать `Math.Round`), transforms как 4×4 матрицы. Кандидат — геометрия-как-parquet по образцу bim-open-geometry (единый стек, компактнее GLB, BOS-совместимость); GLB (SharpGLTF) — запасной вариант для универсальной открываемости.
33. **Отдельный слой** — `geometry\` рядом с `fingerprints\`; кнопка «Update geometry» (модель или категория через фильтр 3D-вида), связь по UniqueId, бейдж свежести, `hasGeometry` в fingerprint.json.
34. **Three.js-панель** — `InstancedMesh` из symbol-кэша + матриц, тот же интерфейс, что 2D-план (п.15); lite-контуры становятся LOD/fallback.

**Оценка:** дни, не недели. **Триггер:** демка платного тира / standalone-пользователи / MEP-аналитика.

### Отложено осознанно

## #70 — Plan: Pipeline Feature

state: open | labels: - | created: 2026-07-21 | comments: 4
https://github.com/Nikola1Davydov/AnalyzeTool/issues/70

## Prerequisites (blocker — before any mutating pipeline runs)

- Write-safety hardening: re-entrancy guard, `IFailuresPreprocessor`, MCP timeouts/logging.
  A pipeline chains mutating commands in batch with no human between the nodes — this debt
  becomes a hard blocker here, not just for Family Control actions.

## Step 1 — Local Pipeline Engine

### 1.1 Foundation (no UI, no Revit dependency in the core)
- Design the pipeline JSON schema: nodes, edges, parameters, command contract version
  (`CheckNaming@2`), pipeline metadata (name, author, file schema version)
- Define the `NodeOutput` data envelope with partitioning `Dictionary<MachineId, MachineResult>`
  — locally always a single `MachineId.Local` entry
- Engine interfaces: `IPipelineEngine`, `INodeDispatcher`, status events
  (Queued → Executing → Completed / Failed / Cancelled)
- Implement `PipelineEngine`: linear execution, data flow between nodes, `CancellationToken`
  through the whole pipeline
- Unit tests for the engine against a fake dispatcher (no Revit)

### 1.2 Command Core Integration
- **`LocalDispatcher` = thin wrapper over the existing `CommandQueue`** (`CoreServices.Queue`),
  NOT a new queue → ExternalEvent path. The pipeline engine is just another caller, like
  WebView2 and the MCP bridge. This reuses for free: busy-bar visibility of the running node,
  `GetQueueStatus` introspection, and the pre-execution gate for confirming mutating nodes.
- Capability flags **extend the existing `[RevitCommand]` attribute** (`ReadOnly` already
  exists — no parallel `Mutates` flag): add `Headless`, `ExecutionScope` (PerMachine /
  Orchestrator), `SupportsProgress`. This is a public SDK contract change → SemVer minor bump,
  design once.
- **Standalone deliverable (ship before the engine):** declarative command parameters via
  attributes (`[NodeParam]`) + JSON schema generation — one schema serving nodes, MCP tool
  definitions, and validation. This improves the MCP layer immediately (agents currently guess
  payload shapes from descriptions), independent of pipelines.
- `OutputSchema` is the expensive part: commands currently return anonymous objects. Typed
  connections require refactoring Tools commands to declared result types — scope it as its
  own task, per command slice, not as "add an attribute".
- Orchestrator nodes run on a background thread outside the Revit context
- Tag existing commands with flags; unsuitable ones (interactive, no structured output) —
  excluded from the palette

### 1.3 Initial Node Set
- 1–2 command nodes from existing checks (e.g. CheckNaming)
- Filter (orchestrator): conditions on fields of the incoming OutputSchema
- ExportExcel (orchestrator)
- ExportPdf (orchestrator)
- Payload rule: compact JSON between nodes (IDs, counts), heavy files — path/link in the envelope

### 1.4 Visual Editor (Vue Flow in WebView2)
- Canvas: linear pipeline (no branching in V1), drag-and-drop from the palette
- Node palette from the command catalog, filtered by capability flags — **shared
  infrastructure with #43 (command palette): build the catalog once, both features consume it**
- Expanding a node → auto-generated parameter form from the JSON schema
  (string → input, bool → toggle, enum → dropdown)
- Typed connections: OutputSchema compatibility check against the next node's input when connecting
- Build-time validation (not runtime): incompatible schemas, missing parameters
- Live node statuses during execution + Stop button (cancellation via CancellationToken)

### 1.5 Saving and Sharing
- Save/load pipelines as `.atpipe` (JSON) in %AppData% or next to the project
- File schema versioning + migration when loading older versions
- Export/import as a file — sharing via Teams/email without any server

### 1.6 Release and Validation
- Ship local pipelines in the open-core version
- Gather feedback: which chains users build, whether `.atpipe` files circulate within teams
- In parallel: show a mockup/demo of session mode to 2–3 BIM managers

Future nodes riding on this platform: #53 (Parameter Requirements check), #47 (AI Reviewer
as a summary node over check outputs).

**Gate before Step 2:** at least one organization with multiple installations and an engaged
BIM manager (pilot). Pipeline files actually circulating within a team. Without this, Step 2
does not start.

## Step 2 — Cloud / Session Layer

### 2.1 Server and Sessions
- ASP.NET Core + SignalR Hub: session creation, code generation, per-session groups
- Transport abstraction: cloud relay (paid) and self-hosted LAN variant (Kestrel on 0.0.0.0,
  session code with packed endpoint) — optional, demand-driven
- Authentication (Entra ID for enterprise), Admin / User roles
- SignalR reconnect logic, command idempotency via Guid

### 2.2 Joining and Consent
- User flow: enter code → explicit consent screen ("the admin will be able to run commands")
  → join session
- Leave Session button always visible
- Policies: read-only commands — silent; mutating — per-command confirmation
- Admin presence dashboard: who is online, plugin version, open document

### 2.3 Catalog Handshake
- User reports their catalog on join: commands, contract versions, plugin version
- Editor merges catalogs into a compatibility matrix (machine × command)
- Pipeline validation against the matrix before launch: unavailable commands/versions highlighted
- Context check on the client: expected document vs `Document.Title` → `Failed("Wrong document")`

### 2.4 Distributed Execution
- `SessionDispatcher : INodeDispatcher` — distributing per-machine nodes via the hub,
  collecting partitions into the same `NodeOutput`
- Queue on the user side with TTL (Expired)
- Per-machine real-time statuses on the canvas (6 ✓ / 1 Executing / 1 Expired)
- Targeting: specific machine / everyone in the session / filter by open document
- Heavy results — Blob Storage, link in the envelope

### 2.5 Enterprise Features (paid tier)
- Session-wide summary reports (aggregating partitions into a single Excel/dashboard)
- Group policies: auto-approve extensions from the organization feed, default consent rules
- Managed installation of missing commands: proposal → signed package from a trusted feed →
  ExtensionLoader (never — code pushed directly over the wire)
- Later, demand-driven: scheduled triggers, graph branching, Teams notifications

### 2.6 Security and Compliance
- Extension package signing, trust at the feed level
- Audit log: who ran what, on whose machine, with what result
- Documentation for IT departments / works council (Betriebsrat): what data flows, which ports,
  what the user can deny

## #79 — Plan: Clash detection + AI-assisted auto-resolution pipeline (detect → classify → propose → approve → apply)

# План на будущее: детекция коллизий и полуавтоматическое их разрешение

## Идея

Найти коллизии умеют все инструменты — ценность в их **разрешении**. Большая часть коллизий в модели однотипна, и решение известно заранее. Канонический пример: колонна проходит сквозь чистовой пол — несущая колонна идёт до несущего перекрытия, а у чистового пола нужно вырезать геометрию вокруг колонны. Таких случаев сотни, каждый фиксится одним и тем же способом.

**Ключевой принцип: AI не редактирует геометрию свободно — AI классифицирует коллизию и выбирает готовый фикс из белого списка команд.** Фикс — это детерминированный вызов Revit API с параметрами (например `JoinGeometryUtils.JoinGeometry` + `SwitchJoinOrder`, либо `InstanceVoidCutUtils` / opening). Каталог команд и есть ограждение: у AI по построению нет доступа к произвольному редактированию.

## Конвейер

1. **Detect** — поиск пересечений через Revit API (`ElementIntersectsElementFilter`, батчами, с прогрессом через `IProgress` в `CommandRequest`). Точная геометрия (solids), без экспорта меша. Для каждой пары собирается геометрическая сигнатура: категории, типы, направление пересечения, объём пересечения.
2. **Classify** — сначала детерминированные правила («вертикальный несущий элемент × горизонтальный пол, тип пола содержит признак чистового, колонна проходит насквозь»). LLM (существующий `Ai`-слайс) подключается только там, где правило не сработало или нужно выбрать между стратегиями.
3. **Propose** — каждой коллизии назначается фикс из каталога: `JoinAndSwitchOrder`, `CreateOpening`, `AdjustTopOffset`, или «не знаю — к человеку».
4. **Approve** — human-in-the-loop в WebView: список коллизий, предпросмотр узла «до/после» (Three.js-вьювер), клик → `SelectionInRevit` / `IsolationInRevit`. Пакетное одобрение однотипных фиксов («применить все 47 фиксов типа „пол режется колонной"») — главная экономия времени.
5. **Apply** — write-команды в слайсе Tools; каждый фикс в своей транзакции (одна неудача не валит пакет), всё в `TransactionGroup` для общего Undo.

## Фазы

### Фаза 1 — без AI, один паттерн (MVP)
- Read-only команда детекции коллизий (новый слайс или `Elements`), пары + сигнатуры.
- Rule-based классификатор для одного паттерна: вертикальный несущий элемент × чистовой пол.
- Write-команда фикса: join + switch order / opening.
- UI-список с предпросмотром и пакетным применением.
- Уже сама по себе экономит часы и проверяет весь конвейер end-to-end.

### Фаза 2 — каталог фиксов + конфигурация
- Расширение каталога фиксов (opening, offset, split и т.д.).
- Конфигурируемые правила приоритета «кто кого режет» («несущее режет отделку», «бетон режет ГКЛ») — у каждого бюро свои нормы моделирования, зашивать нельзя.

### Фаза 3 — AI-классификация и data flywheel
- LLM через `Ai`-слайс выбирает паттерн/стратегию для случаев, не покрытых правилами.
- Каждое решение пользователя («применил / отклонил / исправил вручную») сохраняется как размеченный пример → датасет накапливается как побочный продукт работы → со временем улучшение классификатора вплоть до дообучения локальной модели (Ollama).

## Риски / ограничения (заложить сразу)

- **Связанные файлы**: коллизию со связью нельзя фиксить в линке — только на своей стороне либо в отчёт.
- **Workshared-модели**: перед пакетным применением проверять ownership элементов, иначе часть транзакций упадёт.
- **Приоритеты вырезания** — только через конфигурацию (см. Фаза 2).
- Детекция выполняется в Revit API-контексте (UI-поток) — обязательно батчи + прогресс + отмена через `CancellationToken`.

## Отложено в дальний ящик

Браузерная clash-детекция на меше (three-mesh-bvh) для *геометрических* проверок, которых нет в Revit API: зазоры/клиренсы («ближе 50 мм»), зоны обслуживания оборудования, высоты проходов. Для жёстких пересечений Revit-путь точнее и проще; Three.js остаётся слоем визуализации и триажа результатов.

## #80 — Vision: In-process AI agent — proactive model copilot (agent loop + change journal + shadow index + inbox)

state: open | labels: - | created: 2026-07-24 | comments: 4
https://github.com/Nikola1Davydov/AnalyzeTool/issues/80

# План: встроенный AI-агент, который живёт в модели

## Смена парадигмы

Сейчас AI в плагине — это функция, которую вызывает человек: открыл панель → выбрал → запустил → разобрал список. Цель — инверсия: **агент постоянно наблюдает модель и приходит к пользователю сам**, а человек только утверждает решения. Три слоя:

1. **Непрерывное наблюдение** — агент слушает изменения модели и реагирует в контексте: «ты только что скопировал 40 дверей — у копий пустые параметры классификации, заполнить как у исходных?»
2. **Диалог вместо панелей** — одно поле ввода над всей моделью; агент планирует, зовёт существующие команды как инструменты, показывает план, исполняет с review. Панели становятся инструментами агента.
3. **«Code review для BIM»** — синхронизация = pull request модели: агент делает ревью именно твоего диффа («12 новых элементов без параметров, 2 имени не по конвенции, 1 коллизия») с пакетным исправлением и интерактивным разбором (изоляция элемента во вьюпорте → да/нет → следующий).

## Ключевая архитектурная идея: агент = третий транспорт

`McpBridgeServer` уже доказывает паттерн: фоновые потоки зовут `CommandQueue.ExecuteAsync()`, диспетчер маршалит доступ к модели на Revit-поток через `RevitTaskHub`. Внутренний агент — тот же паттерн, только запросы порождает LLM-цикл в фоновом `Task` (по правилам архитектуры: ProjectReference на Core + `InternalsVisibleTo`, ноль изменений в Core).

### Что уже есть

- **Каталог инструментов с готовыми схемами**: `CommandRegistration` несёт имя, описание, JSON Schema входа (`AIJsonUtilities.CreateJsonSchema` из `InputType`) + флаги `ReadOnly`/`Destructive`. Это готовый формат `tools` для function calling.
- **Единая точка входа**: `CommandQueue.ExecuteAsync(CommandRequest)` с `Source: "agent"`.
- **Ворота согласования**: `CommandRequest.Gate` видит метаданные команды и может отказать — готовый механизм для «ReadOnly исполнять сразу, Destructive — в inbox на одобрение».
- **Наблюдаемость**: `Running`/`RunningChanged`, `GetQueueStatus`.
- **LLM-инфраструктура**: `AiProviderRegistry` (Ollama + OpenAI-совместимые, DPAPI-ключи), `AiClientFactory`.

### Чего не хватает — компоненты

**1. Tool calling в чат-клиенте.** `OpenAiCompatibleChatClient` — plain chat completion, без `tools`/`tool_calls`. Нужен цикл «LLM → tool calls → очередь → результаты → LLM» (вариант: `IChatClient` из уже подключённого `Microsoft.Extensions.AI` с function invocation).

**2. Агентский цикл.** Отдельный компонент по образцу `Mcp.Bridge`: триггер + контекст на входе, цикл с бюджетами (максимум шагов, таймаут, `CancellationToken` — `CommandRequest` уже всё переносит).

**3. Change Journal + триггеры.** См. раздел «Производительность» ниже — проектируется раньше самого цикла.

**4. Inbox UI + реализация Gate.** Vue-лента карточек-предложений: destructive-вызов агента не исполняется, а становится карточкой «агент хочет записать 47 значений — [дифф] [применить] [отклонить]». Чат и inbox — две поверхности одного цикла: чат для задач от пользователя, лента для инициативы агента по триггерам.

**5. Память проекта/бюро.** Принятые/отклонённые решения копятся как few-shot примеры — агент выучивает конвенции без дообучения.

## Производительность (принципиально для больших моделей)

`DocumentChanged` стреляет синхронно в конце транзакции — всё в обработчике продлевает коммит. Правило №1: **обработчик только пишет ID + имена транзакций в буфер и выходит** (микросекунды). Дальше:

- **Дебаунс и слияние**: анализ не на каждое событие, а в паузу активности (через `Idling`) или явный триггер (синхронизация); дедупликация (элемент, изменённый 5 раз, = одна запись). Имя транзакции классифицирует действие вообще без чтения элементов.
- **Ступенчатое чтение**: Уровень 0 — ID + действие + имя транзакции (уже в журнале). Уровень 1 — лёгкая сводка батча (категория, тип, уровень) — миллисекунды через `FilteredElementCollector` по конкретным ID, чанками по 20–30 через короткие вызовы `RevitTaskHub`. Уровень 2 — полные параметры/геометрия **только для элементов, которые агент сам запросил** (это и даёт tool calling).
- **Теневой индекс** (вторая итерация): лёгкий слепок модели (ID → категория, тип, уровень, ключевые параметры), строится фоново чанками при открытии, обновляется инкрементально дельтами журнала. Решает проблему удалений (удалённый элемент прочитать нельзя — а в индексе он есть) и снимает почти все чтения с Revit-потока.

## Хранилища

| Данные | Хранилище | Почему |
| --- | --- | --- |
| Change Journal | Память (ring buffer / `ConcurrentQueue`) | Жизненный цикл — сессия; килобайты; не источник истины |
| Теневой индекс | **LiteDB**, `%LOCALAPPDATA%\AnalyseTool\models\<guid>\index.db` | Точечные обновления/чтения, индексы; чисто managed — нет конфликтов нативных DLL в процессе Revit (риск SQLite/e_sqlite3). Ключ модели — `WorksharingCentralGUID` / UniqueId ProjectInformation, не путь к файлу |
| Память агента, карточки | JSON (`agent-memory.json`) | Килобайты, человеко-читаемо, существующий паттерн `ai-providers.json` |
| Снапшоты для диффа версий / экспорт аналитики / архив журналов | Parquet (`Parquet.Net`) | Write-once данные, колоночное сжатие, дифф = колоночный скан. НЕ для живого индекса (неизменяемый формат) |

Правила: **живое и мутируемое → LiteDB, неизменяемые слепки → Parquet.** **Индекс — восстановимый кэш, истина — всегда модель**: любая рассинхронизация (упал Revit, модель правили без плагина, смена формата) → пометить устаревшим → фоновая переиндексация тем же кодом, что и первичная. НЕ хранить в RVT через Extensible Storage (раздувает файл, уезжает к коллегам, требует транзакций).

## Модель агента (настройки)

- Провайдеры переиспользуются из `AiProviderRegistry`; новый пункт настроек — «модель агента», отдельно от модели для простых подсказок (дешёвые операции — дешёвой моделью, агент — сильной: Qwen 2.5+, Llama 3.1+ или облачная).
- Слабая модель в tool-calling-цикле ломается, а не «работает хуже»: при выборе — проверочный tool call и честное «эта модель не поддерживает агентский режим».

## Три варианта хостинга цикла (совместимы, общий каталог команд)

- **A. Внешний агент через MCP** (уже работает): Claude Code/Desktop → `AnalyseTool.Mcp.exe` → бридж → очередь. Лучший цикл бесплатно, но: отдельное окно, только pull (внешний клиент нельзя разбудить триггерами), чужой UX. Использовать как бесплатный эксперимент до написания кода.
- **B. Встроенный агент** (этот план): свой цикл, полный контроль, проактивность, модель из настроек.
- **C. Sidecar** (опция «премиум-мозг»): цикл Claude Agent SDK / headless `claude -p` в отдельном процессе (по образцу `AnalyseTool.Mcp.exe`), инструменты — наш MCP-сервер, UI — наш WebView. Минусы: API-биллинг, лишний процесс, вендор-зависимость. Проектировать цикл заменяемым (интерфейс «провайдер агента»).

## Безопасность

- Белый список инструментов агента как часть конфигурации Gate. **`ExecuteRevitCode` (Roslyn) исключить из tool-набора автономного агента** или гейтить жёстче всех — произвольный C# в Revit ломает модель «безопасного каталога команд».
- Destructive-команды — только через одобрение в inbox; `ReadOnly` — автоматически.

## Фазы (каждый шаг полезен сам по себе)

1. **Tool calling + цикл с ручным триггером** — кнопка/чат «сделай ревью модели», только ReadOnly-команды, отчёт. Без событий и нового UI — уже «вау».
2. **Gate + inbox** — агент получает право *предлагать* записи (карточки, пакетное применение через `SetDataToParameters`).
3. **Change Journal + `DocumentChanged`-триггеры** — проактивность, «ревью после синхронизации».
4. **Теневой индекс (LiteDB)** — реакция на удаления, независимость от Revit-потока, большие модели.
5. **Память проекта + снапшоты (Parquet)** — конвенции бюро, дифф версий.

- #79 — коллизии: конвейер detect → classify → propose → approve → apply становится частным случаем работы этого агента (карточки в том же inbox).

## #81 — Automate SDK package publishing (deferred — currently manual)

state: open | labels: enhancement | created: 2026-07-26 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/81

Publishing `AnalyseTool.Sdk` to nuget.org is a **manual** step today — see `RELEASE_CHECKLIST.md`, section "Artifacts & distribution".

## Why it was deferred

Automation was built and then removed on purpose. The contract changes a few times a year, and the standing cost was out of proportion to that cadence:

- a Trusted Publishing policy registered on nuget.org, tied to one workflow **filename** (renaming the file silently breaks publishing),
- a `NUGET_USER` repository variable + an OIDC `NuGet/login` step in the release workflow,
- a `PublishSdkPackage` NUKE target that, via `.DependsOn(Ci)`, re-ran the entire CI gate on every **plugin** release — even when the SDK version had not moved.

## What we lost

`TestSdkPackage` (builds an external-author project against the freshly packed nupkg) no longer stands between a broken package and the feed *by construction*. The signal still exists — it runs on every push — but the gate is now discipline: the checklist says to push only the artifact from a green run. A published version cannot be recalled.

## What to restore if publishing gets frequent

The removed code, for reference:

| Commit | What it added |
| --- | --- |
| `af709f7` | `PublishSdkPackage` target (`src/build/Build.Publish.NuGet.cs`), `.DependsOn(Ci)`, `EnableSkipDuplicate` |
| `9daa799` | Release workflow wiring + default feed switched from GitHub Packages to nuget.org |
| `475acd9` | Trusted Publishing (`NuGet/login`, `id-token: write`, `NUGET_USER` variable, fallback to the `NUGET_API_KEY` secret) |

Notes for whoever picks this up:

- Prefer Trusted Publishing over a long-lived API key — no secret to store or rotate. It keys on repository **+ workflow filename**.
- GitHub Packages is not a useful middle step: it demands a PAT even to *read* public packages.
- Publishing must stay gated on the SDK version actually having changed, otherwise every plugin release pays for a no-op push.
- Whatever ships, the pinned versions in `ONBOARDING.md` §4.1 and `src/LLM.md` §4 must be bumped in lockstep with the push — they have to name a version authors can restore.

Related: #48 (distribution model), #67 (SDK contract).

## #83 — MCP: element placement & data quality

state: open | labels: - | created: 2026-07-26 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/83

# MCP: element placement & data quality
 
Improvements needed so an LLM agent can place elements reliably through the MCP transport.
Findings from a session where the agent had to place a door and a tree in an existing model.
 
---
 
## P0 — Correctness
 
Without these, commands silently return something other than what was asked. This is the worst
failure mode: the agent does not notice the miss and keeps building on an empty result.
 
### Placement
 
- [ ] **`PlaceFamilyInstances(typeId, placements[])`** — programmatic placement with coordinates,
      returning created element ids. Replaces interactive-only `PlaceFamilyInstance`.
  - [ ] Required `units` field (`"mm" | "m" | "ft"`) — agents will send millimetres, not internal feet
  - [ ] Required `coordinateSystem` field (`"project" | "shared"`) — the difference is hundreds of
        metres on real projects
  - [ ] Per-placement `hostId`, `levelId`, `rotation`, `flipFacing`, `flipHand`
  - [ ] Response splits `created[]` and `failed[]` with a per-item reason
- [ ] **`GetElementGeometry(id)`** — placement is impossible without it. `{id, name, level}` does not
      say where a wall is or which side faces outside.
  - [ ] `locationCurve` (start, end, length)
  - [ ] `orientation` — exterior normal
  - [ ] `width`, `baseLevel`, `heightOffset`, `isExterior`
  - [ ] `openings[]` with `distanceAlongCurve` and `width` — without this a batch stacks the second
        window on top of the first
### Query data
 
- [ ] **Split types from instances in `GetElements`** — add `elementKind: "instances" | "types" | "all"`,
      defaulting to `instances`.
  - Observed: `{category: "Wände", limit: 10}` returned 10 `WallType` and zero instances. System types
    sort first by id, so `limit` cut off exactly what the query was for. Needed `limit: 120` to reach
    8 walls.
- [ ] **Add `familyId` / `familyName` to `GetElements` results** — results of `GetFamilies` and
      `GetElements` currently cannot be joined.
- [ ] **Split `nameContains` into `familyNameContains` and `typeNameContains`**
  - Observed: `nameContains: "Laub"` on category `Bepflanzung` returned `[]`. The family is
    `Baum RPC - Laubbaum`, but its types are named `Japanischer Ahorn - 3,0 Meter`. The filter matched
    type names only, with no way to tell.
- [ ] **Accept `builtInCategory` as an alternative to the localised `category`**
  - `OST_Planting` is language-independent; `"Bepflanzung"` vs `"Pflanzen"` is guesswork on a German install
- [ ] **Return `CategoryNotFound` instead of `[]` on an unknown category**, with a `didYouMean[]` list.
      An empty array is indistinguishable from "zero matches".
---
 
## P1 — Trustworthy values & sane failures
 
- [ ] **Return raw numeric parameter values alongside the formatted string**
```json
  {
    "name": "Breite",
    "storageType": "Double",
    "value": 1.01,
    "unit": "m",
    "display": "1,010 m"
  }
```
  Currently only `"1,010 m"` is returned — a German decimal comma with the unit inside the string.
  Comparing a door width against a wall thickness requires locale-aware parsing, and an
  order-of-magnitude error is a matter of time.
- [ ] **Wrap batch placement in a single `TransactionGroup` + `Assimilate()`** so one Ctrl+Z undoes the
      whole operation instead of 12 separate undos
- [ ] **Add `failOnFirstError` vs `bestEffort` mode** — "place 20 windows" wants best-effort,
      "place a door and a stair" wants fail-fast
- [ ] **Add `dryRun: true`** — return what *would* be created, no transaction. A cheap self-check for the agent.
- [ ] **Typed placement errors** instead of raw Revit exceptions
```csharp
  public enum PlacementError
  {
      SymbolNotActivated,      // symbol.Activate() was not called
      HostRequired,            // door/window without a host wall
      PointNotOnHostCurve,     // projected distance exceeds tolerance
      OpeningWiderThanWall,    // opening does not fit the wall segment
      OverlapsExistingOpening,
      LevelNotFound,
      WorksetNotEditable
  }
```
- [ ] **`GetActiveView`** — view type, level, `isTemplate`. RPC planting cannot be placed in a 3D view
      without topography, and there is currently no way to check before advising the user.
---
 
## P2 — Intent-level API
 
Highest hit-rate gain. LLMs are bad at computing coordinates and good at stating intent.
Let the server do the geometry.
 
- [ ] `PlaceOnWall(wallId, typeId, Distribution.Centered)`
- [ ] `PlaceOnWall(wallId, typeId, Distribution.Evenly, count, sillHeight)`
- [ ] `PlaceInRoom(roomId, typeId, Anchor.Center)`
- [ ] `PlaceAlongCurve(curveId, typeId, spacing)`
Server reads `LocationCurve`, divides it, checks collisions against existing openings.
"Three windows evenly along the south wall" then works on the first attempt instead of the third.
 
---
 
## P3 — System elements
 
Walls, floors and roofs are not `FamilyInstance` and cannot be created through MCP at all today.
These close the "build me a box" scenario rather than only "add to an existing box".
 
- [ ] `CreateWalls(segments[], typeId, levelId, height)`
- [ ] `CreateFloor(loop, typeId, levelId)`
- [ ] `CreateRoof(footprint, typeId, levelId, slopes[])`
---
 
## P4 — Context economy
 
Matters on large models, but pointless while the data above is still wrong.
 
- [ ] **Hide `uniqueId` and `versionGuid` behind `verbose: true`** or a `fields[]` selector.
      `versionGuid` was identical across all 213 families — it describes the document, not the record.
      Together they are roughly half the payload of a list response.
- [ ] **Add `parameterNames` to `GetFamilyTypes`**, and return no parameters by default.
      A request for one door family returned 4 types × ~50 parameters when `id` and `name` were enough.
- [ ] **Cursor pagination** — `GetFamilies` returns `count: 213, returned: 40` with no way to fetch the
      rest except raising `limit`
```json
  { "count": 213, "returned": 40, "nextCursor": "eyJhZnRlcklkIjoyMDkyMTA5fQ==" }
```
- [ ] **One response envelope for every command** — `GetFamilies` returns `{count, returned, families}`,
      `GetElements` returns a bare array with no count
- [ ] **Use `null`, not `""`, for absent values** — `"level": ""` on a type reads as "has a level, unnamed"
- [ ] **Drop the workset block when `isWorkshared: false`** — `"workset": "", "worksetId": 0` is noise
- [ ] **Return created ids from interactive placement** — subscribe to `Idling`, wait for the user to
      exit placement mode, then return what was created. Collapses "place → verify" into one call.
      (`PlaceFamilyInstance` currently returns `{ok: true}` and verification needs a separate
      `GetFamilyInstances` round trip.)
---
 
## Suggested order
 
1. **P0** — makes placement possible at all
2. **P1** — makes results trustworthy and failures recoverable
3. **P2** — the quality jump; do not defer this, the agent will keep missing with raw coordinates even
   with full geometric context
4. **P3 / P4** — scope expansion and cost reduction

# MCP: server ergonomics, safety & protocol surface

Server-level issues — these are not about individual commands, so they are kept separate from
the placement / data-quality checklist.

---

## P0 — Bootstrap command

The agent currently starts blind. In an observed session, four calls were spent discovering context
that one call could have returned.

- [ ] **`GetModelOverview()`** — single entry point, called first in every session
  ```json
  {
    "title": "...", "revitVersion": 2024, "language": "de-DE",
    "displayUnits": "mm", "isWorkshared": false,
    "activeView": { "name": "Ebene 0", "type": "FloorPlan", "levelId": 2554001 },
    "levels": [{ "id": 2554001, "name": "Ebene 0", "elevation": 0 }],
    "categoryCounts": { "Wände": 8, "Türen": 1, "Fenster": 0 },
    "hasTopography": false
  }
  ```
  - [ ] `language` — tells the agent to write category names in German instead of guessing
  - [ ] `displayUnits` — removes the millimetres-vs-internal-feet ambiguity up front
  - [ ] `categoryCounts` — shows where actual model geometry exists, not just a type palette
  - [ ] `hasTopography` / `activeView` — required to know whether RPC planting can be placed at all

Recommend it in every tool description as the first call of a session.

---

## P0 — Guard rails on destructive commands

`DeleteFamilyElements` and `PurgeFamilies` are currently exposed to the agent on the same footing as
`GetElements`: one call, no confirmation. Deleting a family removes all of its instances. A single
hallucinated id is enough to take apart someone's project.

- [ ] **Mandatory `dryRun` first call** — returns exactly what would be deleted and how many instances
      are affected
- [ ] **Confirmation token** returned by the dry run and required by the real call
- [ ] **Instance-count threshold** — refuse outright above N affected elements unless explicitly forced
- [ ] **Mark destructive commands in their description** so the client can surface them differently

This is the one place where friction is the feature.

---

## P1 — Tool descriptions are part of the data contract

Descriptions drive command selection more strongly than parameter schemas do. Some are already good —
the `"Language-specific: e.g. \"Wände\", not \"Walls\""` note prevented a wrong call in practice.
Others are missing entirely.

- [ ] **State read-only vs modifies-model** in every description
- [ ] **State the typical cost** of a call (cheap / scans the document / extracts geometry)
- [ ] **State the prerequisite command** — `GetFamilyTypes` is useless without `GetFamilies`,
      and that belongs in the description rather than being left implicit
- [ ] **Unify naming** — `company_checkcollisions_RunClashDetection` and `GetElements` are two schemes
      in one server. Extension prefixes also cost context on every tool listing.

---

## P1 — Evals

A concrete task set already exists from real sessions. Run it after every API change.

- [ ] Build a task suite:
  - [ ] "Place a front door in an exterior wall"
  - [ ] "Place three windows evenly along the south wall"
  - [ ] "Find every door wider than 1 m"
  - [ ] "Which walls have no openings"
  - [ ] "Build a simple house" (once system-element creation exists)
- [ ] Track **first-attempt success rate**
- [ ] Track **calls per task** — easy to ignore, but it maps directly to cost and to the chance the
      agent loses the thread. Observed: 8 calls to place 2 family instances; 3 would have been enough.
- [ ] Track **tokens per task** — catches payload bloat regressions

---

## P2 — Use the rest of the protocol, not only tools

Everything is currently exposed as tools.

- [ ] **Expose static reference data as MCP resources** — level list, categories with their localised
      names, wall types. The client caches them: no tool call spent, no clutter in the call history.
- [ ] **Add MCP prompts for canned workflows** — e.g. "check clashes between MEP and structure and
      produce a report". This also pins down the correct command sequence instead of hoping the model
      infers it.

---

## Suggested order

1. `GetModelOverview` — cheapest item on either list, removes a whole class of context-blind errors
2. Destructive-command guard rails — before anyone runs this against a production model
3. Tool descriptions — no code changes, immediate effect on command selection
4. Evals — needed before the API changes in the other checklist land, so the effect is measurable
5. Resources / prompts

## #85 — MCP: per-document history & persistence

state: open | labels: - | created: 2026-07-26 | comments: 0

# MCP: per-document history & persistence

Persisting what the agent learns and what it did, keyed per document.
Three separate mechanisms — only one of them is a search problem.

---

## P0 — Document key

Everything below hangs off a stable document identifier.

- [ ] **Use `Document.CreationGUID` as the key** — no custom GUID in Extensible Storage needed
- [ ] **Verify Save As behaviour empirically** — does `CreationGUID` regenerate on Save As?
      This decides whether a copy inherits the original's history. Do not take the docs' word for it;
      a one-minute test settles it permanently.
  - [ ] If it does **not** regenerate: store `PathName` alongside the history and compare on open.
        Mismatch likely means a copy — regenerate the key and ask the user whether to carry history over.
- [ ] **For workshared models, key on the central model GUID**
      (`ModelPathUtils` / `GetWorksharingCentralModelPath`), not the local copy — otherwise every team
      member gets an isolated history where it should be shared.

---

## P0 — Operation log (event sourcing, not RAG)

Append-only audit trail. Deterministic queries only: last N operations, operations touching element X,
what session Y created. No semantic search.

This is the counterpart to the destructive-command guard rails: `PurgeFamilies` stops being
irreversible once you know exactly what it removed.

- [ ] **Record every model-modifying command**
  ```json
  {
    "opId": "01J8X...", "timestamp": "2026-07-26T14:22:10Z",
    "command": "PlaceFamilyInstances",
    "args": { "typeId": 2125221, "placements": [] },
    "created": [2554282], "modified": [], "deleted": [],
    "transactionGroupName": "MCP: place front door",
    "docVersion": 447
  }
  ```
- [ ] **Store as JSONL** — one operation per line, atomic append, tail-readable without loading the file
- [ ] **Rotate by month or size** (`operations-2026-07.jsonl`)
- [ ] **Expose `GetOperationHistory(count)`** so the agent can answer "what did I change"
- [ ] **Per-operation rollback** — Revit's linear Undo does not know where one logical agent operation
      ended and the next began
- [ ] Doubles as the eval data source: real call sequences against real models

---

## P1 — Project conventions (persistent state, not RAG)

Knowledge the agent re-derives from scratch every session. Kilobytes — loads into context whole,
so there is nothing to retrieve.

Observed: four calls at the start of a session spent rediscovering exactly this.

- [ ] **Persist inferred facts**: exterior wall type, level naming scheme, door/window family prefixes,
      units, language
- [ ] **Distinguish `inferred` from `userConfirmed`** — the first may be re-checked, the second may not
  ```json
  {
    "exteriorWallType": { "value": "Ziegel+WD hart 300+160", "source": "inferred", "confidence": 0.8 },
    "units":            { "value": "mm", "source": "userConfirmed" }
  }
  ```
- [ ] **Plain JSON file**, written via temp + `File.Replace` for atomicity
- [ ] **Expose as an MCP resource, not a tool** — the client caches it, costing no tool call
- [ ] Effectively the persistent version of `GetModelOverview`

---

## P1 — Storage layout

Mirrors the existing versioned AppData structure used for extensions.

```
%AppData%/AnalyseTool/<version>/documents/<creationGuid>/
    conventions.json
    operations-2026-07.jsonl
```

- [ ] **Start with JSON / JSONL — do not add SQLite yet**
  - SQLite in a Revit add-in pulls a native DLL (`e_sqlite3.dll` / `SQLite.Interop.dll`). All add-ins
    share one process; if another plugin already loaded a different version, the result is its version
    or a `BadImageFormatException` — painful to debug on a client machine.
  - Solvable (explicit `SetDllDirectory`, dedicated `AssemblyLoadContext`, static linking via
    `SQLitePCLRaw.bundle_e_sqlite3`) but not worth it for an append-only log.
- [ ] **Hide storage behind an interface from day one** so the swap stays local
  ```csharp
  public interface IOperationLog
  {
      void Append(OperationRecord record);
      IReadOnlyList<OperationRecord> GetRecent(int count);
      IReadOnlyList<OperationRecord> GetByElementId(long elementId);
  }
  // JsonlOperationLog now, SqliteOperationLog later
  ```
  `GetByElementId` is a linear scan over JSONL — fine up to tens of thousands of records. The moment
  it stops being fine is the signal to introduce SQLite.

### SQLite triggers — none reached yet

- [ ] Element cache: a 50k-element projection in JSON filtered with LINQ is slow and memory-hungry
- [ ] FTS5: full-text search over a family library is not worth hand-rolling
- [ ] Concurrent access: two processes writing the same store

## P2 — Element cache (materialized projection)

Same pattern as the product catalog projection. Deferred deliberately — a stale cache is worse than no
cache, because the agent confidently builds on wrong ids, and Revit reuses ids after deletion.

- [ ] **Do not start without versioning.** Subscribe to `DocumentChanged`; every cached response carries
      a `docVersion`; mismatch invalidates.
- [ ] **Move `versionGuid` out of individual records into the response envelope** — it describes the
      document, not the record, and duplicating it across 213 entries is pure payload.
      (Supersedes the "hide versionGuid" item in the data-quality checklist: it is not noise, it is the
      invalidation key, in the wrong place.)
  ```json
  {
    "docVersion": { "guid": "fe17adb3-...", "saves": 447 },
    "count": 213, "returned": 40,
    "families": []
  }
  ```

## P3 — Where RAG is actually warranted

Only two cases. Everything above is deterministic access and would be roughly three times more
expensive and less accurate as retrieval.

- [ ] **Family library search** — thousands of `.rfa` on a network drive, queries like "two-sash window

      Name matching cannot bridge that.
  - [ ] Start with **SQLite FTS5** over family/type names and parameters — covers most fuzzy search

  - [ ] Add vectors only where FTS5 demonstrably fails: `sqlite-vec` as an extension on the same

- [ ] **Standards / regulations** — DIN, state LBO, Abstandsflächen, if the urban planning direction
      grows. Large texts, natural-language questions: textbook RAG.

## Out of scope

- [ ] **Do not persist conversation history.** The client already holds session context. A server
      storing "what we discussed" creates a second source of truth that will eventually diverge.
      Persist only what outlives the session and belongs to the *document*, not the conversation.

## #87 — Extension supply chain: no signature or hash verification, and the download marker is lost

state: open | labels: enhancement | created: 2026-07-28 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/87

Assessment of the install/update path as it stands after the extension manager work, written so it can be handed to a corporate IT reviewer. Findings are from the code, not assumptions.

## What already holds up

- **The package is inspectable.** A plain zip of DLLs — nothing packed, encrypted or obfuscated. Antivirus and EDR see the archive and every file extracted from it.
- **Zip-slip is blocked twice** (`ExtensionPackage.cs`): entry names containing `..` or rooted paths are rejected, and every destination path is re-checked to stay inside the target folder.
- **HTTPS is enforced.** `ExtensionUpdateFeed.DownloadPackageAsync` refuses any non-`https://` download URL.
- **Nothing updates itself.** `CheckExtensionUpdates` and `UpdateExtension` are separate, both user-invoked. The host never fetches and executes new code on its own — a materially different risk profile from a self-updating add-in.
- **Install requires consent.** `InstallExtensionFromFile` refuses without `consent=true`, and the consent is logged with publisher and source file.
- **Per-user install**, `%LOCALAPPDATA%`, no admin rights, no machine-wide change.

## Gaps

### 1. No signature and no hash verification — highest impact
Neither the zip nor the assemblies inside are checked for an Authenticode signature, and the update feed carries no digest to compare against. HTTPS proves the connection reached github.com; it says nothing about who authored the artifact. Whoever controls the `updateFeed` URL — or the repository behind it — delivers code that runs in-process. This is the first question an IT reviewer asks.

### 2. Extensions are full trust, in-process
The collectible `AssemblyLoadContext` is an unload/type-identity mechanism, **not a sandbox**. An extension can touch any file the user can, open sockets, start processes — the same rights as Revit itself. There is no permission model, and the docs should not let "isolated load context" be read as a security boundary.

### 3. Mark-of-the-Web is dropped on extract
A downloaded zip carries the zone identifier, but `ZipFile` extraction does not propagate it to the extracted files (Explorer's own extractor does). The DLL on disk therefore looks locally created, and SmartScreen does not apply to it.

### 4. Running from a user-writable path
`%LOCALAPPDATA%` with no admin is exactly the pattern AppLocker/WDAC policies exist to block, since it allows execution without IT approval. In a locked-down environment this is a finding in itself, independent of what the code does.

### 5. Script extensions look like a known malware shape
Compiling a `.cs` in memory and executing it is a pattern some EDR products flag heuristically regardless of content. AI-driven C# execution is off by default, which is right; worth keeping that way and documenting why.

## Proposed work, in order of value per effort

- [ ] **Publish a digest in the feed and verify it before install.** Cheapest meaningful fix — closes artifact substitution even when the transport or the host is untrusted.
- [ ] **Preserve Mark-of-the-Web** on extracted files (write the zone identifier stream), so AV and SmartScreen treat them as what they are: downloaded binaries.
- [ ] **Surface the signer.** If `entryAssembly` is Authenticode-signed, show the publisher in the manager; add an opt-in "only install signed extensions" setting. Even display-only gives IT something to write a policy against.
- [ ] **Document the trust model** — one page stating what is verified, what is not, and with which privileges extension code runs. Link it from ONBOARDING and the design doc.

## Context

This model matches how pyRevit, Dynamo and most Revit add-in ecosystems work — none of them sandbox either. That makes it unsurprising, not safe; the signing question still has to be answered when someone asks.

Related: #48 (distribution model), #76 (registry).

state: open | labels: - | created: 2026-08-01 | comments: 0

Part of #70. Design: [`docs/pipeline-design.md`](https://github.com/Nikola1Davydov/AnalyzeTool/blob/claude/pipelines-plan-f8jrgf/docs/pipeline-design.md).

Needs #88 (nothing mutating runs unattended before it) and #89 (typed edges).

**This is the whole of "pipelines" until the gate opens.** A format plus a linear runner —
no canvas, no palette, no new frontend surface. It gives MCP something it lacks today: a way
to freeze a chain that worked and replay it without an LLM.

## Design decisions already taken

- **A node IS a command**, and this needs no capability flag. Routing is already implicit:
  `CommandDispatcher.DispatchAsync` awaits `ExecuteAsync` on the caller's thread, and
  `RunInRevitAsync` is the only path to the Revit thread — so a command that never calls it
  never touches it. The `Headless` flag from #70 decides nothing and is dropped (as are
  `SupportsProgress`, `[NodeParam]` and an execution-mode signal — reasons recorded in the doc).
- **A run interleaves and is not atomic.** `RevitTaskHub.Execute` drains its whole queue, so
  other transports run between nodes. Accepted for V1 and stated in the contract; mutating
  nodes re-check their own preconditions (`Overwrite`/`OnlyIfEmpty`/`SkipIfEqual` are the
  existing mechanism). Three commands already make multiple round-trips today
  (`PurgeFamilies`, `PurgeFamilyTypes`, `LibraryService`) — a pipeline stretches that window
  from milliseconds to minutes.
- **No Microsoft Agent Framework in V1** — an external dependency inside Core, which loads
  into an ALC in the Revit process and multi-targets net8/net10. `.atpipe` stays the contract,
  so MAF remains adoptable at #92 for free.

## Scope

- [ ] `.atpipe` v1 in Core. Reserved up front because retrofitting each is a migration:
      per-node `contract` version, `state` for pause/resume, **`onFailure`**
      (`continue` | `stopNode` | `stopPipeline`, default `stopPipeline` for `Destructive`),
      and a run receipt embedded in every exported artifact (the `.atpipe`, command contract
      versions, and for AI nodes the model).
- [ ] `IPipelineEngine`, `INodeDispatcher`, status events (Queued → Executing → Completed /
      Failed / Cancelled), linear execution, `CancellationToken` through the run.
- [ ] `LocalDispatcher` over `CommandQueue` — busy bar, `GetQueueStatus` and the pre-execution
      gate come for free.
- [ ] Result caching keyed by (inputs + params) hash, **`ReadOnly` nodes only**. ComfyUI's
      nodes are pure functions; ours change a live model.
- [ ] **Revit-free test project.** `AnalyseTool.Test` holds one `UnitTest1.cs` and references
      `AnalyseTool.App`, so it drags in Revit — engine tests against a fake dispatcher cannot
      live there.
- [ ] `RunPipeline` / `ValidatePipeline` commands; storage under
      `%LOCALAPPDATA%\AnalyseTool\pipelines\` via `PathProvider`.
- [ ] Orchestrator nodes as ordinary commands in Tools: Filter, ExportExcel, ExportPdf.

## Done when

A hand-written (or agent-written) `.atpipe` runs end to end from MCP or the console, with
live status and a working Stop.

## #92 — S3 (GATED) — AI nodes, approval as a graph invariant, pause/resume

state: open | labels: - | created: 2026-08-01 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/92

Part of #70. Design: [`docs/pipeline-design.md`](https://github.com/Nikola1Davydov/AnalyzeTool/blob/claude/pipelines-plan-f8jrgf/docs/pipeline-design.md). Detail in https://github.com/Nikola1Davydov/AnalyzeTool/issues/70#issuecomment-5074654067.

Behind the same gate as #91, and needs the `state` field reserved by #90 — that reservation is
what makes suspension possible without a format migration.

## The AI node is a command, not a new node kind

The repo already contains five AI commands with the prompt baked into C# —
`OllamaSuggestNames` is the template: it takes `{ model, prompt, items: [{ id, currentName,
context }] }`, returns `{ suggestions: [{ id, name }] }`, and its own doc comment says it *"does
not touch the Revit model — the caller reviews and applies each rename via RenameFamily"*.

So the AI node is that, with the prompt and the output schema moved from C# into node params:
one new `AiTransform` command in `Tools/Ai/Features/`. The engine keeps one node kind and needs
to know nothing about AI; only the graph validator does, and by command identity.

Four rules, read off the existing command rather than invented:

1. Input is a list of items carrying **our** `id`.
2. Output is those same ids plus new fields — **the AI adds a column, it never invents the
   table**. Provenance, approval rendering and "no dropped or reordered rows" all fall out of
   this. Returned ids are validated against the input set in node infrastructure.
3. The AI never writes; a separate command applies. **AI decides WHAT, the C# command decides
   HOW** — and the approval node sits exactly on that seam.
4. One call per batch, because a consistent result requires the model to see the whole list.

Terminal report nodes (#47) are the one exception to rule 2 — nothing downstream consumes them.

## Three kinds of AI node

- **AI transformation** — `AiTransform`; output constrained by a JSON schema set in the node
  config, which doubles as the model's response format and its validator. An AI node is
  **easier to type than a command**: its output schema is configuration, not a refactor.
- **AI router** — semantic branching. Needs branching, so not before the editor.
- **Bounded agent node** — an agent loop with its own tool allowlist, step budget and goal. The
  only kind that genuinely needs engine involvement, since it composes other commands.

## Where the model comes from

`AiClientFactory.Create(providerId, model)`. `AiProviderRegistry` already holds the built-in
local Ollama **plus user-added OpenAI-compatible endpoints** with a DPAPI-encrypted key, so the
cloud path exists today and "AI nodes need a strong local machine" is not true.

Reusing the MCP connection to a chat client is rejected: MCP is inverted (the chat client is the
caller, we are the tool provider), `RevitBridgeClient` is connect-per-request with no way to
initiate toward the client, and a run would then require the chat app to be open — which defeats
a repeatable pipeline. The agent's role is to **author** pipelines and to **invoke**
`RunPipeline`, not to be the model inside a node.

## Approval is a filter, not a barrier

Stated as a barrier the invariant kills press-and-forget. So: items passing a machine-checkable
predicate flow through and are written; the rest are parked as a card in the inbox (#80) and
**the run completes**.

```json
{ "id": "n3", "command": "Approval", "params": {
    "autoAccept": { "valueMatches": "^[A-Z]{2}_[A-Za-z0-9]+_\\d{3}$",
                    "maxItems": 50, "minConfidence": 0.9 } } }
```

The three conditions are not interchangeable: a constraint on the value itself is **strong**
(checked against a rule), `maxItems` bounds damage but not correctness, and an LLM's
self-reported confidence is **weak** — uncalibrated, and least reliable on exactly the atypical
cases. Tiebreaker only, never sole criterion.

No global "trust the AI" setting: that is a global answer to a per-case question, ticked once
and silently covering every future run. The predicate lives on the node, in the file, versioned
and reviewable.

## Scope

- [ ] `AiTransform` command; model per node from `AiProviderRegistry`.
- [ ] Item batching inside the node (10–20 per call, re-joined); returned-id validation.
- [ ] Provenance per item ("AI decided, confidence, why") on the card and into project memory (#80).
- [ ] Approval node: filter semantics, `autoAccept` predicate, pause/resume across a Revit restart.
- [ ] **Three levels deciding whether `autoAccept` is honoured**: `Destructive` → off by default;
      a node may opt in explicitly; a short list refuses it outright — `DeleteFamilyElements`,
      `PurgeFamilies`, `PurgeFamilyTypes`, `ExecuteRevitCode`. Level 3 is an **inverted
      allowlist**: only commands the host knows to be reversible may be loosened, so every
      unknown and every third-party command stays a barrier. No new SDK property, same reasoning
      that deferred `RequiresUser`. (Depends on the `Destructive` repair done in #88 — the flag
      was previously missing on exactly the irreversible commands.)
- [ ] Graph validation enforcing the invariant.
- [ ] Run-level `dryRun`: AI nodes execute for real, `Destructive` nodes report what they would
      do. Trust earned by observation rather than declared by checkbox. `SetDataToParameters`
      already has `Overwrite`/`OnlyIfEmpty`/`SkipIfEqual`, so a fourth mode fits naturally.
- [ ] Re-evaluate Microsoft Agent Framework here (deferred from #90).

## #93 — Verify the author publishing path end to end: PackExtension → zip → install

`dotnet build -t:PackExtension` is what an extension author's whole release story rests on

## What CI already covers

More than it looks. The NUKE `TestSdkPackage` target packs the SDK, builds `samples/Acme.Sample`

The interesting half. `Build.Ci.cs` asserts a zip **exists** — not what is in it:

- [ ] **Layout.** `plugin.json` and `ui/` at the root, per-year binaries in `2025/`, `2026/`,

- [ ] **`updateFeed: github:owner/repo` → `CheckExtensionUpdates`** on a real release, since that is

## #95 — Freeze the Launcher: move the host contract into bootstrap.json

state: open | labels: enhancement | created: 2026-08-08 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/95

`AnalyseTool.Launcher.dll` is the one file Revit holds open for the entire session — it is named in the `.addin`, so it can never be replaced while Revit runs, and updating it always means a reinstall. Everything else can, in principle, be swapped underneath it.

Today the Launcher is not a shim: it hardcodes the host's assembly name, type names, method names and dependency list, and it stamps itself with `PLUGIN_VERSION`. So the one file that *cannot* be updated is also the file most likely to *need* updating. This issue makes the Launcher a frozen, generic bootstrapper and moves every host-specific detail into a data file the host owns.

This is the prerequisite for side-by-side host versions and background updates (follow-up, out of scope here) — but it stands on its own: it removes the "rename a type, break the installed base" trap that `CLAUDE.md` currently warns about.

## What couples the Launcher to the host today

All from `src/AnalyseTool.Launcher/`:

1. **Host assembly name and location** — `App.LoadIsolatedDlls` builds `Path.Combine(pluginFolder, "AnalyseTool.App.dll")` from its own folder. The host must be named that and sit next to the Launcher.
2. **Entry type and method names** — `RibbonHostType = "AnalyseTool.App.Common.Extensions.RibbonHost"` plus a simple-name fallback, and the method strings `"Build"`, `"OpenFamilyControl"`, `"ShowFamilyPalette"`, `"OpenSettings"`, `"Reload"` spread across `App.cs` and `RevitCommands/SystemCommands.cs`. `AnalyseToolCommand` separately resolves `"AnalyseTool.App.AnalyseToolCommand"`.
3. **The set of ribbon buttons is frozen by the number of slot classes.** Revit needs a type it can load from the Launcher DLL for every `PushButtonData`. `RibbonHost` names six of them (`MainCommandClass` … `BugsCommandClass`). A seventh host-level button needs a seventh class in the Launcher — i.e. a reinstall. (Extension buttons are unaffected: `RefreshExtensionButtons` uses AdWindows and needs no slot at all.)
4. **The dependency graph is frozen too, and this one is easy to miss.** `new AssemblyDependencyResolver(typeof(App).Assembly.Location)` resolves through `AnalyseTool.Launcher.deps.json`. A host build that adds a NuGet dependency cannot resolve it, even with the DLL sitting in the folder. The hardcoded `dependencies = new[] { "Newtonsoft.Json.dll" }` preload is the manual patch over the same problem.
5. **The Launcher versions itself as the plugin.** `AssemblyInfo.cs` stamps `AssemblyVersion(ToolData.PLUGIN_VERSION)`. "Frozen" and "re-versioned every release" cannot both be true.
6. **`BugsCommand` bakes in `ToolData.LINK_TO_GITHUB`.** Frozen Launcher, frozen URL.

## The contract after the change

Exactly three things stay fixed forever. Everything else becomes data.

| Fixed | Value |
| --- | --- |
| `.addin` entry point | `AnalyseTool.Launcher.App`, `AddInId 8F8F151B-…` — already fixed, keep it |
| Ribbon slot types | `AnalyseTool.Launcher.Slots.Slot00` … `Slot15` — generic, never renamed |
| Host entry surface | three static methods, below |

```csharp
// on the type named by bootstrap.json "entryType"
static void Build(UIControlledApplication app, string bootContextJson);
static int  InvokeSlot(int slot, object commandData);   // returns (int)Result
static void Shutdown();                                  // optional; called from OnShutdown
```

The second parameter of `Build` is **a JSON string, not a path** — that is what makes the signature permanent. New facts can be handed to the host forever without touching the Launcher:

```jsonc
{
  "schema": 1,
  "launcherVersion": "1.0.0",
  "launcherPath": "C:\\...\\AnalyseTool\\AnalyseTool.Launcher.dll",
  "hostRoot": "C:\\...\\AnalyseTool",
  "slotTypePattern": "AnalyseTool.Launcher.Slots.Slot{0:00}",
  "slotCount": 16,
  "revitYear": "2025"
}
```

`Shutdown()` is in the frozen surface from day one on purpose: adding it later would need a Launcher change, which is the exact thing this issue exists to prevent.

**Back-compat comes for free.** Today's installed Launcher calls `Build(app, launcherPath)` — same arity, same parameter type. The host sniffs the first character: `{` means a v1 boot context, anything else is a legacy path. On the legacy path it builds the ribbon with the six named command classes; on the v1 path it uses slots. Old Launcher + new host keeps working, and the six named classes stay as deprecated aliases until the installed base has rolled over.

## bootstrap.json

Ships in the host folder, written by the build, owned by the host:

```jsonc
{
  "schema": 1,
  "version": "1.4.6.0",
  "entryAssembly": "AnalyseTool.App.dll",
  "entryType": "AnalyseTool.App.Common.Extensions.RibbonHost",
  "probePaths": ["."],
  "preload": [],
  "requires": { "minLauncherSchema": 1 }
}
```

| Field | Meaning |
| --- | --- |
| `schema` | Contract version. The Launcher refuses a schema it does not know and falls back (see below). Additive changes keep the number. |
| `version` | Host version — logged, shown in Settings, used by a future updater. The Launcher only reports it. |
| `entryAssembly` | Assembly to load into the isolated context. |
| `entryType` | Type carrying the three static methods. No simple-name fallback any more: the name is data now, so a rename is a one-line edit in a file the host ships, not a guess. |
| `probePaths` | Folders (relative to the host root) searched for dependencies when the resolver comes up empty. Replaces the hardcoded preload list. |
| `preload` | Escape hatch for assemblies that must exist in the context before the entry assembly binds. Should be empty once probing works. |
| `requires.minLauncherSchema` | Host build refusing to run on an older shim, with a clear message instead of a `MissingMethodException`. |

### Resolution order

1. `current.json` next to the Launcher, if present, pointing at a host root elsewhere (the side-by-side layout — the file is not written by anything yet, but the Launcher supports it from day one so the follow-up needs no shim change).
2. `bootstrap.json` next to the Launcher — the normal case.
3. Hardcoded legacy defaults (`AnalyseTool.App.dll` + `AnalyseTool.App.Common.Extensions.RibbonHost` + `Build`) so a deployment predating this change still boots.

### Safe mode

Once a pointer can select a host version, a bad host means Revit starts with no plugin and no explanation. Cheap guard: write a marker file naming the version about to be loaded, delete it after `Build` returns. Finding the marker for the same version at startup means that version took Revit down last time — fall back one step down the resolution order and say so once in a `TaskDialog`.

## Gotchas found while reading the code

- **`PathProvider.RootDirectory` is derived from `typeof(PathProvider).Assembly.Location`.** It breaks (empty string) under byte-loading and is simply wrong once the host lives in a version folder. It must be set from the boot context instead. Consumers: `McpServerController` (path to `mcp\AnalyseTool.Mcp.exe`), `ClientAppHost` (WebView2 virtual host mapping), `GetChangelog`, `CreateExtensionTemplate` (path to `AnalyseTool.Sdk.dll`).
- **Byte-loading the host** (`LoadFromStream`, as `ExtensionLoadContext` already does) would unlock the host DLLs and make Debug redeploy work with Revit open. Worth doing, but only after the `RootDirectory` item above — that is what currently blocks it.
- **The isolated context stays non-collectible.** Nothing here needs unload; hot-swapping the live host is a separate, much larger question (Revit builds the ribbon and registers dockable panes at startup only).
- **The shim is still built per Revit year** — `net8.0-windows` for R25/R26, `net10.0-windows` for R27. Frozen means one unchanging *source*, not one binary for all years.
- **`Report a bug` in the Launcher** exists so it works when the host fails to load, which is a good reason to keep it — but its URL then freezes with the shim. Move the normal-path button into the host and leave the Launcher one as the failure-path fallback.

## Proposed work

- [ ] Give the Launcher its own version constant, decoupled from `ToolData.PLUGIN_VERSION`.
- [ ] Define `bootstrap.json` schema v1; emit it from the build into the host folder.
- [ ] Read it in `App.LoadIsolatedDlls` with the three-step resolution and the legacy defaults.
- [ ] Switch the entry call to `Build(app, bootContextJson)` with the `{`-sniff; add `Shutdown()` and wire `OnShutdown`.
- [ ] Add `Slots.Slot00`…`Slot15` + `InvokeSlot` routing; keep the six named classes as deprecated aliases; teach `RibbonHost` to pick slots when the boot context is v1.
- [ ] Build the `AssemblyDependencyResolver` from the host entry assembly, with `probePaths` folder probing as the fallback.
- [ ] Replace `PathProvider.RootDirectory` with a value handed in through the boot context.
- [ ] Boot marker + safe-mode fallback.
- [ ] Drop the "update the FQN strings in `Launcher/App.cs` when renaming `RibbonHost`" note from `CLAUDE.md` — it stops being true.

**Verify:** R25 (net8) and R27 (net10) builds; old Launcher + new host; new Launcher + host folder with no `bootstrap.json`; malformed `bootstrap.json`; host that throws in `Build`.

## Out of scope

Side-by-side version folders and the `current.json` writer, the background updater, package signing, and organisation-controlled version policy. This issue only makes them possible without ever touching the installed shim again.

Related: #87 (supply chain — signature verification becomes a hard requirement once anything downloads a host build).

## #97 — MCP: a failing command's real error never reaches anyone — only ex.Message, no inner exception, nothing logged

state: open | labels: bug | created: 2026-08-13 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/97

Found while field-testing the 1.5 MCP server (#96) in a live Revit session.

Every failing command looks the same from the agent's side. One command failed on every input for an entire session, and the caller got nothing to act on — no message, no stack, no `didYouMean`, even though that command's declared output type has fields for exactly those.

## Cause

`src/AnalyseTool.Mcp.Bridge/McpBridgeServer.cs:276`

```csharp
catch (Exception ex)
{
    return Err(id, McpWire.Codes.CommandFailed, ex.Message);
}
```

Two defects in one line:

- **`ex.Message` and nothing else.** A command's exception reaches this catch after being marshalled off the Revit thread, so the outer exception is routinely a wrapper: `AggregateException` gives "One or more errors occurred.", `TargetInvocationException` gives "Exception has been thrown by the target of an invocation.". The sentence that says what actually broke lives in `InnerException` and is thrown away here.
- **Nothing is logged.** The exception is turned into a wire error and dropped. It does not reach Serilog either, so after this line the information does not exist anywhere — including on the machine where it happened.

Worth stating plainly, because it misled the first triage: the `Tool execution failed` text the agent saw is its own client's wrapper, not ours. Nobody currently knows what the bridge actually sent. That is the bug.

## Fix

- Walk the `InnerException` chain and report the innermost message, or join the chain.
- `Log.Error(ex, "MCP command {Command} failed", command)` before returning, with the arguments. A failure an agent hits against someone's real model is not reproducible afterwards without this.
- Consider putting the exception type name in `hint`, so an agent can tell "I sent bad input" from "the plugin broke" and stop retrying in the second case.

## Why this one first

It is cheap, and it is what makes every other MCP bug diagnosable. Right now isolating one costs a whole Revit session, which is how a completely broken read command reached a release candidate unnoticed.

## #99 — MCP: a long command outlives the call, and its result is lost for good

state: open | labels: bug | created: 2026-08-13 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/99

Found while field-testing the 1.5 MCP server (#96) in a live Revit session.

## What happened

A run over 54 rooms took roughly ten minutes. The MCP call dropped at about four. Revit carried on and finished the work correctly — but the answer, a report of sheet scales and a list of overflowing rooms, was gone. There is no way to ask for it. Recovering the state took a second, separate query against the model.

## The part that is ours

Note the numbers: `RevitBridgeClient.InvokeAsync` is bounded at **10 minutes** (0f144d9, #88), and the call died at **four**. So the timeout that actually bound here was the AI client's, not ours — and that is exactly why raising our ceiling would fix nothing. We do not control the caller's patience, so the design has to survive the caller giving up.

Today it does not. A command's result exists only as the return value of the call that is no longer there.

`GetQueueStatus` is not the answer either: it reports that something is still running, and has nothing to say about a command that has finished. So the agent knows to stop resending — which did work, and prevented a duplicate run — but still cannot obtain the result.

## Options

Both are worth having; the first is the one that fixes the data loss.

- **A job id and a way to collect it.** `tools/call` returns an id immediately for long work; the result is kept for some window and fetched by id. This survives a dropped connection, a restarted client, and a user who closed the chat.
- **Progress out to MCP.** `IProgressAware` already exists and the WebView transport already binds a progress sink per request — the MCP transport does not. A caller receiving progress does not read a long silence as a hang, which is what made the client give up at four minutes in the first place.

## Why it matters more than it looks

The commands worth automating are the slow ones. A tool that silently loses the answer to anything taking more than a few minutes is a tool that cannot be trusted with the work it was built for — and worse, the model was already modified by then, so a retry is not free.

## #103 — RemoveDevExtension leaves undeletable `.old` folders behind on synced/shared paths

state: open | labels: bug | created: 2026-08-13 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/103

Found in the plugin log of a 1.5.0 session. Happened three times, always on a OneDrive-synced folder.

```
22:34:07.153 [WRN] Could not fully delete
  C:\Users\…\OneDrive - …\DBA Tools Distribution\…\Austausch\niko.sheet-creator.old;
  leftover is ignored by the scanner
System.IO.IOException: Access to the path '\\?\C:\Users\…\niko.sheet-creator.old' is denied.
   at System.IO.FileSystem.RemoveDirectoryRecursive(…)
   at AnalyseTool.Core.Features.Extensions.RemoveDevExtension.TryDelete(String directory)
```

## What happens

`RemoveDevExtension` parks the folder as `<id>.old` and then deletes it. The park succeeds; the delete does not, because a sync client (OneDrive here) still holds a handle. The failure is caught, warned, and the scanner ignores the leftover — so nothing breaks, and the user is told the extension was removed, which is true.

The cost is that **the shared folder slowly fills with `.old` directories** nobody will ever clean up. That is worse than it sounds for this release specifically: a shared team folder as an extension source is one of 1.5's headline scenarios, so the litter lands where colleagues see it.

## Options

- **Retry briefly.** A sync client's handle is usually transient; two or three attempts a second apart would clear most of these. Cheap, and it fixes the common case rather than describing it.
- **Sweep on the next scan.** The scanner already recognises and skips `*.old` — while it is there it could attempt a delete, so a folder that was locked at removal time disappears the next time Revit starts.
- **Do not park where you cannot delete.** Detect the failure and warn the user with the path, so at least the person who created the mess knows it exists. Weakest option; leaves the work to them.

The first two compose well: retry now, sweep later.

## #106 — Dry-run + confirmToken for destructive commands: show what will change before it changes

state: open | labels: enhancement | created: 2026-08-14 | comments: 1
https://github.com/Nikola1Davydov/AnalyzeTool/issues/106

**Platform debt, and the cheapest safety win available.** Independent of the MCP UI work — it needs no new protocol, no resources in the bridge, no SDK change to start.

## What stands between "delete" and deleted, today

Two surfaces, and neither has any content.

- **In the dock**, the confirmation reads literally: *"`niko.x.DeleteY` modifies the model"* plus the command's description (`ScriptLauncherView.vue:513`).
- **Over MCP**, `Destructive = true` becomes the `destructiveHint` annotation — something the client *may* act on (`RevitCommandAttribute.cs:37`).

Neither says **what** will change. That is worse than nothing: a confirmation with no content trains the reflex click, and then keeps producing the feeling of a safeguard after it has stopped being one.

#88 fixed the other half of this — warnings are now recorded instead of swallowed — but that is a report *afterwards*. This is the same question asked *before*.

## What it buys

**The confirmation becomes a decision again.** "47 families, 3 of them used in a linked model" is something a person reads. "This command modifies the model" is not.

**The check moves to where it is nearly free.** For `PurgeFamilies` the expensive half is finding the unused families; the delete is cheap. A preview there is one extra read pass, not double the work.

**The agent gets something to reason about.** This is the larger half, and it only exists over MCP. Today the loop is: call the destructive tool, read the result, hope. With a preview the agent can compare the diff against what the person actually asked for — *"you asked to purge unused families, but three of these 47 are placed in a linked model, exclude them?"* — a conversation that cannot happen now.

It also catches **bugs in the command itself**. #98 is the archetype: `GetElements` answered with the wrong elements and looked completely fine. The same class of bug in a writing command is invisible until the damage is done; a preview is the only place it surfaces first.

**Why undo is not the answer.** It is per-session and per-document, it does not survive a sync in a workshared model, and it is worthless when nobody is watching — which is precisely the unattended-agent case 1.5 opens up. And with one command = one transaction, five commands from one button are five separate Ctrl+Z with no indication of how many.

## Why a token, and not just "call it twice"

Three distinct jobs, and only the token does all three:

1. **It binds the confirmation to the change set that was actually computed.** If the model moves between preview and commit — a colleague synced, the agent placed something — the token is stale and the commit refuses. Without one, "yes, delete those 47" can delete 51.
2. **The commit path requires a token that only a preview can mint.** So the step cannot be skipped. This is the real difference from `destructiveHint`: a hint is a request to be polite that the client may ignore, a required token is enforced server-side. Same shape as the C#-execution switch, and for the same reason.
3. **It makes the log legible** — preview → token → commit, matchable after the fact. There is nothing there today.

## Cost, honestly

- Every writing command needs "what would change" computed separately from "do it". Trivial for some (delete N ids), most of the work for others, and **genuinely awkward** for a few: `LoadLibraryFamilies` cannot know the outcome without loading, `PlaceFamilyInstance` blocks on a human click. It will not be uniform, and trying to make it uniform across all destructive commands is how this stalls.
- A short-lived cache: token → change set + a document/version stamp. Small, but it is state, and Core is headless, so it needs a home.
- If extensions are meant to support it, it becomes an SDK contract — a 1.3 decision, not part of this.

## Scope

**Not "all destructive commands."** Four or five where the preview is nearly free and the damage is worst: the Family Manager deletes and purges.

Start with the worst rather than the easiest — if the shape does not survive `PurgeFamilies`, it will not survive anything. Prove out what a diff looks like, where the token lives, and what happens when it goes stale. **Then** decide whether it belongs in the SDK.

## Related

- #88 — collected warnings; the "after" half of the same story.
- #98 — a read command that answered wrongly and looked fine; the failure mode this protects writes from.
- #92 — approval as a graph invariant; a token is the per-command version of the same idea.

## #107 — MCP 2026-07-28: what the new spec changes for us — and whether the SDK supports it yet

state: open | labels: enhancement | created: 2026-08-14 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/107

Tracking issue. The `2026-07-28` MCP specification is the largest revision since MCP launched, and
it lands on several things already in this backlog — two planned items are now deprecated, one gets a
much cheaper answer, and one capability we needed but had no name for now exists.

## Source, and what it is worth

Everything below comes from Microsoft's
[mcp-for-beginners, ch. 1.1](https://github.com/microsoft/mcp-for-beginners/blob/main/01-CoreConcepts/mcp-2026-07-28-release-candidate.md),
which summarises the six SEPs. **Caveat:** that chapter was written against the *release candidate*
(locked 2026-05-21, spec scheduled to ship 2026-07-28), and `modelcontextprotocol.io` was not
reachable from the authoring environment, so **none of this is verified against the final spec.**
Verify before building. Primary sources to check:
[draft spec](https://modelcontextprotocol.io/specification/draft) ·
[changelog](https://modelcontextprotocol.io/specification/draft/changelog) ·
[release blog post](https://blog.modelcontextprotocol.io/posts/2026-07-28-release-candidate/).

## The gating question

- [ ] **Does `ModelContextProtocol` 1.3.0 support `2026-07-28`?**
      (pinned in `src/Directory.Packages.props:42`)

Nothing else here can start until this is answered. Tier-1 SDKs were expected to ship support inside
the ten-week RC window, but 1.3.0 may predate it. If it does not, the first task is the SDK bump,
and everything below waits.

## What changes for us

| Change | Effect here |
| --- | --- |
| **Sampling deprecated** — use the LLM provider API directly | Do not build it. We already have `Tools/Ai/` and `Microsoft.Extensions.AI`, which *is* the recommended path. |
| **Logging notifications deprecated** — use `stderr` for stdio, OpenTelemetry for structured | Already done the recommended way: `AnalyseTool.Mcp/Program.cs:18,107` write to stderr with a comment explaining why not stdout. Nothing to build. |
| **Roots deprecated** — use tool parameters / resource URIs | We never used them. |
| **`ttlMs` + `cacheScope` on `tools/list`** (SEP-2549) | Cheaper fix for #100 than a push channel — see the comment there. Also strengthens #84 P2. |
| **Tasks extension** — `tools/call` answers with a task handle, client drives `tasks/get`/`update`/`cancel` | #110 — the answer to #99, #102 and the 10-minute timeout workaround in #88. |
| **`structuredContent` may be any JSON value**, not only an object (full JSON Schema 2020-12, SEP-2106) | #111 — retires the array-rooted limitation documented in `Program.cs:230-253`, unblocks part of #89. |
| **Elicitation restructured** — `InputRequiredResult` + `requestState`, re-issued call instead of a held stream | The official mechanism for #106 — see the comment there. |
| **MCP Apps is now a formal extension** (SEP-1865) | Relevant to #71. UI templates are declared *ahead of time* so hosts can prefetch, cache and security-review them — a materially different threat model from generating HTML at call time. |
| **Stateless core** — `initialize` handshake and `Mcp-Session-Id` removed | Little direct effect: we are stdio against a single local Revit, and the SDK owns the handshake. |
| **Missing-resource error code `-32002` → `-32602`** | No effect: our wire uses its own string codes (`McpWire.Codes`) and we do not serve resources yet. |

## The direction of travel

Worth recording, because it argues against a design this backlog was drifting toward: the spec is
moving **away** from long-lived streams and server-initiated push, and **toward** self-contained
requests, explicit handles, and cache-freshness hints. Server-initiated requests are now allowed
*only while the server is actively processing a client request* (SEP-2260) — a user can never be
prompted out of nowhere.

So "build an unsolicited push channel through the bridge first" is the wrong opening move. Every
capability we actually want — progress, long operations, confirmation prompts, a fresh tool list —
has a request/response-shaped answer in this spec.

## Children, in order

1. **The gating question above** — answer first
2. #108 — progress. Unaffected by any of this, cheapest, already half-built
3. #109 — cancellation. Token already threaded end to end
4. #110 — Tasks, for long-running commands
5. #84 P2 — resources, read-only first (see the comment there)
6. #100 — `ttlMs` instead of a push channel (see the comment there)
7. #106 — dry-run, in the new elicitation shape (see the comment there)

Filed alongside but not on this path: #111 (deletes code, can go any time once the SDK question is
settled) and #112 (rate limiting — the one gap against the official security checklist).

## #108 — MCP: report progress — the sink exists on both ends, only the wire hop is missing

state: open | labels: enhancement | created: 2026-08-14 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/108

Part of #107. The cheapest item on the MCP roadmap, and the only one untouched by the `2026-07-28`
changes — progress notifications stay, and "Progress Tracking" is on the official best-practice list.

## Why it is cheap

Both ends already exist. What is missing is the hop between them.

- `IRevitTask` commands can already report progress — `IProgressAware` has been in the SDK since 1.1.
- `CommandRequest.Progress` (`IProgress<ProgressInfo>?`) is already on the request envelope —
  `Core/Common/Dispatch/CommandQueue.cs:21` — and its comment already says it is "bound by the
  transport to the originating caller (window, request id)".
- `CommandQueue.ExecuteAsync` already forwards it into `DispatchAsync` — `CommandQueue.cs:116`.
- `WebView2Transport` already binds a sink, so progress works today *in the UI*.

The MCP transport binds nothing. `CommandRequest.Progress` is left null on every call arriving from
the bridge, so a Revit command that reports progress reports it into the void.

## What is actually missing

`McpWire` has exactly two request types — `invoke` and `list` (`McpWire.cs:40-41`) — and the
envelope is strict request/response keyed by `id`. There is no shape for "here is an interim update
about a call still in flight".

So this needs:

- [ ] A progress frame on the wire, correlated by the existing `id`
- [ ] The bridge binding a `CommandRequest.Progress` sink that writes those frames
- [ ] `AnalyseTool.Mcp` translating them into MCP progress notifications
  (the SDK owns the MCP-side format)

## Why it matters beyond the feature

Right now a long command is indistinguishable from a hung one — see #102 and #104, where exactly
that ambiguity cost the time. An agent that can see movement does not retry, does not give up, and
does not pile a second call onto a busy Revit.

It is also the smallest possible version of "the bridge says something the client did not ask for
about a call in flight" — worth building first for that reason alone, since Tasks (#107) needs the
same correlation discipline.

## #109 — MCP: no way to cancel an in-flight call, though the CancellationToken is already threaded end to end

state: open | labels: enhancement | created: 2026-08-14 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/109

Part of #107. On the official MCP best-practice list next to progress: *"Allow clients to cancel
in-flight requests that are no longer needed or taking too long."*

## The plumbing is already there

- `CommandRequest.CancellationToken` is on the envelope — `Core/Common/Dispatch/CommandQueue.cs:18`
- `CommandQueue.ExecuteAsync` passes it into `DispatchAsync` — `CommandQueue.cs:116`
- `IRevitTask.ExecuteAsync(IRevitContext ctx, CancellationToken ct)` — every command already receives it
- `McpWire.Codes.Cancelled` already exists and is already documented as "the call was cancelled — by
  the caller or by shutdown"

So the token reaches every command, and the error code for the outcome is already minted. What has
no path is the *request* to cancel: `McpWire` has two verbs, `invoke` and `list`
(`McpWire.cs:40-41`), and neither of them is "stop the call with this id".

## What to do

- [ ] A `cancel` request type on the wire, carrying the `id` of the call to stop
- [ ] The bridge holding the `CancellationTokenSource` per in-flight id and cancelling it
- [ ] `AnalyseTool.Mcp` wiring MCP's cancellation to it (the SDK owns the client-facing side)
- [ ] Confirm the result comes back as `Codes.Cancelled`, not `Codes.CommandFailed` — the distinction
      already exists in the code and should survive the round trip

## Why it is worth doing early

Today the only way out of a call into a stuck Revit is the 10-minute `InvokeAsync` timeout added in
#88 — deliberately generous, because a timeout that fires on legitimate work is worse than none.
That trade only exists because there is no cancel. With one, the timeout stops being the sole escape
hatch, and the agent gets a way to abandon work it no longer wants without waiting out the bound.

Pairs naturally with the progress work: same correlation by `id`, same in-flight bookkeeping.

## #110 — MCP Tasks: a long Revit command should return a handle, not hold the call open for ten minutes

state: open | labels: enhancement | created: 2026-08-14 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/110

Part of #107. This is the capability we have been working around for three separate issues without
having a name for it.

## The workaround we have now

A Revit command that takes minutes currently has exactly two outcomes over MCP, and both are bad:

- the MCP call sits open until it finishes, holding the agent (and, per #102, the whole WebView UI);
- or `RevitBridgeClient.InvokeAsync` gives up at its 10-minute bound (#88) and the result is **lost
  for good** — that is #99, verbatim.

The 10-minute bound was chosen in #88 as the least-bad number, with the reasoning written down at
the time: *"generous on purpose: real work takes minutes, and a timeout that fires on legitimate
work is worse than none."* That is a workaround for a missing protocol feature, and it now has a
real replacement.

## What the spec offers

Per [ch. 1.1](https://github.com/microsoft/mcp-for-beginners/blob/main/01-CoreConcepts/mcp-2026-07-28-release-candidate.md),
Tasks graduates from an experimental `2025-11-25` core feature to a first-class **extension** in
`2026-07-28`, reshaped around the stateless model:

- the server may answer a `tools/call` with a **task handle** instead of a result;
- the client drives it with `tasks/get`, `tasks/update`, `tasks/cancel`;
- task creation is **server-directed** — the client advertises the extension, the server decides
  which calls run as tasks;
- `tasks/list` was removed entirely (it cannot be scoped safely without sessions).

The important property for us: **this is all request/response.** No unsolicited push, no held
stream, nothing the bridge's envelope cannot express with one more verb.

## What it would fix

- **#99** — a long command outliving the call stops losing its result; the handle survives it.
- **#102** — the MCP side stops being the thing that holds a call open while the UI is frozen.
- **#104** — the 4-minute `GetCategoriesInRevit` hang becomes a visible running task rather than an
  indistinguishable stall. (Not a fix for the hang itself — that stays open.)
- **#88's remaining item** — "a server-side early return when `RevitAvailability.IsRevitBusy`, so a
  blocked Revit answers immediately instead of consuming the client's 10 minutes" is close to
  exactly what a task handle *is*.

## Open questions before building

- [ ] Does `ModelContextProtocol` 1.3.0 implement the Tasks extension? (the #107 gate)
- [ ] Client support — an extension is negotiated, so a client that does not advertise it gets the
      old blocking behaviour. Which of our target clients advertise it?
- [ ] Which commands should be server-directed into tasks? A duration threshold, or an explicit
      opt-in on `[RevitCommand]`? Note `PlaceFamilyInstance` already blocks on a user click, and
      `ExecuteRevitCode` is unbounded by construction.
- [ ] Where does the result live between completion and `tasks/get`? Today nothing outlives the call.

**Migration note from the spec:** the experimental `2025-11-25` Tasks API is *not* backward
compatible with this extension. We never implemented the experimental one, so this costs us nothing
— worth recording so nobody starts from the older examples.

⚠️ Unverified against the final spec — see the caveat in #107.

## #111 — structuredContent: the array-rooted restriction is gone in 2026-07-28 — GetElements can finally declare its output

state: open | labels: enhancement | created: 2026-08-14 | comments: 1
https://github.com/Nikola1Davydov/AnalyzeTool/issues/111

Part of #107, and the immediate follow-up to #89.

## The constraint we documented

`AnalyseTool.Mcp/Program.cs:230-253` carries a long comment explaining why some commands can never
advertise an `outputSchema`, and the third reason is the binding one:

> **an array-rooted schema** — several commands legitimately return a JSON array (GetElements,
> GetCategoriesInRevit…), and structuredContent is defined as an OBJECT, so such a tool cannot
> honour the promise no matter what. Its shape stays in the description and in the text block.
> Making those commands wrap their answer in `{ items: [...] }` would fix it, at the cost of a
> breaking change for the frontend that reads them — a separate decision, not one to smuggle in here.

That was the right call at the time, and the trade it describes was real: honour the schema promise,
or keep the frontend working. Pick one.

## The constraint is lifted

Per [ch. 1.1](https://github.com/microsoft/mcp-for-beginners/blob/main/01-CoreConcepts/mcp-2026-07-28-release-candidate.md),
SEP-2106 lifts tool schemas to full JSON Schema 2020-12:

- input schemas keep the `type: "object"` root constraint, but gain composition (`oneOf`, `anyOf`,
  `allOf`), conditionals and references (`$ref`, `$defs`);
- **output schemas are unrestricted, and `structuredContent` can now be any JSON value rather than
  only an object.**

So the choice above disappears. No wrapper, no frontend break, and the array-returning commands can
declare what they return like everything else.

## Work

- [ ] Drop the array-rooted case from `DeclaresObjectResult` (`Program.cs:248-253`) — and rename it,
      since it will no longer be about objects
- [ ] Rewrite the comment at `Program.cs:230-253`: two of its three refusals still stand (a command
      that declared nothing, and the free-form fallback the bridge substitutes for an oversized
      schema), the third becomes history
- [ ] Relax the matching assumption at `Program.cs:91-93` and `:139-140`, where `StructuredContent`
      is set only `if (... result is JsonObject resultObject)`
- [ ] Re-check which commands can now declare `OutputType` — this unblocks part of #89

## Two other things worth folding in while in this file

- Input schemas gaining `$ref`/`$defs` may matter for the schema-size cap the bridge enforces: a
  nested type currently inlines, and `$defs` would let it be emitted once. Worth measuring before
  assuming it helps.
- The spec warns that implementations must not auto-dereference external `$ref` URIs, and should
  bound schema depth and validation time — a DoS consideration. `PayloadValidator` validates
  server-side, so that warning is addressed at us.

⚠️ Unverified against the final spec, and gated on the SDK question in #107. But unlike the rest of
that tracking issue, this one deletes code rather than adding it.

## #112 — MCP bridge has no rate limiting — the one item on the official security checklist with nothing behind it

state: open | labels: enhancement | created: 2026-08-14 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/112

Part of #107, and the only gap found when checking the bridge against the official MCP security
best-practice list.

## We pass the rest of the list

Measured against the seven security items in
[mcp-for-beginners ch. 08](https://github.com/microsoft/mcp-for-beginners/blob/main/08-BestPractices/README.md):

| Item | Where |
| --- | --- |
| Authentication | Session token on every request, generated by the host, stored in a user-only `mcp.json` (`McpWire.cs:21-24`) |
| Parameter validation | `PayloadValidator` checks the payload against the command's published `inputSchema` before dispatch |
| Tool permission control | `HiddenFromMcp` + `McpBridgeServer.IsAvailableToAi` — the bridge, not the exe, is the access boundary |
| User consent and control | The C#-execution switch is human-only by design: `SetCodeExecution` is `HiddenFromMcp`, so the AI can never grant itself code execution |
| Tool safety / explicit consent per invocation | Partially — the seam exists (`CommandRequest.Gate`, whose comment already reserves it for "a user-consent step later"), and #106 is the work |
| Data privacy | Localhost-bound, single user, no egress |
| **Rate limiting** | **Nothing.** |

## The gap

`grep -ri "ratelimit\|throttl\|SemaphoreSlim\|MaxConcurrent"` over `AnalyseTool.Mcp.Bridge/` and
`AnalyseTool.Mcp/` returns nothing. The only bound of any kind on the bridge is a message size cap
(`McpBridgeServer.cs:372`, `ms.Length > MaxMessageBytes`).

So an authenticated caller can dispatch commands as fast as it can open sockets, and each one lands
on `CommandQueue`, which — by its own class comment — *"is not yet a scheduling queue: requests
execute immediately and may overlap."* The serialisation that does exist is the `RevitTaskHub`
external event, i.e. contention on the Revit thread itself, which is the worst possible place to
absorb a flood.

## How much this actually matters

Honestly: less than for a public server. The bridge binds `127.0.0.1` and demands a token, so this
is not reachable from the network or the browser. The realistic trigger is not an attacker but **an
agent in a retry loop** — which is not hypothetical here: #98 had `GetElements` failing on every
input, and #97 made every failure look identical, which is exactly the setup that produces a hot
retry loop against a Revit thread that has real work to do.

That is the reason to file it rather than to build it today: the threat is a buggy client, not a
malicious one, and the fix belongs in the same place the consent gate does.

## Where it goes

`CommandQueue` is the natural home — its class comment already says the funnel exists so
*"scheduling, priorities, consent gates and per-source policy can be added in ONE place without
touching any transport."* Per-source is the right axis: `webview2` should not be throttled the way
`mcp` is.

- [ ] Decide the shape: per-source concurrency cap, or a rate over time
- [ ] Do not throttle `GetQueueStatus` — it is already in `CommandQueue.Untracked` for the same
      family of reasons, and a status poll must keep answering while everything else is backed up
- [ ] Return a distinct wire code so a client can back off deliberately rather than guessing
      (`McpWire.Codes` is a closed set on purpose — this would be a deliberate addition)

## #113 — Answers drop identifiers they already hold: builtInCategory, levelId, parameter units

state: open | labels: enhancement | created: 2026-08-14 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/113

How to make an agent understand a Revit model better, without spending context on it.

## The principle

There are three tiers of knowledge here, and they want different mechanisms:

1. **Universal / static** — the `BuiltInCategory` enum, the API object model. Hundreds of entries, of
   which a session needs a handful. **This must never be shipped as context.**
2. **Per install** — the localised-name ↔ `BuiltInCategory` mapping, language, Revit version. Small,
   stable, currently re-derived by tool call every session. The real candidate for a cached resource
   (#84 P2).
3. **Per document** — levels, category counts, active view. Small, changes constantly.
   `GetModelOverview` already covers it.

The point that makes this tractable: **tier 1 is only useful projected through tier 3.** The full
category table is useless as context; the ~30 categories that exist *in this model*, annotated with
their language-independent ids, is exactly right and costs almost nothing.

So the rule is **fold the static identifier into the dynamic answer** rather than shipping it
separately. Everything below is an instance of the same omission: an answer discards an identifier
it was already holding, and the agent is left to infer it.

Note that none of this waits on resources, the wire verbs, or #107 — these are fields on answers
that are already being sent.

---

## 1. `builtInCategory` — the strongest case

`GetModelOverview` returns `categoryCounts` as `Dictionary<string, int>`: *localised name → count*.
The agent receives `{"Wände": 8}`.

The `BuiltInCategory` is in the same loop. It is used one line further down for `hasTopography`
(`GetModelOverview.cs:57-59`) under a comment that states the reason precisely:

> Asked of the CATEGORY, not of the counted name: the name is localised, the built-in category is not

— and then discarded.

Meanwhile `GetElements.Request.BuiltInCategory` is documented as *"Preferred over 'category' when
you know it: it means the same thing on every install"*. Nothing in any answer ever tells the agent
what it is. It has to already know that `Wände` is `OST_Walls`, from training. On a German model it
will usually guess right; on a Czech or Japanese one it will not.

- [ ] `categoryCounts` → `{ "Wände": { "builtInCategory": "OST_Walls", "count": 8 } }`
- [ ] `GetCategoriesInRevit` — currently `List<string>` of localised names only, so the same gap
      (also the last bare-array output left; see #111)
- [ ] `ElementSummary.Category` (`ElementSummary.cs:15-16`) — a localised string, no
      `builtInCategory` beside it

Shape change on `categoryCounts` is breaking for whatever reads it in the frontend — worth checking
before picking the shape. An additive parallel map (`categoryBuiltIns`) is uglier but free.

## 2. `levelId` — a join key you already know how to add

This exact problem was found and fixed for families. `ElementSummary.FamilyId` carries a comment
that says what the fix was for:

> this is the join back to GetFamilies, which was impossible before: the two commands described the
> same families and shared no key

`ElementSummary.Level` (`ElementSummary.cs:18-19`) is **a string**, while `LevelInfo`
(`GetModelOverview.cs:138-141`) carries `Id`, `Name` and `Elevation`. So an element can only be tied
to its level by joining on a display name, which is not guaranteed unique — the same class of defect
that was already diagnosed and repaired one field above.

- [ ] Add `levelId` next to `level`, `NullValueHandling.Ignore` like `familyId` (many elements have
      no level, and that absence is itself informative)

"Understanding the structure of the project" is mostly this: answers that interlock by key, so a
chain can be walked without asking again.

## 3. Parameters — localised names, and values without units

Two gaps in one place.

`CategoryParameterInfo` (`ElementSummary.cs:82-95`) carries `name`, `storageType`, `isReadOnly`,
`isType`. **Parameter names are localised too**, exactly like category names, and there is no
`builtInParameter` beside the name. This is the same disease as §1, one level down, and it has not
been noticed yet because the category case is louder.

`ElementSummary.Parameters` is `Dictionary<string, string>`. The agent sees `"Höhe": "2400"`.
Millimetres? Probably, by inference from `displayUnits` in the overview. But `storageType` says
`Double`, not "this is a length", so nothing states it.

- [ ] `builtInParameter` alongside `name` where the parameter is built-in (null for project/shared
      parameters, which is itself worth knowing)
- [ ] The parameter's spec (length / area / angle / plain number) on `CategoryParameterInfo`

For a read this is a nuisance. For `SetDataToParameters` it is the difference between a 2400 mm wall
and a 2400 ft one, and that command writes in bulk — see #88 for what it already does about silent
partial writes.

## 4. What actually belongs in a resource

Tier 2 above: the per-install localised ↔ `BuiltInCategory` table. Stable for the lifetime of an
install, never changes mid-session, and under `2026-07-28` it can carry `cacheScope` so the client
caches it properly (#84 P2, and the comment there).

That one is genuinely blocked on the bridge learning a resource verb. §§1–3 are not.

## 5. Do not guess whether this worked

Everything above is a hypothesis about agent behaviour. #84 P1 is what tests it, and
**"calls per task"** is the metric that answers it — the observation recorded there was *8 calls to
place 2 family instances; 3 would have been enough*. If these changes are right, that number falls.
If it does not move, we added fields and told ourselves a story.

#111 (`GetCategoriesInRevit` is the remaining bare array).

## #115 — MCP в другую сторону: внутренний агент как MCP-клиент, а не только сервер

state: open | labels: enhancement | created: 2026-08-25 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/115

Дополнение к #80 (встроенный агент) и #56 (AI-слой + RAG). Ни там, ни там MCP не рассматривается
в этой роли, а роль дешёвая и снимает целый класс работы.

## Идея

Сейчас MCP у нас — это то, чем мы **являемся**: `AnalyseTool.Mcp.exe` отдаёт наши команды наружу.
Все три варианта хостинга в #80 трактуют MCP так же — как способ, которым нас *ведут* (A) или
которым мы отдаём инструменты чужому циклу (C).

Но встроенный агент из #80 варианта B — сам по себе LLM-цикл с function calling. Значит он может
быть MCP-**клиентом** и потреблять чужие серверы.

Тогда вместо «написать интеграцию с каждой системой» задача становится «уметь быть клиентом»:

- база документов проекта (#56, фазы 3–4) — если сервис извлечения говорит MCP, агент ходит в него
  клиентом, а не через ProjectReference
- CONTACT Elements (в #56 упомянут `ContactApiService`)
- трекеры задач, почта, календари, вики бюро
- всё, для чего в экосистеме уже есть готовый сервер

Это ровно тот же принцип, на котором построен весь остальной проект — один контракт, много
реализаций (Sdk для расширений, `CommandQueue` для транспортов), — только применённый к
**исходящим** интеграциям, где мы его пока не применяли.

## Что для этого уже стоит

`ModelContextProtocol` 1.3.0 уже подключён (`src/Directory.Packages.props:42`) — сейчас используется
только серверная часть, в `AnalyseTool.Mcp/Program.cs`. Клиентская часть в том же пакете.
`Microsoft.Extensions.AI` там же (`:26`), и в #56 фаза 0 уже планирует `IChatClient` — function
calling и MCP-инструменты сходятся в одном месте.

⚠️ Не проверено отсюда: точный клиентский API пакета и его версия. Смотреть вместе с вопросом-гейтом
из #107.

## Где это НЕ должно жить

**Не в процессе Revit.** Причина та же, по которой в #80 выбран LiteDB, а не SQLite: «чисто
managed — нет конфликтов нативных DLL в процессе Revit». MCP-клиент к нескольким внешним серверам —
это граф зависимостей, сокеты и чужие процессы, и тащить это в общий с Revit CLR не надо.

Естественный дом — отдельный процесс. В #56 фаза 3 уже заложен «ingestion worker (console app или
Aspire service)», в #80 вариант C — sidecar по образцу `AnalyseTool.Mcp.exe`. Это один и тот же
процесс, и MCP-клиентские соединения — его работа.

## Безопасность — здесь появляется новый путь эскалации

Стоит записать до того, как это построят.

Клиент MCP означает, что **содержимое из внешних систем втекает в контекст агента**, а этот агент
имеет право звать `SetDataToParameters` и другие destructive-команды на живой модели. Письмо,
комментарий в трекере или страница вики — это текст, который писал не пользователь, и он может
содержать инструкции.

Митигация в #80 уже есть, её надо просто распространить:

- [ ] Destructive-вызовы, случившиеся в цикле, где в контексте было внешнее содержимое, — **только**
      через карточку в inbox, без исключений
- [ ] `ExecuteRevitCode` уже исключён из набора автономного агента (#80, раздел «Безопасность») —
      это правило тем более обязательно здесь
- [ ] Внешнее содержимое помечать в контексте как данные, а не как указания — и это должно быть
      видно человеку в карточке: «на основании письма от …»
- [ ] Явный список разрешённых внешних серверов в настройках, как белый список инструментов агента

Отдельно к #56: там в открытых вопросах уже стоит GDPR-ревью перед индексацией почты. Агент,
ходящий в почту клиентом в реальном времени, — тот же вопрос, только без этапа индексации, на
котором его можно было бы заметить.

## Что это даёт в сумме

Работа по стандартизации, которую мы делаем **наружу** (быть хорошим MCP-сервером), окупается
второй раз, если её потребить **внутрь**. Один протокол на обе стороны, и каждая новая внешняя
система — это конфигурация, а не спринт.

## #116 — Порог прерывания: агент не имеет права на внимание пользователя

state: open | labels: enhancement | created: 2026-08-25 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/116

Политика для проактивного режима из #80 (фаза 3). Заведено отдельно, потому что от неё зависит,
взлетит ли проактивный агент вообще, — а в самом плане она не сформулирована.

## Проблема

Ассистент, который говорит слишком часто, выключают за день. Второго шанса не бывает: человек,
один раз решивший, что штука мешает, больше её не включит и коллегам отсоветует. Это не проблема
качества находок — можно находить правильные вещи и всё равно быть выключенным.

Причём весь остальной план сделан хорошо именно в той части, где «как найти». Отсутствует «когда об
этом стоит открыть рот» — а это разные решения, и второе решает судьбу первого.

## Принцип

В дизайне #80 ответ уже лежит, он просто не назван. Inbox — **не канал уведомлений, а очередь,
которую человек разгребает в своём темпе.** Отсюда:

> Агент не имеет права на внимание пользователя. Он имеет право только на место, куда сложить.

## Что из этого следует

- [ ] Никаких всплывающих подсказок, тостов и модальных окон от агента. Совсем.
- [ ] Единственный фоновый сигнал — счётчик на иконке ленты. Он не мигает и не анимируется.
- [ ] Накопление — поведение по умолчанию. Ничего не «срочно».
- [ ] Человек открывает ленту сам, когда готов, и это единственный момент, когда агент говорит.

Побочная выгода, ради которой это стоит записать в архитектуру, а не в гайдлайн: **раз никто не
ждёт ответа сейчас — фоновую работу можно планировать свободно.** Анализ в паузы `Idling`,
чанками, с отменой при возвращении человека к работе. Принцип не ограничивает производительность,
а разрешает её.

## Что надо решить отдельно

**Что вообще достойно карточки.** Карточка, которую регулярно отклоняют не глядя, хуже отсутствия
карточки: она обучает человека отклонять не глядя, и следующая — важная — уедет туда же.

Здесь нет универсального правила, и подбирать порог придётся на реальной работе. Стартовые
ориентиры:

- находка должна быть **действием**, а не наблюдением («заполнить 40 пустых параметров» — да; «в
  модели 3800 элементов» — нет)
- находка должна быть **проверяемой глазами за секунду** — отсюда изоляция/выделение в виде из #80
- у находки должен быть **пакетный ответ** — если исправлять придётся по одному, это не карточка,
  а отчёт

## Как понять, что порог неверный

Метрика — **не** количество находок. Метрика — **доля карточек, по которым человек что-то сделал**
(применил или осознанно отклонил, а не смахнул пачкой).

Если доля падает, порог слишком низкий, и чинить надо порог, а не UI. Это стоит считать с первого
дня фазы 3, иначе понять будет не по чему: жалоб не будет, просто однажды ленту перестанут
открывать.

## Связанное

- #80 фаза 3 — проактивность, откуда это растёт; фаза 2 — inbox и `Gate`
- #79 — коллизии попадают карточками в ту же ленту, значит и под тот же порог
- #45 — подсказка-призрак: там принцип соблюдён от рождения (появилась, не мешает, игнорируется
  бесплатно). Это тот же порог, только в другой поверхности.

## #117 — Локальная модель — не бесплатный тариф, а условие допуска

state: open | labels: enhancement | created: 2026-08-25 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/117

Переосмысление фазы 2 из #56 и открытого вопроса о границе тарифов там же.

## Как это сформулировано сейчас

В #56 фаза 2 подписана «Embedded inference (free tier, zero-install)», а в открытых вопросах стоит:

> Tier boundary: is RAG search free and LLM synthesis paid, or is RAG paid entirely?

То есть локальный вывод трактуется как **дешёвая версия облачного**: хуже, зато бесплатно и без
установки.

## Почему это, скорее всего, неверная рамка

Для проектного бюро данные модели, переписка с заказчиком, протоколы совещаний часто **не могут
покидать периметр** — это условие договора или внутреннего регламента, а не предпочтение и не
вопрос цены.

Для такого клиента локальная модель — не «бесплатный тариф», а **единственный допустимый**.
Облачная не продаётся ни за какие деньги: решение принимает не тот, кто пользуется, и принимает он
его не по функциональности.

Если это так, то:

- **фаза 2 из #56 — не приятное дополнение, а условие входа в целый сегмент.** Её приоритет выше,
  чем у «бесплатного тарифа».
- **готовность платить может быть именно за локальность**, а не за способность. Граница тарифов
  тогда проходит не по «поиск бесплатно / синтез платно», а по «работает целиком у вас» — и это
  более дорогой и более защищённый товар, чем перепродажа облачных токенов.
- **#115 (MCP как клиент) попадает под то же правило**: внешний MCP-сервер — это тоже исходящий
  трафик. Белый список серверов должен уметь состояние «никаких внешних».
- **настройка «модель агента» из #80** должна выражать не только выбор провайдера, но и ограничение
  «ничего не покидает машину» — как режим, который нельзя случайно нарушить добавлением провайдера.

## Неприятное следствие, которое надо назвать

Локальные модели слабее. А в #80 записано верно:

> Слабая модель в tool-calling-цикле ломается, а не «работает хуже»

Значит сегмент, которому локальность нужнее всех, получает агента, который работает хуже всех — и
ломается тихо, а не заметно. Это не аргумент против, но это то, что определит, что именно можно
обещать этому сегменту.

Возможный ответ: для «периметровых» клиентов сузить обещание. Не проактивный агент общего
назначения, а детерминированные проверки плюс локальная модель на объяснение и формулировку —
гибрид, где LLM не принимает решений. Это укладывается в ту же логику, по которой в #80
`ExecuteRevitCode` исключён из набора автономного агента.

## Что надо проверить, прежде чем на этом строить

⚠️ Это гипотеза о рынке, а не факт. Я не знаю ваших клиентов.

- [ ] Спросить у нескольких реальных бюро: есть ли у них письменный запрет на выгрузку данных
      проекта во внешние сервисы, и кто его снимает
- [ ] Проверить, отличается ли ответ для данных модели и для документов проекта (протоколы, письма)
      — второе обычно строже
- [ ] Выяснить, засчитывается ли «европейский хостинг» как достаточная мера, или требуется именно
      локальность — от этого зависит, нужна ли фаза 2 или достаточно выбора региона

Если ответ окажется «всем всё равно» — рамка «бесплатный тариф» верна и приоритет фазы 2 остаётся
прежним. Стоит выяснить до того, как в неё вложатся.

## #118 — Делегация: локальный триггер + sidecar с сильной моделью (проактивность без пробуждения чужого клиента)

state: open | labels: enhancement | created: 2026-08-26 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/118

Конкретизация варианта C из #80. Там sidecar описан как **способ хостинга цикла**; здесь он
становится **тем, что запускается событием в модели**, — и это превращает его из альтернативы
варианту A в единственный вариант, дающий проактивность.

## Задача

Нужны одновременно две вещи, которые обычно исключают друг друга:

- **проактивность** — агент замечает и приходит сам, а не ждёт вопроса
- **сильная модель** — локальные слабее, а слабая модель в tool-calling-цикле ломается, а не
  работает хуже (#80)

Прямое решение — «толкнуть событие во внешний чат-клиент» — **невозможно**. MCP-сервер не может
начать разговор: соединение открывает клиент. `2026-07-28` это ужесточает (SEP-2260:
server-initiated запросы только пока сервер обрабатывает клиентский). Уведомления сервер→клиент
(`resources/updated`, `tools/list_changed`) толкают **состояние**, а не задачу — клиент от них не
начинает новый ход.

Поэтому вариант A (внешний Claude Desktop) остаётся pull-only навсегда. Разница с вариантом C не в
модели и не в цене — **в том, кто держит инициативу.**

## Топология

Каждая стрелка направлена в разрешённую сторону; будить чужой клиент не требуется нигде.

1. Сработал триггер в Revit — **локально**
2. Детерминированный фильтр решил, что есть о чём думать — **локально, без модели**
3. Плагин позвал внешний мозг — **инициатор: плагин**
4. Мозг дотянулся за подробностями через наш MCP — **инициатор: мозг как клиент**
5. Ответ лёг карточкой в ленту — **плагин толкнул в свой WebView** (канал уже есть:
   host-initiated broadcasts без request id, см. `clientapp/src/RevitBridge.ts`)
6. Человек открыл ленту, когда захотел — **инициатор: человек** (#116)

Следствие: **MCP перестаёт быть альтернативой внутреннему агенту и становится его частью.** Вся
работа по #97, #113 и по описаниям команд окупается здесь второй раз — это рука, которой удалённый
мозг тянется внутрь.

## Конвейер: замечать и понимать — разные вещи

Стоимость растёт только к концу. Наивная схема «событие → прочитать → проанализировать» смешивает
слои и поэтому тормозит работу.

| Слой | Что делает | Цена |
| --- | --- | --- |
| 0. Обработчик `DocumentChanged` | пишет `(ID, имя транзакции, время)` в кольцевой буфер и выходит | микросекунды, **ноль чтений** |
| 1. Фильтр | решает, интересна ли пачка — только по количеству, имени транзакции, времени | **ноль чтений** |
| 2. Момент | не на событии: пауза `Idling` либо явная граница (синхронизация, сохранение). Дебаунс + слияние | — |
| 3. Чтение | минимум под конкретный вопрос, чанками 20–30 через короткие заходы на поток Revit | миллисекунды, **прерываемо** |

**Имя транзакции недооценено.** Это готовая строка («Вставить», «Удалить», «Изменить тип»), которая
классифицирует действие, не читая ни одного элемента. Большинство триггеров может срабатывать на
ней одной.

**Теневой индекс (#80) меняет экономику.** В установившемся режиме чтений из Revit почти нет:
«у каких из этих сорока дверей пустая классификация» — запрос к индексу, вне потока Revit. Дорогая
часть одна — первичная сборка при открытии документа, фоновая и чанками; до готовности агент молчит.
Открытие документа не блокируется никогда.

## Два правила, которых в #80 нет

- [ ] **LLM вне горячего пути.** Слои 0–3 — детерминированный код, никакой модели. Модель зовётся
      только когда код уже решил, что есть о чём думать, и получает **сводку** (~100 токенов), а не
      выгрузку. Следствия: медленная модель никому не мешает, вход влезает в любое окно, и слабая
      модель не может сломать **обнаружение** — только формулировку.
- [ ] **Анализ обязан быть прерываемым.** Человек вернулся к работе → отмена, буфер сохраняется,
      продолжим в следующую паузу. Работа агента всегда ниже приоритетом, чем работа человека.

## Пример целиком

Сценарий из #80 — скопировали 40 дверей, у копий пустая классификация:

1. Событие: 40 добавленных ID, транзакция «Вставить» → буфер. Микросекунды.
2. Дебаунс 2 с. Тихо.
3. Фильтр: 40 добавленных вставкой → интересно. **Чтений ноль.**
4. Ждём `Idling`.
5. Индекс по этим ID: категория, тип. **Revit не тронут.**
6. Классификации в индексе нет → одно чтение 40 элементов по одному параметру, чанками, прерываемо.
7. Детерминированно: пусто у 40 из 40, у источника заполнено.
8. **Только теперь** модель, со сводкой в три строки: текст карточки + решение, стоит ли показывать.
9. Карточка в ленте. Никто не прерван.

Модель вызвана один раз, после того как всё дорогое уже произошло.

## ⚠️ Блокирующий вопрос — коммерческий, не технический

Чем финансируется внешний мозг. Решать **до** кода: от этого зависит вся экономика.

- [ ] **Подписка Claude Code так не вызывается.** Подписка авторизует человека в Claude Code /
      Desktop; programmatic-доступ — отдельный продукт с оплатой за токены. Плагин не может делать
      вызовы, списывающиеся с чужой чат-подписки.
- [ ] **Ключ пользователя (BYO-key)** — чисто, законно, работает. Инфраструктура **уже есть**:
      `AiProviderRegistry` с DPAPI-шифрованием, и #56 фаза 0 прямо говорит «reuse BYO-key pattern».
      Прагматичный ответ по умолчанию.
- [ ] **Наш ключ, перепродажа** — проще пользователю, маржа и риск наши, и для #117 хуже всего.
- [ ] **Claude Code пользователя как sidecar** — дешевле всего для него, но **допустимо ли третьему
      продукту программно его водить, надо прочитать в условиях.** Не проверено; на этом нельзя
      строить, пока не подтверждено.

## Потолок расходов — обязательный элемент, а не настройка

В интерактивном режиме расходы коррелируют с вниманием человека. **Проактивный агент жжёт деньги,
пока никто не смотрит.**

- [ ] Жёсткий дневной потолок, видимый пользователю
- [ ] Упёрся в потолок → молчит до следующего дня. Это нормальное поведение, а не отказ.
- [ ] Локальный фильтр (слой 1) — это в том числе **фильтр на трату**: тот же механизм, что не даёт
      дёргать человека (#116) и занимать поток Revit

## Сегментация

Если думает облако, локальной модели в этой схеме **делать нечего** — слои 0–3 это обычный C#.
Первая версия может обойтись без локального вывода вообще: ни GGUF, ни проверки железа, ни
LLamaSharp, ни нативных DLL в процессе Revit.

Но это ровно тот сегмент, который в #117 не может выпускать данные наружу. Значит два продукта:

- **облачный мозг** — дёшево построить, сильный, требует egress
- **локальный мозг** — дорого построить, слабее, продаётся тем, кому первый не продать

Строить первым облачный правильно, **если** данные выпускать можно. Это тот же вопрос, что в #117,
и здесь он стоит дороже: определяет не приоритет фазы, а порядок постройки продукта.

Отдельно: #56 фаза 2 от этого не умирает — маленькая локальная модель обслуживает **другой ярус**.
Подсказка-призрак (#45) требует долей секунды, облачный круг там недопустим. Три яруса задержки:
мгновенно в интерфейсе → только локально; фоновая проактивность → облако идеально; интерактивный
чат → облако приемлемо.

## #119 — Проверка моделей по своду правил бюро: скиллы, авторство с ИИ, детерминированная проверка

state: open | labels: enhancement | created: 2026-08-28 | comments: 3
https://github.com/Nikola1Davydov/AnalyzeTool/issues/119

Зонтичный план. Из обсуждения внутреннего агента выросла отдельная продуктовая ветка, которая с
агентом связана, но **от него не зависит и отгружается раньше**.

## Два продукта на общем фундаменте

| | Проверка | Ассистент |
| --- | --- | --- |
| Что делает | правила → находки → отчёт | агент, проактивность, суждение, диалог |
| Где ИИ | только при авторстве правил | в рантайме |
| Отгружается | сам по себе | после |
| Планы | **этот** | #80, #118 |

Общий фундамент: каталог команд · теневой индекс · журнал изменений · артефакт правил · лента
карточек. Из-за него построить оба дешевле, чем каждый по отдельности — но отгружаются они
независимо.

## Почему это вообще работает

Категория зрелая (Solibri, Navisworks Validate), и это плюс: спрос доказан, объяснять никому ничего
не надо. У неё известное узкое место — **составление наборов правил мучительно.** Бюро покупает
лицензию, полгода не может собрать ruleset, внедрение затухает.

При этом стандарт у бюро **уже написан**: сорок страниц Word, которые никто не читает, потому что
это проза и проверять её можно только вручную, а значит никогда. Между «текстом» и «набором правил»
лежит человеко-месяц, которого ни у кого нет.

**Вот эту дистанцию ИИ сокращает по-настоящему.** Не «умный анализ модели», а перевод существующего
документа в исполнимую форму. Дифференциатор узкий, конкретный и защитимый.

## Инвариант

> **Смотрит код. ИИ составляет правила и объясняет находки.**

Как только модель выносит вердикт о соответствии, теряется всё, ради чего это делается:
воспроизводимость (два прогона — один результат), защитимость («почему помечено?» → «правило 14,
цитата, стр. 8»), бесплатность прогона. Инженерная область требует именно этих трёх свойств.

Отсюда же — что обещать. **Соответствие** заявленным правилам объективно и отчётно, это продаётся.
**Оценка качества** субъективна, требует LLM и не сертифицируется. Обещать только первое.

## Артефакт: скилл, а не файл настроек

Свод правил — переносимый пакет, а не конфиг:

- лежит **рядом с моделью**, не внутри Claude Code — доступен любому агенту, не привязан к вендору
- привязка к **идентичности модели** (`WorksharingCentralGUID` / UniqueId `ProjectInformation`), не
  к пути к файлу — та же задача и то же решение, что для теневого индекса в #80
- форма — папка с markdown и вспомогательными файлами; следовать существующему соглашению о скиллах
  ничего не стоит и даёт совместимость даром
- слоями: платформа (`LLM.md` через `GetAuthoringGuide` — **такой скилл у нас уже есть**) → бюро →
  проект → дисциплина. Проектный переопределяет офисный, и видно, где отступили

**Два регистра внутри, и их нельзя смешивать:**

- **проверяемые правила** — компилируются в детерминированные проверки
- **наставления** — проза, идёт в контекст агента, автоматических находок не даёт

Риск, за которым надо следить: чтобы «скилл» не стал вежливым названием для большого промпта. Если
останется только проза — продукт превращается в «мы попросили ИИ быть внимательным».

## Что с чем складывается

- **правила + журнал изменений = ревью диффа при синхронизации.** «Code review для BIM» из #80, но
  без агента: проверяется не вся модель, а что изменилось. Лучшая демонстрация из возможных.
- **правила + выделение = «проверь это».** Выделил → проверил → нарушения подсветились. Выделение
  работает и входом, и выходом.
- **правила + отчёт = договорная ценность** при сдаче модели.
- **правила + BCF = процесс команды**; находки попадают в тот же поток, что человеческие (#79).
- **скиллы + реестр (#76) = распространение.** Порог для автора несопоставимо ниже, чем у
  расширений: нет кода, нет сборки под три версии Revit, нет ALC.
- **правила + RAG (#56) = граница определена.** Что формулируется правилом — в свод и под код. Что
  остаётся прозой (протоколы, переписка) — в RAG.

## Фазы

- [ ] **1. Артефакт + ручное авторство + движок.** Лёгкий класс: именование (типов, видов, листов),
      обязательные параметры по категориям, тип по назначению, дисциплина уровней и рабочих наборов.
- [ ] **2. Импорт из документа.** Кандидаты **с цитатами источника** («стр. 14: …»), человек
      разбирает. Цитата нужна дважды: при разборе — проверить не перечитывая; в находке — «согласно
      вашему руководству, стр. 14» звучит иначе, чем «ИИ считает», и с таким замечанием можно
      спорить по существу, поэтому его принимают.
- [ ] **3. Ревью диффа при синхронизации.**
- [ ] **4. Отчёт о соответствии.**
- [ ] **5. Агент** — всё из #80 и #118.

**Фазы 1–4 не требуют ни агента, ни MCP, ни единого вызова модели в рантайме.** Модель работает
только на шаге 2, один раз на документ.

Практическое следствие: продукт отгружается **до** того, как решён хоть один трудный вопрос — чем
финансировать облако, легален ли sidecar, тянет ли локальная модель, где порог прерывания (#116).
Все они переезжают на фазу 5.

Ветка MCP (#107–112) на критическом пути этого плана **не стоит** — она обслуживает ассистента.
#97 и #98 остаются срочными как ремонт отгруженного.

## Блокирующая зависимость

Правило, написанное как «категория Wände», **ломается на любой другой языковой установке.** Свод
обязан выражаться через `BuiltInCategory` и built-in параметры.

Это #113. То есть та работа — фундамент обоих продуктов, а не только удобство для агента: без неё
скиллы бюро непереносимы между установками, а значит непродаваемы.

## Риски

- **Движок больше, чем кажется.** Данные Revit нерегулярны: параметры различаются по категориям,
  бывают общие и проектные, на типе и на экземпляре, плюс единицы. Простой чекер обрастает частными
  случаями быстро.
- **Язык выражения правил — это проектирование языка**, и его легко испортить. Не проектировать
  заранее целиком: взять двадцать реальных правил и строить формат под них. Что не выражается —
  оставлять прозой во втором регистре, это законно.
- **С Solibri по полноте не выиграть.** Выигрыш в авторстве, в работе внутри Revit (а не после
  экспорта в IFC) и в цене — стандарт есть у всех, а Solibri покупают крупные.

## Следующий шаг — не код

- [ ] **Взять одно настоящее BIM-руководство** и вручную разметить: сколько пунктов проверяемы
      детерминированно, сколько остаются прозой, сколько вообще про процесс, а не про модель.

Полдня работы, и эта таблица отвечает сразу на всё: реален ли лёгкий класс, каким должен быть
формат, что обещать в маркетинге и стоит ли браться. Может подтвердить всю конструкцию, а может
сэкономить месяц.

## #120 — Продуктовая граница: смотреть — бесплатно, обеспечивать соблюдение — платно

state: open | labels: enhancement | created: 2026-08-28 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/120

Стратегическое решение + техническая структура разделения. Продолжает #119: модуль проверки —
платная часть AnalyseTool, платформа с ИИ — бесплатная.

## Переосмысление, с которого всё началось

Работа с ИИ — не отход от исходной идеи анализа, а **то, что сделало её продаваемой**. Без ИИ
модуль проверки был бы Solibri-lite: движок, который никто не внедрит, потому что набор правил
собирать некому. Импорт руководства, формализация прозы, линт свода — ровно то узкое место,
которое ИИ снимает (#119).

## Линия

> **Увидеть — бесплатно. Обеспечивать соблюдение — платно.**
> Бесплатная версия говорит один раз; платная не даёт забыть.

| Бесплатно (витрина) | Платно (модуль) |
| --- | --- |
| платформа, расширения, скрипты, MCP, агент | правило как сохранённая сущность, свод |
| **теневой индекс** | линт: конфликты, покрытие, мёртвые правила |
| **инвентари данных** (распределения, опечатки, непрочищенное) | проверка на каждой синхронизации |
| разовый просмотр находки | пакетное исправление |
| текущее состояние в графике | **память**: динамика по снапшотам, сравнение проектов |
| ручная правка | импорт из руководства, отчёт-документ, история срабатываний |

Индекс и инвентарь — в бесплатной части сознательно: показать человеку беспорядок в его
собственной модели убедительнее любой презентации. Инфраструктура бесплатна; платно то, что на
ней построено.

## Риск, который закрывается дизайном

В бесплатной части есть `ExecuteRevitCode`, MCP и агент — **человек может написать себе проверки
сам**. Значит платная часть — не «проверки». Платная часть — всё, что позволяет своду прожить
годы: происхождение каждого правила, линт противоречий, статистика срабатываний, разрешение
конфликтов, отчёт для заказчика, общий стандарт бюро вместо скрипта в чьей-то папке.

Скрипт проверит. Скрипт не скажет, что два правила спорят три недели и что одно не срабатывало
ни разу за пять проектов. Это и есть ров.

## Техническая структура — три разных вопроса, три ответа

**1. Признак — на команде.** Ещё одно поле в `[RevitCommand]`, рядом с `ReadOnly` / `Destructive`
/ `HiddenFromMcp`, доезжает до `CommandRegistration`. Паттерн уже есть.

**2. Проверка — в `CommandQueue.ExecuteAsync`, один раз.** НЕ в `CommandRequest.Gate`: гейт
ставится транспортом на запрос, и транспорт, который забыл его поставить, обходит лицензию.
Лицензия — политика платформы. Комментарий класса это уже обещает: *«scheduling, priorities,
consent gates and per-source policy can be added in ONE place without touching any transport»*.
Одна проверка закрывает WebView, ленту, MCP и любой будущий транспорт.

**3. Платный код — отдельное расширение**, загружаемое собственным collectible ALC, а не код в
`Tools` за рантайм-гейтом. Главный аргумент — не защита, а **поедание собственной еды**: если
флагманский платный модуль построен как настоящее расширение, каждая возможность, которой ему не
хватит, обязана попасть в SDK — и SDK станет по-настоящему пригодным для третьих лиц, потому что
на нём построено то, что мы продаём. `Acme.Sample` — игрушка; продаваемый модуль — проверка
контракта боем. Плюс обновления вне цикла релизов ядра.

**Цена варианта:** нужна подпись сборок — иначе кто угодно кладёт свою DLL с нужным именем. Это
#87, и он перестаёт быть гигиеной: **проверка подписи становится механизмом монетизации.** Одна
работа, две выгоды.

**Граница проходит по модулям, а не по командам.** Весь модуль платный; бесплатное — другой код
в другом месте, а не урезанная версия того же. Тиерить отдельные команды не нужно.

**MCP получает гейтинг даром:** расширение не загружено → команды не зарегистрированы → их нет в
`tools/list`. А у лицензированного агент видит всё — «платный модуль полностью управляем агентом»
само по себе аргумент в продаже.

## Пробный период — по количеству, не по времени

Не «30 дней», а **число правил** (например, пять). Временная лицензия истекает, пока человек
занят другим. Пять правил дают пройти цикл целиком — импорт, проверка, исправление, отчёт — и
упереться в стену ровно там, где продукт становится полезным: стандарт бюро это 50+ правил.

## Защита — честно

Любая клиентская проверка снимается: это .NET в чужом процессе. Покупатель — бюро, которое не
поставит пропатченную DLL, потому что это компания.

- [ ] обфускация не нужна — ломает отладку, от решительного не спасает
- [ ] не звонить домой при каждом запуске: Revit работает офлайн и в изолированных сетях —
      кэшированная лицензия с длинной отсрочкой
- [ ] сильная часть защиты — сервисная: импорт руководства через сервис, реестр, обновления.
      Что не лежит на диске, то не патчится.

## Следствие, меняющее приоритеты

Бесплатная часть становится витриной — а сейчас она встречает человека так: #98 (GetElements
падает на любом вводе), #97 (все ошибки неотличимы), #100 (tools/list протухает), #102 (UI
замерзает). Пока это была «поддержка отгруженного» — терпимо. Теперь это **блокеры выхода**:
кто упёрся в падающий базовый инструмент, до платного модуля не дойдёт.

Порядок: починить витрину (#97 → #98 → #100) → инвентарь на индексе (бесплатно) → правила
платным модулем.

монетизация) · #80 (индекс) · #97 #98 #100 #102 (блокеры витрины)

## #121 — Шаблон параметров: декларативная половина свода (GUID + привязки + значения)

state: open | labels: enhancement | created: 2026-08-28 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/121

Часть платного модуля (#120), уточняет #119. Развитие идеи из #53 (Parameter Requirements
Table) — теперь у неё есть основание в конструкции свода.

## Дыра, которую это закрывает

В макете есть строка `FLUCHTWEGBREITE — expected by standard · not in project`. Она ни на чём не
стояла: откуда система знает, что параметр *ожидается*? **Отсутствие проверяемо только против
декларации.** Шаблон — эта декларация.

Заодно исчезает двусмысленность «параметра нет ≠ параметр пуст» (ловушка из #119): первое чинится
созданием из шаблона, второе — заполнением.

## Ключевая сходимость: шаблон и правила — один артефакт

Запись шаблона = идентичность (имя, **GUID**, тип данных) + привязка (категории, тип/экземпляр)
+ допустимые значения + правила. Но «допустимые значения + не пусто» — это правило из
конструктора, а «привязан к Türen» — это область правила.

Значит не «база параметров И свод правил», а **свод правил, получивший декларативную половину**.
Одна сущность, один файл, один интерфейс. Два артефакта здесь строить нельзя — они разойдутся.

## Механика Revit, которую нельзя обойти

- [ ] **GUID — это всё.** Общие параметры идентифицируются GUID'ом, не именем. Шаблон обязан
      хранить GUID, и «создать в проекте» создаёт параметр с тем же GUID — иначе спецификации,
      марки и фильтры между проектами не переносятся.
- [ ] **«Одно имя, разные GUID» — самостоятельная находка линта.** Классическая тихая болезнь
      бюро; никто её не видит, пока не «сломается» спецификация. В макете это красная строка
      TRAGWERK.
- [ ] **Файл общих параметров Revit — это .txt.** Не изобретать свою идентичность: импортировать
      существующий файл бюро как отправную точку (тот же ход, что с BIM-руководством — контент
      уже есть, он просто в неудобной форме) и экспортировать обратно для совместимости. Своё

- [ ] **«Применить к проекту» — запись**: предпросмотр + одна транзакция с внятным именем, как у

## Главный выигрыш: направление потока переворачивается

проекте данных нет — и правила приходят **из шаблона, в день ноль**: применил шаблон бюро →
параметры созданы, привязаны, проверка работает до первой стены.

Один артефакт, два направления. Это и есть переносимость стандарта бюро между проектами.

Слои: офисный шаблон + проектные переопределения, как у свода.

## #122 — Отчёт как документ: А4-канва из живых блоков, печать из WebView2

state: open | labels: enhancement | created: 2026-08-28 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/122

Часть платного модуля (#120). Даёт содержание кнопке «Compliance report» из #119 и поглощает
часть #57 (табличный блок — место, где спредшит-модуль встречается с проверкой).

## Рамка

**Дашборд — для себя, документ — для других.** В стройке результат работы — документ:
Dokumentation к сдаче, Nachweis, отчёт по фазе. Дашборд в конце всё равно скриншотят в Word.
Убираем этот шаг: поверхность, на которой смотрят данные, **сразу и есть** то, что отдают.

У Revit здесь дыра: для чертежей есть листы, для *данных* — ничего. Документацию по данным все
делают руками (экспорт в Excel → вёрстка в Word), к каждой сдаче заново.

## Форма

Формат страницы (А4 портрет; ландшафт позже), скролл вниз, вертикальный стек блоков. На каждой
печатной странице — **штамп**: логотип бюро, проект (из ProjectInformation — уже читаем для
идентичности модели), дата, автор, «Seite X / Y». Мелочь по коду, огромная разница в «можно ли
отдать заказчику».

## Три свойства, которые делают это продуктом

- [ ] **Блок — это запрос, а не картинка.** Привязан к теневому индексу («распределение
      BRANDSCHUTZ по Türen», «находки последней проверки», «покрытие»). Собрал документ один
      раз → он перерисовывается при каждой синхронизации и в каждом проекте. Отчёт — шаблон,
      а не разовый артефакт. В этом разница с «экспортом в PDF», который везде приделан сбоку.
- [ ] **Блок декларативен** (тип + запрос + подпись = JSON) → **его может собирать агент**:
      «собери отчёт к пятничной сдаче» → черновик из блоков, человек принимает или отклоняет
      каждый (в макете — зелёный пунктирный блок Accept/Discard). Та же модель активации, что у
      правил (#118, #119): LLM собирает декларативный артефакт, детерминированный движок рендерит.
- [ ] **Печать почти бесплатна:** WebView2 умеет `PrintToPdfAsync`, постраничность — print-CSS
      (разрывы, повтор шапки таблицы, номера страниц). Ни генератора PDF, ни второй вёрстки.

## Граница бесплатно/платно (по линии #120)

- график в раскрытой строке инвентаря — бесплатно (витрина)
- конструктор документа, печать, штамп — платно
- блоки с **динамикой** («пустых полей за 6 недель: 120 → 44») — платные вдвойне: физически
  требуют снапшотов (#80, Parquet). Кривая качества к сдаче — доказательная история, за которую
  бюро платит. Буквально: бесплатная версия говорит один раз, платная помнит.

## Ограничение, принятое как фича

**Редактор документов — продукт-ловушка.** Закрепить жёстко:

- вертикальный стек, одна колонка, никакого свободного позиционирования
- блоки крупные: заголовок, текст, график, таблица, находки, покрытие, тренд, разрыв страницы
- ценность — в живой привязке к данным, не в вёрстке. Кому нужна вёрстка, у того есть Word.
- 16:9-слайды — отложены: это другой медиум, а не другой размер страницы

Вкладка Report: https://claude.ai/code/artifact/02606410-fcf3-4c25-a8e9-388b924fe5e1 — две
А4-страницы (бумага остаётся белой и в тёмной теме — это предпросмотр печати), живой график,

## #123 — MCP-поверхность модуля проверки: инвентарь как самое плотное представление модели, черновики правил, RunCheck

state: open | labels: enhancement | created: 2026-08-28 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/123

Мост между модулем проверки (#119, #120) и агентом (#80, #118). Требование пользователя,
зафиксированное дословно: создание правил через LLM/MCP и доступ к состоянию свода — «это
важная вещь, это должно быть».

## Поверхность

| Команда | Что делает | Доступ |
| --- | --- | --- |
| `GetDataInventory(kind, category?)` | инвентарь с распределениями — то, что видно во вкладке Data | read-only |
| `GetRuleset()` / `GetRulesetHealth()` | свод, конфликты, покрытие, мёртвые правила, статистика срабатываний | read-only |
| `CreateRuleDraft(...)` | **черновик**, не правило | пишет в свод, не в модель |
| `RunCheck(scope?)` | прогнать проверку, вернуть находки | read-only по модели |
| `PreviewFix(ruleId)` / `ApplyFix(ruleId)` | предпросмотр / применение исправления | Apply — destructive, через гейт (#106) |
| `CreateReportBlockDraft(...)` | черновик блока отчёта (#122) | пишет в документ-шаблон, не в модель |

## Два принципиальных решения

**Черновик, а не правило.** Агент, создающий правила напрямую, — это ИИ, пишущий политику:
правило определяет, что пометят и что автоматически перезапишут в чужой модели. Черновик,
который активирует человек, стоит одного клика и сохраняет конструкцию «агент предлагает —
человек утверждает» (#80 inbox, #118, блок Accept/Discard в #122). Позже можно добавить
пользовательский переключатель «активировать сразу» — но по умолчанию черновик.

**`GetDataInventory` ценен агенту сам по себе, безо всяких правил.** Строка

```
BRANDSCHUTZ: EI30 214 · EI60 38 · EI90 12 · пусто 44
```

— это ~20 токенов, и она говорит о модели больше, чем триста строк `GetElements`. Это ответ на
экономику контекста из #118 (окно, в которое не влезает цикл) и лучший вклад в #105: агент
бежит в `ExecuteRevitCode`, когда специализированные команды неудобны — плотный инвентарь
делает специализированный путь *выгодным*.

## Что откуда берётся

Всё читает **теневой индекс** (#80), не модель: `GetDataInventory` и `RunCheck` не трогают поток
Revit и отвечают при занятом Revit. Это то самое свойство, ради которого индекс переехал в
бесплатную часть (#120).

## Свод как MCP-ресурс — позже

Свод стабилен, кэшируем, привязан к проекту — буквально то, подо что в MCP сделаны ресурсы, с
`cacheScope` из 2026-07-28 (#107). Упирается в то же, что и всё остальное: у моста нет глагола
для ресурсов (#84 P2). До тех пор — инструмент `GetRuleset`.

## Гейтинг

Ничего специального: модуль не лицензирован → расширение не загружено → команд нет в
`tools/list` (#120). У лицензированного агент видит всю поверхность — «платный модуль полностью
управляем агентом» — аргумент в продаже.

## Связанное

ответов) · #84 P2, #107 (ресурсы) · #106 (гейт на Apply)

## #124 — Папка проекта: общее хранилище источников, свода и журнала

state: open | labels: enhancement | created: 2026-08-31 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/124

Где физически живут неизменяемые источники (raw/), вики-свод, шаблон и журнал. Решение:
**папка и есть интерфейс** — не «загрузка в систему», а обычная папка, в которую бюро и так умеет
класть файлы. Explorer как UI с нулевым обучением.

## Схема

```
по умолчанию:  %LOCALAPPDATA%\AnalyseTool\projects\<model-guid>\   ← работает сразу, соло
в настройках:  «Папка проекта» → \\server\Projekte\WohnparkSüd\AnalyseTool\  (или OneDrive)

внутри:
  sources\          ← сюда кидают всё: PDF, письма, транскрипты, .txt параметров
  regelwerk.md      ← вики: правила + наставления, с цитатами
  template.params   ← шаблон параметров (#121)
  log\              ← журнал
  .cache\           ← служебное: снимки по хешу, индекс извлечения
```

Выбрал общую папку → команда соединилась: несколько человек кидают документы, свод общий, журнал
общий. **Коллаборация без единого нашего сервера** — файловый шар и есть бэкенд. Для периметрового
клиента из #117 идеально: ничего не покидает сеть бюро, нам нечего хостить и нечего проходить по
GDPR-аудиту. Паттерн UX уже есть в продукте — папки библиотек в палитре семейств.

**Не в RVT** (Extensible Storage раздувает файл и уезжает ко всем — уже запрещено для индекса в
#80, для PDF тем более).

## Идентичность по хешу, не по пути — насмерть

Папка живая: файлы переименуют, поправят, удалят. Цитата «R-012 → S. 8» обязана открываться
годами, поэтому при первом прочтении файл получает хеш, снимок уходит в `.cache\`, цитаты
ссылаются на хеш. Поломки превращаются в проверки линта:

- [ ] файл изменился → **новая версия** + линт дрейфа: «v8 пришла, 12 правил цитируют v7,
      страница 8 изменилась — перепроверить?» (диффом извлечения v7 против v8)
- [ ] файл удалили → «источник исчез из папки, снимок сохранён, 12 правил цитируют»
- [ ] тот же файл под другим именем → узнан по хешу, дубликата нет

Дрейф источника — тот самый класс тихого устаревания («ошибки копятся, и не заметишь откуда»),
только на уровне документов, и он ловится механически.

## Два настоящих риска

**Одновременная запись.** Несколько человек и агентов в `regelwerk.md` на SMB — потерянные
правки. Без переусложнения: правки свода через плагин с **lock-файлом** («свод редактирует
Анна» — модель, которую Revit-пользователи знают наизусть), а **журнал шардован по людям**
(`log\anna.jsonl`) и сливается при чтении — записи не конкурируют вообще. По сути worksharing
для знаний: центральная папка, локальные кэши, моменты синхронизации.

**Папка станет свалкой.** Кинут всё: фото, ZIP, «Kopie von Kopie (2)». Система триажит, а не
давится: новый файл → очередь «Новые источники (N)» → человек (или черновик от агента)
распределяет: в правила / только в RAG / игнорировать. Необработанный файл — не ошибка, просто
пока не цитируется. Watcher **уже заявлен** в #56 фазе 3 («watch project folder, index
new/changed files») — та же папка, тот же наблюдатель, два потребителя: правила и RAG.

## GDPR-галочка с первого дня

Письма и транскрипты разговоров — персональные данные конкретных людей; транскрипты ещё и
согласие на запись. В #56 уже стоит открытым вопросом. В дизайне с первого дня: «эти типы файлов
индексируем только после решения бюро» — не после первого вопроса юриста.

## #125 — Headless-доступ к проекту: сервис-ответчик над папкой, Teams/Telegram как адаптеры

state: open | labels: enhancement | created: 2026-08-31 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/125

«Какое состояние проекта? Какие проблемы?» — вопрос в чат, ответ на текущий момент. Возможно,
потому что **всё спроектированное читается без Revit**: индекс, снапшоты, свод, журнал, отчёт
живут в папке проекта (#124), а не в RVT. Revit нужен, чтобы данные производить; чтобы отдавать —
нужна только папка. Это исполнение давней идеи #52 (Fingerprints — данные модели вне Revit).

## Архитектура: не «телеграм-бот», а на шаг общее

Примитив — **сервис, читающий папку, с тем же MCP-контрактом, что у #123**:

```
в Revit:      GetDataInventory / GetRuleset / RunCheck  → живой индекс
вне Revit:    те же команды                              → снапшоты из папки
```

Один словарь, две подложки — агенту всё равно, откуда ответ. Каналы (Claude Desktop,
Telegram, Teams, почта, cron) — тонкие адаптеры, мозг один.

**Где крутится мозг:** OneDrive держит файлы, а не вычисления. Естественный хост — ingestion
worker из #56 фазы 3: он и так долгоживущий и смотрит папку. Один процесс, три роли:
watcher + индексатор + ответчик. Офисный сервер / всегда включённая машина (обязательное
условие для периметра #117); для остальных возможен облачный вариант.

## Три условия выпуска

- [ ] **Штамп свежести на каждом ответе.** «По состоянию на синхронизацию 17:43, A. Weber».
      Никто не открывал Revit три дня → бот честно говорит «данным три дня». Ответ без
      штампа — враньё по умолчанию.
- [ ] **Канал только-чтение по отношению к модели.** Никаких исправлений через мессенджер
      (обратная петля создаёт *карточки-намерения* — см. следующий issue, — но не изменения).
      Заодно гасит инъекцию: читающий и ничего не могущий бот скучен атакующему.
- [ ] **Кто имеет право спрашивать** — список аккаунтов, привязка к проекту. Это данные
      проекта на телефоне.

Про Telegram честно: сообщения ходят через внешние серверы — для соло нормально, для немецкого
бюро с NDA — разговор с юристом. Поэтому адаптеры: **Teams** для корпоративной Германии.
Архитектура не меняется.

ровно то, что разрешает порог #116.

## Экономика

Каждый вопрос — токены, но отвечает бот из инвентарей и снапшотов, а их плотность уже посчитана
в #123: «BRANDSCHUTZ: EI30 214 · пусто 44» — ~20 токенов вместо трёхсот строк. Компактность,

## #126 — Обратная петля: комментарий из чата → карточка → применение в Revit → исход → кандидат в правило

state: open | labels: enhancement | created: 2026-08-31 | comments: 0
https://github.com/Nikola1Davydov/AnalyzeTool/issues/126

Сценарий-источник (дословно): руководитель получил отчёт в Teams, заметил ошибку в кодировке
имён листов, ответил «хочу так и так — тут ошибка» — и когда проектировщик открывает Revit,
AnalyseTool сам предлагает эту поправку к применению.

Для петли не нужно изобретать ничего нового — все станции уже спроектированы (#116 лента,
#122 блоки-запросы, #123 черновики, #124 папка, #125 сервис). Нужно правильно провести через
них комментарий.

## Шесть станций

**1. Ответ на конкретный блок отчёта.** Блок — это запрос (#122), значит комментарий
**наследует контекст**: какие листы, какой срез. Как комментарий к строке диффа в PR против
письма «где-то ошибка» — разбор LLM становится надёжным, потому что он знает, о чём речь.

**2. Комментарий → карточка, не команда.** Принципиально: чат создаёт **намерения**, никогда —
изменения (#125: канал только-чтение по модели). Карточка несёт:
- слова руководителя **дословно** — это авторитет; разбор LLM — догадка и помечен как догадка
- структурное предложение с предпросмотром: «переименовать 3 листа: A4_101 → A_04_101 …»
- происхождение: «запросил H. Brandt · Teams · вс 21:14 · в ответ на пятничный отчёт»

Комментарий неоднозначен («кодировка неправильная» — а какая правильная?) → бот **уточняет там
же в чате**, у держателя намерения. Карточкой становится только полностью определённое.

**3. Через папку.** Сервис кладёт карточку в `inbox\` (#124), плагин читает при открытии.
**Папка — шина сообщений**, прямого соединения Teams↔Revit нет. Устойчивость ко времени даром:
написано в воскресенье вечером — ждёт до понедельника 8:00.

**4. Лента по правилам #116.** Без всплываний, счётчик, человек открывает сам. Слова шефа,
разбор, предпросмотр, Apply / Decline. Apply — одна транзакция с внятным именем. Применяет
**человек с моделью в руках**, не руководитель из чата: инициатива сверху, исполнение и
суждение на рабочем месте (контекст, занятые элементы, worksharing).

**5. Исход возвращается в Teams.** «Готово: 3 листа · пн 9:12 · A. Weber» — или «Отклонено:
кодировка согласована с заказчиком, AIA стр. 4». **Обязательная станция**: без закрытия петли
руководители перестают доверять каналу после второго безответного комментария.

**6. Поправка — кандидат в правило.** Руководитель только что сформулировал конвенцию, которой
в своде не было. Две кнопки, а не одна:
- [ ] **Исправить 3 листа** — разовая починка
- [ ] **Записать правилом** («имя листа соответствует A_XX_YYY») — через черновик и активацию
      (#123)

Так свод растёт из реальных поправок реальных людей — петля «решения → человек продвигает →
правила» получает вход из внешнего мира. Через полгода таких ответов у бюро накапливается
стандарт, который никто специально не писал.

## Жёсткая линия

**Авто-применения из чата нет. Совсем.** Даже «очевидного». Текст из мессенджера — пусть от
аутентифицированного человека — не трогает модель без человека у модели. Предпросмотр + Apply
в Revit — граница, которая делает схему продаваемой бюро.

## Родство с BCF

Карточка — морально BCF-issue (замечание не-моделлера, разрешаемое моделлером), только с
приложенным машинно-исполнимым предложением. Экспорт карточек в настоящий BCF — мостик к
Solibri/BIMcollab почти даром; кнопка «Export BCF» в макете уже стоит (#79, #119).
